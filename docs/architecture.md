# FamilyOS Architecture

This document describes how FamilyOS is built and the rules that keep it that way, each with its reason. [AGENTS.md](../AGENTS.md) is the short checklist; this is the long form. The rules are not frozen, but they are changed deliberately: a change to a rule updates this document in the same pull request.

The goal is a foundation that is **loosely coupled, yet small enough for a small team to carry**. Many choices follow what comparable open-source projects chose or later regretted (Immich, Home Assistant, Medusa, Backstage, Directus, n8n, Ghost, Karakeep, LibreChat, Tandoor, Mealie, Actual Budget, Paperless-ngx).

## 1. Design principles

1. **Seams first, implementations on demand.** Infrastructure that is likely to change (job queue, file storage, LLM provider, identity) sits behind a port. A second implementation is written only when there is a real need.
2. **Extensions never import each other.** They communicate only through actions, events and typed IDs.
3. **Zod is the single source of truth.** One schema drives request validation, OpenAPI, LLM structured output, draft-card forms and the tools offered to the assistant and to MCP clients.
4. **Expand-only changes.** Database schema, configuration and API only grow in minor releases. Breaking changes happen only in a major release and are announced in advance.
5. **AI proposes, people decide.** No model changes family data on its own; every change it suggests is a draft a person approves (§8, §11).
6. **Region-neutral, language-neutral.** Nothing in the product assumes a country, a language or a household shape (§6, §13).

### Scope

- **One installation is one family.** There is no multi-tenant hosting.
- **SQLite is the only database** (§12).
- **Extensions are packages the family installs.** The image ships them all; a few are always there (calendar, lists, Quick add, the assistant, the board, chores, records) and the others are offered (§6 "Packages and installation"). Only packages built from this repository are loaded: there is no sandbox for third-party code, so there is no marketplace. Language packs and theme packs are data, validated and rendered as data, so they can be installed at runtime as well (§6).
- **FamilyOS does not replace Home Assistant.** It shows what a family chose from it, and switches only the things the family chose, through Home Assistant, for the people allowed to (a capability); family displays and the AI never switch anything. Home Assistant already runs devices well; FamilyOS only calls the few services of a fixed table (on and off, open and close, lock and unlock, run a scene), so the token, which Home Assistant cannot limit, can do no more through FamilyOS than that.

Reasons for the less obvious choices:

- **Kysely, not an ORM, and no repository layer.** Kysely is typed and transparent, and its migrations are explicit code. Auto-generated SQLite schema diffs can rebuild tables, which is risky under a compatibility promise. With SQLite as the only database, repository interfaces would add an interface and an implementation per aggregate for no swap that will happen; tests run against in-memory SQLite with real migrations instead. Table types are written by hand next to the migration that creates the table, and a test compares the migrated schema with them.
- **No dependency-injection framework.** `apps/server` builds every adapter once and assembles a typed `ctx` whose shape the SDK defines. Extensions receive it in `register(ctx)` and in action and job handlers; tests build one from `@famos/testing`. Wiring stays plain TypeScript, and swapping an adapter is one line in the composition root.
- **OpenAPI and a types-only client** (§15), so native clients can generate their own SDK and generator upgrades touch almost nothing.
- **better-auth behind an `Identity` port**, with its tables created by our own committed migrations (the SQL was generated once and reviewed; a test checks it still matches what better-auth expects). Its runtime schema check is off because it would run before our migrations on first start. better-auth needs an email per user, so a profile that signs in only with a PIN gets a synthetic, non-routable address with email sign-in disabled. Passkeys are not offered: for a self-hosted app they need HTTPS and break when the instance's address changes.
- **i18next**, because one mature library serves the web app and the server (notifications, Telegram and email texts) and loads catalogs at runtime without a CDN or a compile step.

### Dependency policy

- Exact versions only; the lockfile is committed.
- Renovate opens grouped update PRs; security updates (especially better-auth advisories) are merged promptly.
- Small utilities are our own code rather than a dependency: the JSON-lines logger (`packages/adapters/src/runtime/logger.ts`), the RFC 9562 UUIDv7 generator (`uuidv7.ts`), Web Push encryption, and the few UI primitives that would otherwise need a headless-UI library (avatar, label, separator).
- No feature depends on a third-party server's API except the ones the family configures (an AI provider, Telegram, an email mailbox, remote backup targets, calendar feeds, the weather). Integrations that follow an upstream API with its own release schedule are not bundled.
- Prefer dependencies with a small surface and low churn (for example `openapi-typescript` over full SDK generators).
- pnpm 12 runs dependency install scripts only for packages listed under `allowBuilds` in `pnpm-workspace.yaml`.
- Tool telemetry is disabled in CI (`TURBO_TELEMETRY_DISABLED=1`, `DO_NOT_TRACK=1`); contributors can run `npx turbo telemetry disable`.
- Known watch items: SvelteKit 3 is new (expect patch releases); Kysely is pre-1.0; Vite 8's Rolldown has an open nondeterministic crash on Linux CI (rolldown#10860) — pin rolldown via `pnpm.overrides` if it appears; revisit TypeScript 7 when 7.1 ships its API; revisit `node:sqlite` when it reaches Stability 2.

### Layers and responsibilities

- **apps/server** is the composition root and the only place that knows concrete libraries. It reads configuration, builds adapters, creates the typed `ctx`, registers extensions and starts the HTTP server and/or worker depending on `FAMOS_ROLES`.
- **Loading extensions.** The server names no extension: at start it loads the extension packages it finds (`apps/server/src/extensions/`) and hands their definitions to the kernel. The packages shipped with the app are found only beside the server bundle (`/app/server` → `/app/extensions` in the image, `apps/server/dist` → `dist/extensions` in a checkout), which is what makes them trusted, so no setting moves the folder; every one listed in its `extensions.json` (always and offered) is loaded. Before the first package is imported, a synchronous resolve hook (`module.registerHooks`) takes over the imports of code inside a package folder: the shared modules (`@famos/sdk`, `zod`, `kysely`, `@famos/time`) resolve to the server's own instances (`shared/modules.json`), `node:` modules and the package's own files resolve as usual, and any other import (another bare package, a file outside the folder) is refused with an error that names the package. A package is also refused when its `famos-package.json` was built for another platform (`built.sdk` must be the host's `SDK_VERSION` or an earlier patch of the same minor; the manifest's caret is checked as well) or when its code carries a manifest that differs from the one the package describes. In development and tests `FAMOS_DEV_EXTENSIONS=<workspace>/extensions` loads the extensions' source instead (`pnpm dev` and `pnpm gen` set it, with a warning in the log); it is refused when `NODE_ENV=production`. Server tests find the extensions the same way (`apps/server/test/support/extensions.ts`).
- **Inbound adapters** (HTTP routes, WebSocket, CLI, MCP, Telegram) only validate input, resolve the `Actor` (who is calling, with which role) and call core or an action. They contain no business rules.
- **@famos/core** is the kernel: members and roles, RBAC, the action registry and runner, drafts, the job runner, the in-process event bus, the migrator and backups.
- **Extensions** own features. Each owns its tables, actions, routes, events, migrations and UI contributions.
- **@famos/sdk** is the only package extensions depend on. It defines port interfaces, `defineExtension`, `defineAction`, ID and slot types.
- **Adapters** implement ports.

Each extension is **one package** with subpath exports:

| Subpath | Contents | Who may import it |
|---|---|---|
| `./contract` | Zod schemas, route definitions, action input/output, event payloads | anyone (other extensions, web, server) |
| `./server` | action handlers, queries, job handlers, migrations | `apps/server` only |
| `./web` | Svelte pages, widgets, draft-card renderers | its own package build (loaded by the app at run time) |

**Extension packages.** `famos-pack` (`@famos/pack`, each extension's `build` script) builds an extension into a package folder, `extensions/<id>/dist/`:

| File | Contents |
|---|---|
| `server/index.mjs` | the server code as one ES module (with its source map) |
| `web/index.js`, `web/chunks/` | the `./web` entry as ES modules (Vite, components with their CSS injected); pages stay chunks of their own, what the entry and its pages share is one `common` chunk |
| `web/styles.css` | the Tailwind utilities its web code uses, in the `ext` cascade layer |
| `messages/*.json` | the extension's catalogs, English and its own translations |
| `openapi.json` | its routes and actions |
| `LICENSE` | the extension's license, or the repository's |
| `famos-package.json` | `format`, `manifest` (its package.json `famos` field, unchanged), `name`, `license`, `built` (`sdk`: the platform version, `svelte`), `entries` (`server`, `web`, `css`), `labels` (each language's `feature_name` and `feature_description`, as `name` and `description`) and `files`: every other file with its SHA-256 |

The server bundle leaves out only the modules the host shares with every package (`SHARED_SERVER`: `@famos/sdk`, `zod`, `kysely`, `@famos/time`) and Node's own `node:` modules; everything else it uses (other extensions' `./contract`, `@famos/i18n`, libraries) is inlined. The build reads the bundle's metafile and fails on any other import it would leave to the host, a builtin written without `node:` or a subpath such as `zod/mini` included. The web bundle leaves out `SHARED_WEB`: the browser subpaths of Svelte and the script subpaths of `@famos/ui`, read from their `package.json` exports, and `@famos/sdk`, `zod`, `@famos/time` and `@famos/api-client`; the app hands those over at run time (§6, Web side). Icons are not shared: each package keeps the ones it uses.

`SDK_VERSION` is the platform version that packages are built against. `packages/pack/platform.json` records it with Svelte's minor, zod's major, Kysely's minor and the export names of `@famos/sdk`, `@famos/time`, `@famos/api-client` and every `@famos/ui` subpath; a test fails when they change and `SDK_VERSION` was not raised (its minor when something a built package may use changed or went away, at least its patch when names were only added). `pnpm --filter @famos/pack platform:update` rewrites the file once the version is raised.

`extensions.json` at the root says which packages the image ships: `always` (calendar, lists, inbox, assistant, board, chores, records: records because home, pets and vehicles need it), `offered` (ambient, kitchen, pets, vehicles, home) and `default`, the offered ones a fresh family gets. `pnpm build` runs turbo, which builds every package, and then `scripts/collect-extensions.mjs`, which copies each listed package and `extensions.json` to `dist/extensions/`; an extension folder the file does not name, or a named one without a built package, fails the build. The server loads these packages at start (§3, Loading extensions).

## 5. Dependency rules (enforced in CI)

- `sdk` depends only on `zod` (and Kysely *types*).
- `extensions/*` may import `sdk`, `ui`, `time`, and other extensions' `./contract` only; their `./web` code may also import `api-client` and the `./api` types of an extension their manifest depends on (server and contract code may not).
- `core` may import `sdk`; it must not import adapters or `db`.
- `web` may import `api-client`, `ui`, `sdk` and `time`; it depends on no extension and loads their `./web` at run time (only its dev server compiles their source), never server code or an extension's `./api`.
- `adapters` and `db` are imported only by `apps/server`. Extensions receive the database through `ctx.db`, typed by the SDK.
- `apps/server` imports no extension: it loads them from packages at start (§3).

Violations fail the build via dependency-cruiser.

**Why the boundaries are hard.** Without them, features start importing each other's internals and sharing tables, and the system becomes impossible to change: Medusa had to isolate its modules and forbid cross-module foreign keys in a major rewrite, and Backstage rewrote its plugin system because wiring was unstructured. With these rules any extension can be removed, turned off or rewritten without touching the others, as long as its `./contract` stays compatible. The price is that some reads are indirect (an action or a typed id instead of a join).

## 6. Extension contract

An illustrative extension (the real ones live in `extensions/`):

```jsonc
// extensions/shopping/package.json (the manifest, see "Manifest" below)
{
  "name": "@famos/ext-shopping",
  "version": "1.2.0",
  "famos": {
    "id": "shopping",
    "version": "1.2.0",
    "sdk": "^0.5.0",
    "capabilities": ["shopping.view", "shopping.edit"]
  }
}
```

```ts
// extensions/shopping/src/server/index.ts
import pkg from '../../package.json' with { type: 'json' };
import en from '../messages/en.json' with { type: 'json' };
import tr from '../messages/tr.json' with { type: 'json' };

export default defineExtension({
  manifest: pkg.famos,
  messages: { en, tr },                         // its texts, under its id (see Language packs)
  capabilities: [shoppingView, shoppingEdit],   // defineCapability(...), see §13
  actions: [addItem, checkOff],                 // see below
  routes: shoppingRoutes,                       // defineRoute(...) definitions; served under /api/v1/shopping
  events: { 'shopping.item.added': ItemAdded },
  migrations,                                   // Kysely migrations; tables prefixed shopping_*
  register(ctx) {
    // subscribe to events, register job handlers
  },
});

// extensions/shopping/src/actions/add-item.ts
export const addItem = defineAction({
  id: 'shopping.addItem',
  title: 'Add item to shopping list',
  input: AddItemInput,                          // Zod
  output: ShoppingItem,
  requires: 'shopping.view',                    // who may call it at all
  approval: { unless: 'shopping.edit' },        // others propose a draft instead
  ai: { description: 'Add things to buy…' },    // the AI may propose it (as a draft)
  undo: (item) => ({ actionId: 'shopping.removeItem', input: { id: item.id } }),
  async run(uow, input) {                       // one SQLite transaction
    const db = uow.db.withTables<ShoppingTables>();  // hand-written table types
    /* … */
  },
});

// extensions/shopping/src/web/index.ts
export default defineWebExtension({
  manifest: pkg.famos,                      // the same id as the server side
  messages: en,                             // English; other languages come with the pack
  nav: [{ id: 'shopping.nav', path: '/shopping', labelKey: 'shopping:nav', placement: 'primary' }],
  pages: [{ id: 'shopping.page', path: '/shopping', component: () => import('./ShoppingPage.svelte') }],
  slots: [{ slot: 'dashboard.card', id: 'shopping.list', component: () => import('./ListCard.svelte') }],
  drafts: [addItemPresenter],               // how proposed addItem drafts look in Quick add
});
```

- **Typed IDs**: UUIDv7 strings with an entity prefix (for example `shop_item_…`), so the owning extension can be resolved from an ID.
- **No cross-extension foreign keys.** Referencing another extension's data means storing its typed ID.
- **Configuration** is a Zod schema with defaults; changes are expand-only.
- **Database access**: `ctx.db` / `uow.db` are typed `Kysely<object>`; each extension adds its own tables with `db.withTables<MyTables>()`. The types only help: what keeps an extension to its own tables is the scope described in "Isolation" below. Members and family settings (time zone, locale) come from `ctx.family` / `uow.family`.
- **Turning off** (Settings → Family → Extensions, `core.setFeatureEnabled`): every id an extension owns is namespaced by its id, so core can stop it without its help. A turned-off extension keeps its data; its routes and actions answer `feature_off`, its actions leave the AI catalog, its jobs stay queued, its event handlers do not run, its capabilities are inactive and the web app hides its nav, pages and cards (`me.disabledExtensions`). Core cannot be turned off. Web entries name themselves for that page with `labelKey`/`descriptionKey`.
- **Web side**: each extension's `./web` entry registers with the app, which never names an extension itself (see "Web side" below).

### Isolation

Each extension gets its own `ExtensionContext`, built by the kernel from its manifest (`kernel.contextFor(id)`): its routes, jobs, event handlers (`register`), search loaders and the host contracts it provides (share target, conversation) all receive it. The action runner builds each action's unit of work for the action's owner, and `uow.run` gives the called action its own extension's view of the same transaction. Core and the infrastructure adapters are the host and see everything; their names (`RESERVED_NAMES` in the SDK: core, auth, identity, ai, queue, email, backup, telegram, webpush) cannot be an extension's id, and no extension's table prefix may overlap theirs. What the context keeps the extension to:

| | What it may | Enforced by |
|---|---|---|
| `db` | Only tables, indexes and views named with its `tablePrefix`, in queries, raw SQL and DDL, its migrations included; never the schema itself (`sqlite_master`, `pragma`) | A Kysely plugin (`scopePlugin` in core) that reads each query before it runs and throws `forbidden`; raw SQL is matched word by word against the names in the schema |
| `files` | Write and delete under `<id>/`; read those and keys another extension granted it | A scoped file store over `core_file_grants`; `uow.files.grant(key, toExtension)` is for the owner only and commits with the change |
| `secrets` | Open only what it sealed | A key of its own (`ext:<id>`, derived from `FAMOS_SECRET`); values are `v2.…` |
| `actions` | Run its own actions and those in `calls`; as an AI actor also what the AI is offered (`aiCatalog`, `aiReadTools`, `aiContextActions`, `aiMissingAreas`), which is how the Inbox and the assistant act for the AI | The action runner, on `ctx.actions.invoke` and `uow.run`; anything else is `forbidden` with an error that names `famos.calls` |
| `http` | Reach `network.hosts`; any public address with `userUrls`; the home network (`allowLocal`) only with `local`; the same for a GET and a POST | A wrapper around the guarded HTTP port |

The guarded `http` runs in job handlers, or in a route as a bounded read-through (the weather is one): a short timeout (a few seconds, never more than 15 s), a size cap, the answer cached for a while and a failure shown as `unavailable`. That is safe because the request is bounded in time and size and served from cache, so a slow or hostile server cannot hold a page load up for long or flood it, and nothing is written outside the household. Anything slow, repeated, or that changes data outside goes through a job. `post` (a JSON body of at most 64 KB, the same address checks, size cap and timeout) is for jobs only: it changes something outside, so it runs after the change that asked for it has committed, and it never follows a redirect, because a POST sent again may do it twice.

Better-sqlite3 has no authorizer hook, so the database scope lives in Kysely: the plugin only reads the query tree (it never rebuilds it, which would cost three times as much), a raw template's text is checked once per call site, and it adds about half a microsecond to a query that takes twenty on a laptop. In-process code could still reach around it (import a database driver, `withoutPlugins()`, which a test forbids in extensions), so the scope is a guard against mistakes and a contract the host can check, not a sandbox: extensions are official and signed.

The Inbox stores the papers it files on a record under `inbox/` and grants each one to records before it calls `records.attachDocument`; a core migration granted the papers filed before grants existed. Values sealed with the key all extensions once shared (`v1.…`) no longer open: a calendar subscription that kept one shows that its address cannot be used until it is entered again.

### Manifest

Every extension describes itself in the `famos` field of its package.json (`ExtensionManifestSchema` in the SDK) and passes it to `defineExtension({ manifest: pkg.famos, … })` and to `defineWebExtension({ manifest: pkg.famos, … })`, so both sides have the same id. It is static JSON so that the host can read what an extension is and what it reaches before running any of its code:

| Field | Meaning |
|---|---|
| `id` | Lowercase letters and digits; the namespace of everything it declares and its API path segment |
| `version` | Its own version, the same as the package's |
| `sdk` | The SDK versions it was built for, as a caret range (`^0.5.0`) |
| `dependsOn` | Extensions that must be present; their migrations run first |
| `optional` | Extensions it works with when present and does without otherwise (Quick add files papers on records only when records is there). They do not change the load order |
| `tablePrefix` | The prefix of its tables; `<id>_` when left out |
| `capabilities` | The ids of every capability its code declares |
| `calls` | The exact ids of other extensions' (or core's) actions its code runs with `uow.run` or `ctx.actions.invoke` |
| `provides` | The host contracts it implements: `shareTarget` (receives what members share from outside the app, §10) and `conversation` (answers what they ask from there, §11) |
| `network` | What it may reach outside the household: `hosts` it calls, `userUrls` (addresses a person typed), `local` (the home network, when a person allows it) |

The registry checks the manifest against the code when the host starts and refuses to start otherwise: the capabilities in the code and in the manifest are the same; no two extensions' table prefixes overlap; the host's `SDK_VERSION` satisfies the `sdk` range (an in-house caret check, read as npm reads it); every entry in `calls` belongs to core or to an extension in `dependsOn` or `optional`, and is an action of it when that extension is present; `provides` lists exactly the contracts the code implements, and no contract has two providers. A missing `dependsOn` extension stops the start; a missing optional one does not. The manifest is also what the extension is held to while it runs (see "Isolation"): its `tablePrefix`, `calls` and `network`. The inbox and the assistant run actions of any extension on the AI's behalf; those are not `calls`, they come from the AI catalog and are allowed only for AI actors.

The SDK's error classes (`FamosError`, `LlmError`, `ExternalHttpError`) are checked with `isFamosError`, `isLlmError` and `isExternalHttpError`, which read a `Symbol.for` brand, never with `instanceof`: an extension built on its own can carry a separate copy of the SDK, whose classes are different objects. A test fails on `instanceof` for them.

### Web side

The web app is a shell that knows no extension: an extension can be installed or left out without changing it. Everything it shows of one comes from the extension's `./web` entry (`defineWebExtension`), which registers once with `registerWebExtension` (`apps/web/src/lib/contributions.svelte.ts`), and the app reads the reactive registry (`contributions`), never a list of its own. `scripts/shell-agnostic.test.ts` fails when `apps/web` depends on an extension, or `apps/web/src` names an extension's API (`/api/v1/<id>`), capability (`can('<id>.…')`), events, a page an extension serves, or has a route folder named after one.

**Loading at run time.** The app's build contains no extension. Each one is the `web/` of its package, imported by the browser at start:

- **One instance of what is shared.** The app's own build provides the modules a package leaves out. The `sharedModules()` Vite plugin (`@famos/pack/vite`, client build only) makes each `SHARED_WEB` specifier an entry chunk of the app with its exports kept exactly (`preserveSignature: 'strict'`); the app's code imports the same module from the same chunk, so a package and the app run one Svelte runtime, one `@famos/ui/app` context, one zod and one Temporal. The plugin writes `_app/shared-modules.json` (specifier → chunk). A shared chunk holds the whole module, since a package may use any export; zod is shared without its `locales` (every language zod has, a third of it), which no extension needs. `@famos/ui` compiles with `css: 'injected'` (`dynamicCompileOptions` in `apps/web/vite.config.ts`), so a component a package uses brings its styles even when no page of the app does.
- **The shell.** `mountSpa` (`apps/server/src/http/static.ts`) writes, first in `<head>`, an import map from `shared-modules.json`, the list of packages (`<script type="application/json" id="famos-extensions">`: `fingerprint`, and per package `id`, `version`, `entry`, `css`, `files`), a `modulepreload` of each entry, and last in `<head>` each package's stylesheet. The import map is an inline script, so the policy's script hashes cover it. `/` and `/index.html` are always this shell, never the raw file. Package files are served at `/extensions/<id>/<digest>/<path>` (`mountExtensionAssets`), the digest being of `famos-package.json`, which lists every file's hash: cached for good, `nosniff`, and only the `web/` files the package lists. `GET /api/v1/core/extensions/loaded` (`core.loadedExtensions`, public) says which extensions run and their fingerprint.
- **Importing.** `apps/web/src/lib/extensions.ts` imports every listed entry at once (`Promise.allSettled`, top-level await, so whatever reads `contributions` waits for it); one that fails is logged and left out, and the app opens with the rest. The dev server instead compiles the workspace's extension source with a lazy glob, filtered by `core.loadedExtensions`, which keeps hot reload.
- **Styles.** A package's `web/styles.css` holds the utilities its code uses in the `ext` layer, built against the app's theme, base and type roles by reference, so none of them is repeated. Every stylesheet declares the same order, `@layer properties, theme, base, components, ext, utilities;` (the first sheet to load places a layer). The app writes every theme variable (`theme(static)`), so a utility the app never uses still finds its value. Layers cannot order a variant against a base class held in two sheets (an extension's `hidden md:inline`, where the app's sheet has `hidden` and only the package's has `md:inline`), so the app's Tailwind also scans the bundled extensions' web source: its sheet rules on every class they use, and their own sheets add nothing for them. A package built after the app (a newer version, one installed later) relies on its sheet alone for the classes the app lacks; a variant of such a class over a base class the app has can lose.

An entry contributes:

- **Navigation and pages**: `nav` (tabs, More, the settings list, with `order` placing a settings page among the app's own), `pages` served by the catch-all route (patterns with `:name`), `shortcut` (the key after `g`) and `share`: the one entry where things are shared with the family (Quick add), which Today links to through `app.share()` and which gets the `n` key. Settings pages an extension owns are its pages (Photos and weather is ambient's); memory is core's, so its page lives in the app (`/settings/memory`, `core.memory.use`).
- **Slots**: typed contribution points whose contracts are plain data plus a component loader: the app's own (`dashboard.card`, `today.atmosphere`, `today.capture`, `today.head`, `nav.action`, `display.widget`, `display.status`, `display.ambient`, `setup.step`, `settings.display`) and those an extension owns. An owner declares its slot from its contract by adding to the global `FamosExtensionSlots` interface (`record.section` in records, `inbox.fileTarget` in inbox), so the page that renders it and the extensions that contribute to it share one type. It is a global rather than an augmentation of `@famos/ui/slots`, because a checker that reaches a component of `@famos/ui` through a link can see a copy of that module an augmentation does not reach.
- **Today**: `timeline` (the day's things; a timeline's `page` is where the day links), `today` facets and `blocks` (below), `dashboard.card` cards.
- **Draft presenters** for the extension's own actions. Core's actions are presented by the app (`apps/web/src/lib/app-slots.ts`).
- **Texts**: `messages`, its English catalog, which `registerWebExtension` adds under its id (see "Language packs").

**Today facets** are what Today shows in shapes of its own rather than as a card, so each style can draw them its way: `perMember` (counts per person: chores as rings, bars, "2 left", a display's total), `memberStatus` (a few words beside each person's name, already in the reader's language: who is home; never coloured, the notes of several such facets stand side by side, and none with names off), `photo` (the photo of the day), `weather` (the next hours, for a style that draws them itself) and `setupHint` (a step of a new family's first steps; a `fresh` step also says whether the family is new). A style shows a facet only when an extension that is turned on provides it and the viewer holds its `requires`. **Blocks** are what "What Today shows" lists: the app's own (the clock, the greeting, the weather and the photo when something provides them, the next thing, the day, where everyone is, Needs you, the next days, done today), those extensions add (`blocks`, placed by `order`; the chores and the meals), and every card; a card or a facet names the extension's block it belongs to with `block`. Block ids are what people hide, so they never change.

`requires` is mandatory wherever a family display reads (timeline contributions, facets, `today.atmosphere`, `display.*` and cards with a glance): a display has a day when it holds the `requires` of any timeline contribution, and pairing offers exactly the capabilities these name. App services (translation, members, time zone, realtime events, toasts, `share()`) come from `useApp()` (`@famos/ui/app`), provided through Svelte context under `Symbol.for('famos.app')`; extensions reach Svelte, `@famos/ui` and `@famos/sdk` only as packages, with Svelte a peer (`scripts/extension-externals.test.ts`), so their bundles leave them out and use the app's.

### Packages and installation

Each extension is a built package (`@famos/pack`). The image carries every one in `/app/extensions`; `extensions.json` there says which are `always` installed, which are `offered`, and which a new family gets by `default` (ambient, so Today has its weather and photos from the first day and setup offers the weather place). Its `independent` list names extensions released on their own (a tag `ext-<id>-v<x.y.z>`, published only to the official index), which the image does not carry; the shipped ones are released with the product and carry its version. The family chooses the rest in Settings → Family → Extensions (`apps/web/src/routes/settings/extensions`).

- **The installed set** lives in `core_settings` under `extensions` (`packages/core/src/extension-state.ts`): `installed`, `known` (every extension that ever ran, with its table prefix and last version), `failed`, `restartRequestedAt` and `loaded` (what the last start ran, recorded with `known` at every start). The server reads it through the database handle before it builds the kernel (`apps/server/src/extensions/installed.ts`), since it decides what the kernel is made of. Without a stored state: a database with data (a family from before installing existed) gets every shipped extension that has migrations there, plus the always set, so an upgrade keeps everything with no step of its own; an empty database gets the always set and the defaults; workspace source (`FAMOS_DEV_EXTENSIONS`) gets everything. The first start stores what it chose.
- **One broken package never stops the rest.** An installed package that cannot be read or imported, whose database holds migrations the package does not have (a newer version made it) or whose new migrations sort before applied ones, is left out and said why; so is one the registry refuses (its manifest disagrees with its code, it clashes with another): `createKernel` takes the ids it may leave out (`refusable`, every id not always installed), drops the culprit and whatever `dependsOn` it, and builds again (`kernel.refused`). A failing migration (`MigrationFailedError` names the scope) or `register` of an offered package is recorded in `failed` and the server exits with code 75 to start again without it; the record is per version, so it does not loop, and installing the package again (or a new version) tries once more. An always installed extension that fails stops the server, as before.
- **Installing** is `core.installExtension` (what the extension `dependsOn` comes with it, and must be at hand), **uninstalling** `core.uninstallExtension` (refused for always installed ones and for one another installed extension needs). Both change the installed set, which loads at the next start; the data of an uninstalled extension stays (tables, files, jobs, drafts) and comes back with it. Its drafts wait unseen by approvers (nothing could apply them); its jobs are not claimed; its scope is reported as orphaned by the migrator. Turning an extension off (the switch on its row in Extensions, `core.setFeatureEnabled`) stays the switch for while it runs. `core.listExtensions` lists every extension with its status (`loaded`, `pending_install`, `pending_uninstall`, `refused`, `failed`, `available`) (a refused or failed one with `reason`, English words for the log and the command line, and `reasonCode`/`reasonParams` from `EXTENSION_PROBLEMS`, which the page translates; `ExtensionRefusedError` and the `failed` records carry them), what it reaches by its manifest (hosts, typed addresses, the home network, foreign calls, the capabilities it adds), its labels and `nextVersion` (a newer version installed from a file that loads at the next start); the Extensions page shows that before Install. All three need `core.extensions.manage` (manage, critical) and a person: the action runner never lets the AI run or propose an action that requires a critical capability, so an agent with an API token cannot, even an admin's. The packages come through `ExtensionPackagesPort` (`list`, `place`, and `stage`/`staged` for files): shipped packages are already in place; a signed package from a file is placed in the store.
- **Restarting.** `core.restartServer` records `restartRequestedAt` and emits `core.restart.requested`; the process serving the API shuts down gracefully with exit code 75 on it, and one that serves no API (`FAMOS_ROLES=worker`) looks at the stored time every 30 s. The image's entry point is a supervisor (`apps/server/src/supervisor.ts`, built as `famos.mjs`): `serve` runs `main.mjs serve` as a child, starts it again on 75 (immediately after a run of some length, with a back-off from 1 s to 30 s while starts keep ending quickly), passes any other exit code through, and passes SIGTERM and SIGINT on; every other command runs in its own process, as `main.mjs <command>` does. `/health` carries `boot`, an id of the process's start, so an app waiting for the restart sees it change: the page that asked covers itself and reloads when `boot` changes. Other open apps notice when their live connection comes back: they compare the fingerprint of the extensions they loaded with `core.loadedExtensions`, and a display reloads by itself while a member gets a notice with Reload (nothing they type is lost).
- **Signed packages and the store.** Besides the shipped packages, a family can install a package from a file or from the official index (below). The file is a `.famext`: a gzip tar of a built package folder (`famos-package.json`, every file it lists, nothing else) plus `famos-package.sig`, `{ keyId, sig }`, an ed25519 signature over the exact bytes of `famos-package.json`. The description lists every file's SHA-256, so the one signature covers the whole package. `@famos/pack/famext` makes one (`pack`, `sign`, `generateSigningKey`, `loadSigningKey` from a key file or an environment variable); packing checks the hashes first and writes entries in a fixed order with a fixed time, so the same build packs to the same bytes.
  - **Checks** (`apps/server/src/packages/`, Node's own `node:crypto` and `zlib`, `tar` only as a parser): at most 20 MB compressed, 60 MB unpacked (gunzip stops at the limit, so a small archive cannot expand without bound) and 2000 files; regular files only (a link, a device or any other entry refuses the whole archive) with plain relative paths (no absolute path, `..`, `.`, empty segment, backslash or control character; tar's own extraction would strip these with a warning, a package is refused instead); the signature by a key in `TRUST_ROOTS`; every listed file present with its hash and no file it does not list; then `parseManifest`, `reservedClash`, the manifest's SDK caret, and the platform it was built for (`built.sdk`, the same check as for shipped packages), and its entries among its files.
  - **Trust roots** (`apps/server/src/packages/trust.ts`) are an array of `{ keyId, kind: 'official', publicKey }`; a key's id is the first 16 hex digits of the SHA-256 of its public key (SPKI DER), so a signature can never name a key it was not made with. The list holds the project's release key (`3bab2b9c2b26fecd`), whose private half exists only as the release workflows' secret (docs/releasing.md says how it is made and rotated). Several keys may be listed at once, so a key can be replaced without stranding what it signed. Third-party packages could come later as another `kind` (an author's key, or a family's own), each with its own consent and warning on the install screen; nothing here assumes the official kind beyond the list itself. There is no setting or environment variable that adds a key: tests pass their own roots to the store.
  - **The store** is `<data>/extensions/<id>/<digest>/` (`digest`: the first 32 hex digits of the SHA-256 of `famos-package.json`, the same name its web files are served under), holding the files as signed plus the signature. `core.uploadExtensionPackage` (`POST /api/v1/core/extensions/packages`, multipart, one file, 20 MB, `core.extensions.manage`, a person only) checks a file and keeps it under `<data>/extensions/.staging/<digest>/`, answering what it is (id, version, the version the server has now, labels, what it reaches, dependencies, the signer) and, on a refusal, `details` with a group `reason` (`unsigned`, `too_large`, `incompatible`, `invalid`; `older` as a conflict), a stable `code` and the values its sentence names (`untrusted_key` with `keyId`, `file_mismatch` with `path`, `sdk` with `needs` and `has`, …) for the Extensions page, which shows only its own translated sentences built from them (the English message is for the log), which offers it as **Add from a file** in its head's ⋯ and shows the result in the details panel; nothing is installed until `core.installExtension { staged: digest }`, which checks the staged copy again, moves it into the store and adds the id (with what it `dependsOn`, from what the server has). Folders are written beside their target and renamed into place, so a half-written copy is never found.
  - **At every start** each stored copy is checked again (signature, files, links, platform) before any of its code is imported; one that fails is left out with a warning, and an installed extension with no other copy is refused, never the host. The copy that runs is the highest version among the shipped one and the stored ones; a shipped copy wins a tie (it is trusted by where it is), so a newer image replaces an older stored copy, and of two stored copies of one version the later placed one wins. A stored copy of an always installed extension keeps `always`. Uploading an older version than the server has is refused (`conflict`, reason `older`); the same version as the shipped one installs it without a file step. After a start, the store keeps for each extension the copy it runs and the newest other one (a display still showing the previous version can fetch its files) and removes the rest, and uploads nobody installed for a day.
- **The official index.** Releases publish packages on the project's GitHub Pages: `https://onurceri.github.io/family-os/extensions/index.json`, signed by the release key in `index.json.sig` (`{ keyId, sig }` over its exact bytes), listing `{ format: 1, extensions: [{ id, version, sdk, url, sha256, size, labels, reach? }] }` (`reach`: `{ network: { hosts, userUrls, local }, capabilities: <count>, dependsOn }` from the package's manifest, written by the index builder and covered by the signature; Look for more shows it before Download, and the download is refused with `reach_changed` when the package's own manifest says something else; an entry without it is read as before) with each `url` relative to the index (`<id>/<id>-<version>.famext`, served from Pages too: release asset addresses redirect to another host). The server reads it **only when an admin presses Look for more**, never on a schedule or at start, so a family that never asks makes no call to it. `core.findExtensions` enqueues `core.fetchExtensionIndex`; the job asks `ExtensionPackagesPort.findPackages`, which the composition root implements (`apps/server/src/packages/official.ts`) with plain `fetch` to that fixed address (not `ctx.http`: it is the project's own host, not one a person typed): https only, no redirect followed (one is refused), the index at most 1 MB and its signature 4 KB counted as they arrive, 20 s each. The signature must be by a key in `TRUST_ROOTS`; an entry whose address is not on the index's own host is left out. `FAMOS_EXTENSION_INDEX_URL` (https only) moves the address for tests; the signature is still checked against the same roots, so it adds no source of code. What it lists is kept in `core_settings` (`extension_index`) and `core.getFoundExtensions` answers the newest version of each id whose SDK caret this server satisfies and that is newer than the package it has. `core.downloadExtension` enqueues `core.fetchExtensionPackage` (lane `long`): the port downloads the file (2.5 min), checks its size and SHA-256 against the index (`mismatch` otherwise), then stages it exactly like an upload, so every check of a file runs again; the admin then installs it with `core.installExtension { staged }`. Failures are recorded with `details.reason` (`unreachable`, `unsigned`, `invalid`, `mismatch`, `reach_changed`, `gone`, or a package refusal) for the page to say, and never retried by themselves. All three need `core.extensions.manage` and a person.
- **The command line**: `famos extensions list`, `famos extensions install <id…>`, `<file.famext…>` or `--all-offered`, `famos extensions uninstall <id>`, run as the server (the `cli` system actor) on the same data; a running server loads the change at its next start.
- **Purging** an uninstalled extension's data is `famos extensions purge <id> [--yes]`, on the command line only: it is irreversible, so it is no action and has no route, and nothing in the app or an agent can reach it. It refuses an always installed id, an installed one, one still loaded (in its own process, or by the last start, `state.loaded`: that server runs it until it starts again, whatever its roles or address, so no network call is needed), one with no `known[id].tablePrefix` (it never ran here), and a prefix that overlaps the host's (`RESERVED_TABLE_PREFIXES`, `sqlite_`) or another known or available extension's: the prefix is all that names the tables of an extension whose code may be gone, so it must name nothing else. Then it writes a backup (and stops if that fails) and removes, in one transaction with foreign keys off and checked before the commit: the tables, views, indexes and triggers named with the prefix; the scope's `_migrations` rows, so a later install migrates from nothing; its jobs (`<id>.*`, and `core.notify` of its kinds); its drafts, notifications, idempotency answers and search entries; file grants to it and of its files; its keys in role overrides, notification preferences, display capabilities (devices and pairings), features, AI areas, AI switches, auto-approval, the search index state, Today's hidden blocks, and `known`/`failed` of the extension state. Its files (`files/<id>/`) go after the commit. The audit log and AI usage are history and stay; so do handles of API tokens (ids only) and a stored package of it (code, not data).

### Records and record pages

Vehicles, pets and the home each need the same three things: duties that come back with a reminder before they are due, papers, and a page that shows both. Writing that three times would give three slightly different behaviours; putting all three in one extension would break the extension model and the family could not turn one off on its own. So the `records` extension owns what they have in common: **obligations** (a duty with a due date, an optional repeat of N months or years, a lead time, an assignee) and **documents** (links to files that arrived through the Inbox). It knows a record only by its typed id (`vehicle_…`), the kind (`vehicle`) and a name and page path that the owner keeps current with `records.renameRecord`; it never reads a domain table. Domains call its actions (`records.addObligation`, `completeObligation`, `archiveForRecord`, …) with `uow.run` inside their own actions; a run inside another action is decided like any call (refused as `nested_needs_approval` when it would only be a suggestion), except that records' actions are `nested: { governedBy: 'owner' }`: run by the domain that owns the record (its `recordIds`), they are covered by the domain action's own permission and approval.

- **Domains own their data.** Vehicles, pets and home keep their own tables and fields and declare their presets (a neutral name and a suggested interval) as data in their contract. An archived or removed record archives its obligations through `records.archiveForRecord`; `records` hides ids it no longer knows.
- **Dates.** Obligations are by calendar date only: odometers and other units differ by country and vehicle, and a date is what families act on. A repeat is stored as an RFC 5545 rule (`FREQ=MONTHLY|YEARLY;INTERVAL=n`) but expanded from the first due date with month-end clamping (31 January → 28 February → 31 March; 29 February → 28 February → 29 February), because a duty "on the 31st" must not skip short months. Completing records a history entry and moves the due date to the first occurrence after today (or after the due date when done early); a one-off is archived as done.
- **Reminders.** Notification kind `records.obligationDue`. Jobs `records.remind` are planned in the transaction of every change at `due − lead days` and on the due date, 09:00 family time. A job carries the due date and `updated_at` it was planned for and does nothing when they no longer match. Recipients: the assignee, else everyone holding the obligation's `audience` capability (a domain passes its own, for example `vehicles.view`; default `records.view`).
- **AI.** `records.addObligation` and `records.completeObligation` carry `ai` hints. The model names records and obligations by handle (see "AI record context" below). `completeObligation` also takes `nextDueDate` (a renewed policy runs until…): for a repeating duty it becomes the new anchor of the series, and asking for the date it already has does nothing, so approving twice is harmless. `label` is a reviewer-only copy of the entry's name, never stored.
- **Slots.** `setup.step` is an optional step of first-run setup (`{ done }`): the setup page renders the contributions one at a time after the founder's account exists and they are signed in, without filtering by `requires` (capabilities are not loaded yet; the founder holds all of them); a step must offer Skip and never block. A domain extension owns the record page and renders `<Slot name="record.section" props={{ recordId, recordKind, recordName, recordUrl, audience, presets }} />` (the slot is declared in the records contract); with no `contributions` the slot asks the app (`useApp().slots(name)`) for the enabled ones that the viewer may see. `records` contributes "What needs doing" and "Papers". Domains pass `presets` (`ObligationPreset[]` from their contract: id, title key, `every`, lead days) for the "what usually needs doing" list. `records` also contributes the Today card "Coming up" (30 days, across records, with the record name and page).
- **Filing without the AI.** Filing is the path that keeps a paper away from the model, for areas the AI may not read: the AI is never asked to sort shared items into areas, because sorting would mean reading them. The Inbox lets a person put an item's files on a record themselves: `inbox.createItem` with `fileToRecordId`/`fileToRecordKind` (and optionally a label), or `inbox.fileItem` for an item already there. Both call `records.attachDocument` through `uow.run` in the same transaction, so a refusal (no `records.edit`, a missing file, records off) rolls everything back. A filed item has status `filed`, no `inbox.process` job is enqueued, and a job already queued finds the status and stops. The picker is the `inbox.fileTarget` slot (declared in the inbox contract), which domain extensions contribute their records to; with no contribution "Add to…" is hidden. The file stays where the Inbox stored it (`inbox/<item>/<n>`); `records.getDocumentFile` serves only keys linked to a record, sandboxed like the Inbox file route.

### Calendar feeds

Families live with calendars they do not own (the school year, public holidays, a club's fixtures) and want the family calendar on their phones. Both directions use ICS feeds, which need no account linking or OAuth; two-way CalDAV sync would need a sync engine with conflict handling and is not built.

- **Out: a secret feed** at `/api/v1/calendar/feed/<token>.ics`, of the whole family or one member's events (plus whole-family events). The long random token is the credential (only its hash is stored); the feed is read-only, has no session and carries notes only when its creator chooses so. A feed acts for the member who made it and is judged as they are today: each fetch resolves the owner with `credentialOwner` (active, and holding `calendar.view`, or `calendar.manage` for a whole-family feed) and answers 404 otherwise. Only a password sign-in may create one (`assertFullSignIn`), and the calendar ends its feeds through the `endCredentials` hook (below).
- **In: read-only subscriptions** (`https:`, or `webcal:` meaning `https:`), refreshed by a job with conditional requests through the guarded HTTP port (size cap, timeout, no redirects across hosts, private addresses only when the admin allows them for that subscription, for a NAS). The subscription URL is a credential (Google and iCloud secret addresses), sealed with `FAMOS_SECRET` and never returned in full. Events are parsed with `ical.js` and stored in their own table keyed by subscription, UID and RECURRENCE-ID; a refresh replaces a subscription's events in one transaction, so a broken feed can be removed without side effects. They are expanded with the same recurrence code, cannot be edited, and do not remind unless the subscription says so.

### The family board

Families need a place for short, lasting notes everyone sees (the fridge door, a kitchen whiteboard), and FamilyOS has wall displays where a board works and a chat would not. The `board` extension holds short notes (up to 500 characters, an optional photo, an optional end day after which the note leaves, pinning, and "seen" per person) on its own page, as a Today block and on displays. There are no replies, threads or chat: families already have a chat. Capabilities: `board.view`, `board.post` (write, edit and remove one's own notes), `board.manage` (remove anyone's note, pin). Its look comes from theme tokens; note colours are papers the author picks, never member colours. A read action with `ai` hints lets the assistant read the board, and the AI may propose a note like any other action.

### AI record context

The model can only point at records it was told about, by the names the household uses. So an extension may declare `defineExtension({ ai: { context: 'vehicles.aiContext' } })`: the id of a **read-only** action of its own (the registry checks) returning `{ kind, label, items: [{ id, label, details?, url? }] }` (`AiContextSchema` in the SDK). An area with more than one kind of record lists several actions (`context: ['home.aiContext', 'home.aiContextItems']`), one kind each. Quick add:

1. takes the areas of the mention kinds offered for the reading (§6, already filtered like the AI catalog), so an area that is off for the AI, or local-only with a remote model, contributes nothing;
2. invokes each context action **as the AI actor** (`ctx.actions.invoke(id, {}, aiActor)`, local when the model is; `ctx.actions.aiContextActions()` lists them for extensions that are turned on). Access control refuses a locked area even here, and the AI actor only holds `view` capabilities; at most 50 items per area are used, the ones the message names first;
3. prints the labels and details under a "Known names" section of the system prompt, never an id and never a handle; each kind says which of them it points at (`knownFrom`);
4. keeps the items with their ids in memory for the resolvers (`MentionContext.records`, `ctx.record(words, kinds)`): a resolver only ever emits an id it matched among them or read from its own tables, so a suggestion cannot name a record that was not listed, and the record's kind, name and page come from the item, not from the model.

Extensions with their own context so far: `vehicles` (name, plate, make, model, year, fuel; no VIN or notes), `pets` (name, species, breed; no chip number, vet or notes), `home` (homes by name and tenure; things by name, brand, model, room, home and warranty end; no address, serial numbers, account numbers or notes; services are not shared) and `lists` (open shopping items with the list they are on, and open tasks with their due date, so a message that something is bought or done can tick it off or complete it; at most 60 and 40), `records` (open obligations: "Car insurance (Family car)", due date, repeat). `records.aiContext` lists an obligation to an AI actor only if that actor holds the obligation's `audience` capability (unknown audience counts as `records.view`). A domain passes its own capability (`vehicles.view`), and a locked area's capabilities are removed from AI actors, so its duties, record names and dates never reach a prompt even while `records` is open. People are not filtered. The context is data for the prompt only; changes still become drafts a person approves.

### Mention kinds: what the model may read for an extension

Models read language well and do the system's work (ids, dates from a table, which record is meant, which of 25 action schemas fits) badly, and differently from one model to the next. So the reading is split: the model reads a message into a small flat list of **mentions** that is the same whatever is installed (`UnderstandingSchema` in `@famos/sdk`: a `kind` and shared slots such as `title`, `target`, `about`, `people`, `date` as a day reference, `time`), and code turns each mention into a suggestion or a refusal. An extension declares what may be read for it with `defineExtension({ ai: { kinds: [defineMentionKind({ … })] } })`:

- `id` (`<extension>.<kind>`), an English `describe` for the model, the `slots` it uses with a line each, `variants` when it uses the `variant` slot, and English `examples` (`{ text, mentions, why? }`), region-neutral with days in words;
- `actions`: the AI-proposable actions its resolver may suggest, its own or ones its manifest `calls`;
- `knownFrom`: its own `ai.context` actions whose item labels the model is shown as known names;
- `limit`: at most this many mentions of the kind are resolved from one reading (default and at most `MENTION_LIMIT`, 16);
- `handsOff`: kinds of other extensions (named in `dependsOn` or `optional`) its resolver may hand a mention to, when what the mention states is that kind's thing (a treatment still to come is an appointment, `calendar.event`);
- `resolve(ctx, mentions)`: returns `{ propose: { actionId, input, subject, targetTitle?, uncertain?, decided?, from } }`, `{ refuse: { reason, subject, from } }` or `{ handOff: { kind, mention, from } }` per group of mentions, with `reason` one of `REFUSAL_REASONS` (`already`, `unknown`, `other_day`, `ambiguous`, `incomplete`, `not_allowed`, `instruction`). A hand-off is resolved by that kind when it is offered for the reading, once, and refused `incomplete` otherwise.

Every example mention carries its `quote`, the words of its text it rests on, so the model learns to copy them.

Quick add (§10) is the reader: it never names a kind or an action, and offers a kind only while all its actions are in the AI catalog for the reading (`ctx.actions.aiKinds`). Resolvers run in their extension's read-only view (`ctx.actions.resolveMentions`), and what they return is held to their mentions: every mention backs exactly one resolution, so a reading never yields more suggestions than mentions.

The registry refuses a kind not named for its extension, an id twice, a slot it does not know or describe, variants without the `variant` slot (or the reverse), an action that is neither its own nor in `calls`, one that is read-only or has no `ai` hints, `knownFrom` that is not one of its AI context actions, and an example that does not parse as a mention (strictly: no fields the schema lacks), names a kind the extension lacks, or fills a slot its kind does not use (`mentionKindProblems`).

`ctx.actions.aiKinds({ local, actor })` lists the kinds offered for a reading: those of extensions that are on, whose area is open to the AI (local-only areas only for a local model), and whose actions are all in `aiCatalog` with the same options, so a kind disappears with any action it needs. `ctx.actions.resolveMentions(kind, mentions, env, actor)` runs the resolver for an AI actor only, and only while the kind is offered to it (`forbidden` otherwise). `env` is the reading (`text`, `sharer`, and the household `records` already read as the AI actor). The resolver gets a `MentionContext`: its own tables **read-only** (a plugin refuses anything but a select), the family's region formats, and helpers bound to the reading (`day` through `resolveDay` with the date words of every installed language, `time`, `people` through `resolvePeople`, `target` and `record` through `findTarget`, checked against the shared text).

What a resolver returns is held to its mentions: each mention backs exactly one resolution, so mentions may be merged (shopping items into one list change) but never multiplied. A resolution that names no mention, one it was not given or one already held is dropped and logged, mentions nobody holds and those past the kind's `limit` are refused `incomplete`, a suggestion of an action the kind does not name is refused, and a resolver that throws refuses all its mentions. A reading therefore never yields more suggestions than mentions, however the shared text tries. What is proposed still goes through the action runner as the AI actor and becomes a draft.

Quick add does not read through kinds yet; it still extracts proposals as described in §10.

### Restrictive capability defaults

A `view` capability is held by every built-in role by default, which is right for calendars and lists and wrong for money, health or other private records. An extension may therefore set `defaults` on a capability, but only to **remove** grants its level gives: each role's value must be `false` or the level's own (`assertRestrictiveDefaults`, checked by `defineExtension` and again by the registry). It can never add a grant and never declare a critical capability. `defaultGrant` is the one place that reads the defaults, for the built-in roles and for custom roles, which take their base's default unless overridden: for a `money.view` limited to Admin and Member, a custom role based on Member keeps it, one based on Supervised does not until the family grants it. No bundled extension needs this today.

### Region-neutral by default

FamilyOS is for families anywhere, so nothing in the product is shaped by one country. Presets, defaults, enums, AI guidance, examples (in schema descriptions, prompts, guides and tests) and seed data make sense everywhere: presets have neutral names ("Home insurance", "Vehicle inspection", "Vaccination") and only *suggest* an interval, which the person sets; nothing is described as required by law, because legal rules belong to the family; the container's default time zone is UTC and the family's comes from the browser at setup. A test fails on non-ASCII letters in code strings, which catches most region- and language-specific words.

### Language and format locale

Language is not region: an English-speaking family in Berlin wants English words with 24-hour times and weeks that start on Monday. The family has two separate settings. `locale` (a BCP 47 code with a language pack, `en` always) is the **language**: it picks words (translations, AI answer language, and the day and month names in dates). `formatLocale` (a BCP 47 tag such as `en-GB`) is the **region format**: the order of dates, the marks in numbers and money, together with `weekStart` (ISO 1 to 7), `hourCycle` (`h12`/`h23`) and `temperatureUnit`. A tag carries a language as well as a region, so a date written with `sl-SI` alone would say "čet., 22. okt." to an English reader. Dates and times therefore go through the **date locale**, `dateLocale(language, formatLocale, hourCycle)` in `@famos/time`: the reader's language with the region of the format locale where `Intl` holds data for that pair (English with `sl-SI` is `en-SI`: "Thu, 22 Oct", 22/10/2026), the language alone where it does not (Turkish with `en-US` keeps Turkish phrasing, since words of a language the reader did not choose are worse than another order), plus the hour cycle and the tag's calendar and digits. Numbers and money have no words and use `formatLocale` itself. They live in `FamilySettings` (`ctx.family` / `uow.family` on the server, `useApp()` in UIs: `dateLocale()`, `formatLocale()`, `weekStart()`, `hourCycle()`, `temperatureUnit()`); presenters and Today's format objects carry both `dateLocale` and `formatLocale`. On the server the reader is a person with a language: a notification names a date or time as a `{ date }`, `{ time }` or `{ at }` parameter, and core writes it out for each recipient when it is delivered or listed; Telegram writes dates in the linked member's language. Never pass `app.locale()` or `getLocale()` to `Intl`, `formatDate` or the money helpers, nor the format locale to a date or time formatter; a source scan test (`scripts/region-formats.test.ts`) fails if either comes back. The derivations from a tag (`defaultWeekStart`, `defaultHourCycle`, `numericDateOrder`, ...) live in `@famos/time`, as does `regionFormats()`, the list of regions `Intl` knows that Settings offers. Defaults come from the browser at setup (its own tag, `Intl.Locale` week info, `Intl.DateTimeFormat().resolvedOptions()`) and the family can change them in Settings. Week views, repeat pickers and the date table in prompts use the first day of the week; weather asks for the chosen unit; AI prompts state the date order and hour cycle, so the model knows whether "03/04" is 3 April or 4 March. Changing the language never changes the region formats.

### Language packs

Adding a language must not need a code change, so English is the only language the app's code knows (`apps/web/src/messages/en.json`). Every other language is a **pack**, a folder `languages/<code>/` with `manifest.json` and one catalog per namespace (`app.json`, and `<extension id>.json` for any extension it translates). Turkish is bundled in `languages/`; the Docker image copies the folder to `/app/languages` (`check-dockerfile` enforces it). Installed packs live in `<data>/languages/<code>/`, override a bundled pack of the same code (newer translations without an app release), and are archived in backups (`languages/` in the tar). A pack is text only and rendered as text everywhere, never HTML, which is why it is safe to install at runtime when code is not.

**Catalogs register themselves.** Each extension carries its own texts in `src/messages/<code>.json`: `en.json`, which every key must be in, and the translations it ships (`tr.json`). The server entry passes them as `defineExtension({ messages: { en, tr } })`, the web entry its English as `defineWebExtension({ manifest: pkg.famos, messages: en })`; the namespace is always the manifest's id (`app` is reserved). The host never names an extension's catalog: the server builds its English from the extensions it loads (`catalogsOf` in `apps/server/src/i18n.ts`), and the web app registers each extension's English in `registerWebExtension`. A language shows, key by key, the **pack's string, then the extension's own translation, then English**: so a bundled pack holds only `app.json`, an extension can ship its translations with itself, and a pack can still correct or add any extension's strings. A language is offered only when a pack for it exists; an extension's translation of a language without a pack waits until one is installed.

- **Words code must recognize** (command names, weekdays, units, keywords) are comma-separated catalog strings too, read with `ctx.vocabulary(key)` on the server (all installed languages) or `t(key)` in the UI. The Telegram share command is one: its English name and every pack's own name are accepted.
- **`@famos/i18n`** holds the format and the rules, with no file access: the manifest schema (`PackManifestSchema`; the code is validated with `Intl.getCanonicalLocales`), `validatePack` against the installed English (unknown keys are reported and ignored; a namespace the pack lacks only lowers its coverage, and one of an extension that is not installed is left out without a problem; a string whose `{{placeholders}}` differ from English is dropped; 2 MB per pack, 4 KB per string, plural forms of the language's own CLDR categories), `withOwnTranslations` (lays a pack over the extensions' translations of its language, checking those the same way), `coverage`, `negotiateLocale` among the available codes, `satisfiesRange` for the `famos` range, and `createI18n`/`addCatalogs` with English as `fallbackLng`. `@famos/i18n/node` reads and writes pack folders and is used by the server and the tools.
- **The registry** (`apps/server/src/languages.ts`, the composition root) loads bundled and then installed packs at start and on every install or removal, each laid over the loaded extensions' translations of its language; a broken pack is skipped and logged. Coverage and the served catalogs are those of the combination, which is what the family sees. Core sees it only through `LanguagePort` (`KernelOptions.languages`; without one English is listed and any well-formed code is accepted, as in tests). `createTranslate(registry)` rebuilds its i18next instance when the registry changes and renders notifications, Telegram, email and push texts; `kernel.translate`, `ctx.translate` and `uow.translate` expose it.
- **Codes are validated against the registry, not an enum**: family `locale`, a member's `locale`, `core.setMyLanguage` and setup refuse a code no pack exists for (`languages.assertKnown`). Removing an installed pack moves the family back to English and clears members who used it.
- **Routes and actions** (core): `core.listLanguages` and `core.getLanguageCatalogs` are public (setup and sign-in need them; the catalogs are JSON text with an `ETag` of the pack version, English is not served). Changing state goes through actions: `core.installLanguagePack` (validates, writes the pack folder through the port and records it in `core_settings.languages`, both in the action; the file write is idempotent and the one effect outside the database), `core.removeLanguagePack`, and `core.installLanguagePackFromUrl`, which only enqueues the `core.fetchLanguagePack` job (guarded HTTP is for jobs); its progress is in `core_settings.languages.fetch`. All need `core.settings.manage`. `core.setMyLanguage` lets any member choose their own language.
- **The web app** bundles English only (the app's, and each extension's from its web entry). It reads `core.listLanguages`, loads the chosen pack on demand (cached by version in `localStorage` for offline starts), sets `<html lang dir>` and follows `core.family.changed` and `core.languages.changed` events. Signed out, the language is the device's choice (sign-in switcher) or the browser's best match; signed in, it is the member's `locale`, else the family's. The first screen of setup is the language choice, and setup continues in it; it becomes the family's language. Notifications and the assistant follow the member's language; displays use the family's.
- **Prompts** name the language with `Intl.DisplayNames` (`languageName`), never a map. A test (`scripts/language-branches.test.ts`) fails on `=== 'tr'`-style comparisons and hard-coded locale lists outside tests and `languages/`.
- **Tools**: `pnpm lang:template <code>`, `pnpm lang:check <dir>` for a pack folder or an extension folder (see [the guide](guide/languages.md)). CI requires every bundled pack to hold only `app.json`, valid and complete, every bundled extension to ship each bundled language, valid and complete, and so each bundled language to be 100% complete as the app shows it (`packages/i18n/test`).

### Appearance: styles and palettes

Appearance is two independent choices, and any style works with any palette:

- A **style** is code the app ships: how Today and the family display are composed, the type ramp (clock, countdown, big numbers, hero title, date, sentence, caps labels) and the default font for each slot (`display`, `serif`, `body`). Three are bundled in `@famos/ui` as the `STYLES` registry: `broadsheet` (the default), `lanes` and `wall`. A style is reviewed code added at build time; there is no installable style, because an arrangement needs components and code from outside cannot be trusted.
- A **palette** is a theme pack: data only (below). It colours everything, may fill the font slots, and never arranges anything.

Other pages keep the design system's page templates and take only the style's type ramp, fonts and accent, through the role classes in `packages/ui/src/type.css`. Navigation does not belong to a style. The style in use is set on the document (`data-style`) before first paint, like the palette, so a styled app never flashes the default. It is chosen like the palette: a family default, a per-member choice and a per-display choice (`core.setFamilyStyle`, `core.setMyStyle`, `core.setDisplayStyle`); `GET /core/appearance` returns the resolved style beside the resolved theme. Resolution, first match wins: the display's own style, the member's, the family's, the preferred style named by the resolved pack's manifest, `broadsheet`. The type ramp is deliberately not a token: sizes stay in a style's code, so a pack can never make text unreadable, hide a control or move anything.

**`accent`** is the one saturated surface a page may have: the next thing (the hero on Today, the calendar's next event) and nothing else. `on-accent` on `accent` must reach 4.5:1; `accent` is never used as text and is never the only marker of "next" (the next card also carries its time and label). Member colours mark people only: avatars, rings, rules, bars and a light tint behind `ink` text, never a surface, never text, never the hero; semantic colours are never used for people.

### Theme packs

The look is data, like words. A **theme pack** (a palette) is a folder `themes/<id>/` with `manifest.json`, `tokens.json` (the day and night values of the known tokens, `radius`, `font`) and optional `.woff2` files. `themes/ev-isigi` (the default, the values of `packages/ui/src/theme.css`), `coast`, `forest`, `plum`, `paper` and `high-contrast` are bundled; the Docker image copies the folder to `/app/themes` (`check-dockerfile` enforces it). Installed packs live in `<data>/themes/<id>/`, override a bundled pack of the same id, and are archived in backups (`themes/` in the tar).

A pack may hold no CSS, selectors or scripts, because CSS can load images from outside servers (tracking the family), hide approval warnings or controls, and make text unreadable. Values only, each one parsed and checked, keep installing a theme as safe as installing a language. Besides the colour tokens a pack may set `font-display` and `font-serif` next to `font` (a family the app bundles, or one it ships as `.woff2`; a slot left out takes the style's default) and may name a preferred `style` in its manifest, used only when the family never chose one. The app bundles Figtree, Barlow Condensed, Archivo and Instrument Serif (all SIL Open Font Licence) and serves them from its own origin; nothing loads from the network. Every token is part of the pack contract: a new one needs a default in `themes/ev-isigi/tokens.json`, an entry in the token list and a line in the appearance guide, and removing one is a breaking change for packs.

- **`@famos/themes`** holds the contract and the rules, with no file access in its main entry: the one token list (`MODE_TOKENS`, `SHARED_TOKENS`, `CONTRAST_RULES`; the guide, the stylesheet, the validator and a test that keeps `theme.css` equal to the Ev Işığı pack all derive from it), color parsing (hex, `rgb()`, `oklch()` converted to sRGB) and WCAG contrast, the radius and shadow grammars, `validateThemePack` (all errors listed; unknown tokens ignored and reported; missing tokens taken from the default; fonts only WOFF2 from the pack, 400 KB each; 1.5 MB per pack; contrast on the pairs a pack changed) and `renderStylesheet`. `@famos/themes/node` reads and writes pack folders; `pnpm theme:check <dir>` uses it.
- **The stylesheet is generated, never passed through**: `html:root, html .day { --wall: …; … }` and `html.dark { … }` plus `@font-face` rules are built from the parsed numbers (colors re-serialized as `#rrggbb` or `rgb(r g b / a)`), so a pack's text never reaches a browser. The selectors are one step more specific than `theme.css`'s, so the theme wins wherever its stylesheet sits.
- **The registry** (`apps/server/src/themes.ts`) loads bundled then installed packs at start and on every change, behind `ThemePort` in core (`KernelOptions.themes`; without one only the default is listed). Bundled packs are validated with contrast shortfalls reported as warnings, installed packs strictly (a pack that fails a contrast pair is refused with the failing pairs listed).
- **Core** (`packages/core/src/themes.ts`): public routes `core.listThemes`, `core.getAppearance` (the caller's effective theme and style), `core.getThemeStylesheet` (`text/css`, ETag = pack version + content hash) and `core.getThemeFont` (`font/woff2`, same origin); actions `core.installThemePack`, `core.removeThemePack`, `core.installThemePackFromUrl` (enqueues the `core.fetchThemePack` job; guarded HTTP is for jobs), `core.setFamilyTheme` (all `core.settings.manage`), `core.setDisplayTheme` (`core.devices.manage`) and `core.setMyTheme` (any member). Installed packs and choices (family, per member, per display) are small JSON values in `core_settings`; unknown ids fall back to the family theme and then to Ev Işığı. `core.themes.changed` makes open screens reload.
- **The web app** keeps `theme.css` as the built-in baseline (first paint, offline), applies the generated stylesheet as a `<style id="famos-theme">`, stores the last one in `localStorage` (applied by the inline script in `app.html` before first paint) and refreshes when `core.themes.*` events arrive. Displays get their theme from `core.getThisDisplay`. A test (`scripts/theme-colors.test.ts`) fails on hard-coded colors in the web app, `@famos/ui` and extensions outside the token layer.

### Pages with parameters

A web extension's page `path` may contain `:name` segments (`/vehicles/:id`). The catch-all route matches exact paths first, then patterns, and passes the values to the page component as `params`. A page without parameters takes no props.

### Who may open a page

A page declares the capability needed to open it with `requires`, the same one as its navigation entry (an entry hides the way to a page; `requires` on the page keeps a typed address, a bookmark or a shared link from opening it). The shell checks it once for every page, before the page loads (`apps/web/src/lib/page-access.ts`, asked by the root layout): the app's own settings pages are declared by their settings entry (`APP_SETTINGS`), an extension's by its `PageContribution`. Someone without it gets one shared state, `NoAccess` (design system §3.8), never a redirect. The server still refuses every read and action they may not run; this only spares them a page of refusals. `scripts/page-access.test.ts` fails when an extension's page and its entry (the one on its path, or the one it lies under) ask for different capabilities, and when an app settings page sends people away by hand.

## 7. Actions: one definition, many surfaces

An action is the unit of change in FamilyOS. A single `defineAction` produces:

1. an HTTP endpoint (`POST /api/v1/actions/:id`) used by the UI (unless the action is `expose: 'internal'`, below),
2. a draft-card proposal that the AI pipeline can create and a human can approve,
3. a tool for the built-in assistant and for MCP clients, inside the AI sandbox (§11).

Implementing each surface separately would duplicate validation, permissions and side effects; with one definition, permissions and approval live in one place, route handlers stay thin, and a new action with `ai` hints is available to the AI pipeline, the assistant and MCP without agent code.

The **action runner** applies, in order: input validation → access (`requires`, judged by capabilities) → `prepare` (optional work outside the transaction, §11) → approval policy (execute now, or store a draft) → `run()` inside one SQLite transaction → audit log → events after commit.

**Approval policy.** `approval` is `'never'`, `'always'`, `'ai'` (a draft when the caller is AI, the default for non-read-only actions), `{ unless: capability }` (people with the capability apply directly; others who hold `core.drafts.propose` propose a draft, others are refused) or a function. A non-read-only action must declare `requires`, `approval: { unless }` or both; the registry refuses one that declares neither. So a Supervised member's change to shared data becomes a draft for someone who may approve it, with no role names in the code. `{ unless }` may add `except(actor, input)` (a case that never needs approval) and `owner(ctx, input)` (whose own thing the input changes): that member applies directly when their role may propose the change or holds the action's own `requires` (whoever may add a shopping item may remove the one they added), never the AI.

**The access decision.** Whether a call is applied, becomes a draft or is refused is decided in one pure function, `decide(action, actor, env, facts?)` (`packages/core/src/decide.ts`): the access checks (`requires`, displays, the AI's rules, critical capabilities, areas off for the AI, anonymous callers), an AI proposal that would change nothing (`refuseProposal`), and the approval policy. It answers `{ outcome: 'apply' | 'draft' | 'refuse', reason?, capability?, depends? }`; without the facts of a call (its input, and the owner the policy names) it answers for any input and marks `depends` where an input could change it. The runner acts on that answer and nothing else, and the app asks the same function, so a screen never offers what the runner would refuse: `GET /api/v1/core/access` gives the signed-in person the answer for every data-changing action that is on, and `POST /api/v1/actions/{id}/check` the exact one for an input (resolved like a call, then nothing runs and nothing is recorded; limited per person). A refusal is a `403` whose body carries `reason` (`capability`, `approval`, `display`, `sign_in`, `ai`, `critical`, `area`) and the `capability` that would allow it, so the app says why in the reader's words; its `message` never names an action. The web app reads the answers once with the session and again when a role, a member or an extension changes or a change is refused (`apps/web/src/lib/access-book.ts`), and gives them to pages and extensions as `app.access(actionId)`, `app.accessFor(actionId, input)` and `app.approval(actionId, input?)`; a control the answer refuses is not drawn, a suggestion says so under the form's title, and no page works out what a role may do from a capability name (design-system §4.8).

**Closed by default.** `admission`, `approval` and `access.can` are switches over every actor kind, and a kind none of them knows is refused (`admission` and `can`) or needs approval (`approval`); adding a kind to `Actor` does not compile until each of them names it. Code never reads who is acting by comparing `actor.kind` and picking a field; it asks the SDK's helpers, so a caller without the property is never a free pass: `selfOf(actor)` is the member acting for themselves (null for the AI, a display and the system, so "self is not the assignee" refuses them), `memberBehind(actor)` the member an act is done by or for (a member, or the member the AI works for), `personPresent(actor)` a human acting directly (deciding, editing and withdrawing drafts, credentials, devices, sessions and passwords, auto-approval, roles, members and extensions all require it), and `principalOf(actor)` a stable string for audit and attribution. The web has the same for the untyped `proposedBy` of a draft (`memberBehindDraft` in `@famos/ui/slots`). An action run inside another (`uow.run`) goes through the same decision as a call: one that would need approval for this actor is refused (`forbidden`, `details.reason` `nested_needs_approval`), never applied directly, so an outer action cannot give a person a change they could only suggest; the outer action is the one that carries approval. Two things are not asked again: an act a person already decided (applying an approved suggestion, or taking one back), and a service action marked `nested: { governedBy: 'owner' }` that is run by the extension owning the record it is about. An extension declares the typed-id prefixes of its records in `recordIds` (`vehicle` for `vehicle_<uuid>`); the runner reads the record's prefix from its id, never the caller's word, and the caller is the extension whose action is running. So a role that may manage the garage (`vehicles.edit`) also manages the garage's duties and papers through records, while another extension, or a record of another extension, is held to the strict rule. **Connected apps** add one actor kind and one property (§12, "Connected apps"): `{ kind: 'app', appId, roleId, mode }` is an app acting for itself, and a member with `via: { appId, appRoleId, mode }` is a member an app acts for. `selfOf` and `memberBehind` of the second are the member (their own things stay theirs; the notification `except` and attribution follow), `personPresent` is false for both, and `principalOf` is `app:<id>` and `app:<id>/member:<id>`. `access.can` gives the app kind its role's capabilities and the second the capabilities both the member and the app's role hold, and neither ever holds a critical capability or `core.drafts.approve`, `core.mcp.use` or `core.signIn.pin` (`appMayHold`), whatever role the admin picks. `approval` treats both like a member (the role's `unless`, the policy's `owner` and `except`), except that in `mode: 'suggest'` every change that is not read-only becomes a draft, even for an action that never needs approval.

**Doors and what an action exposes.** Each way into the server reads one kind of credential and admits only the kinds of caller it can stand for (`apps/server/src/http/authenticate.ts`, `authenticate(…, door)`): the app's own API and its socket (`/api/v1/*`) take the session cookie, a member, or else a paired display's device cookie, and refuse any `Authorization` header with `400`, so a bearer can never reach these routes by accident; `/mcp` takes a bearer token only, never a cookie, and its caller is the AI actor of the token; the `api` door (`authenticateApp`, mounted by the public API) takes an app key as a bearer, never a cookie, and admits the app kind or a member with `via`, so a signed-in member is never let in there and a member through an app never at the session door (`admits(door, actor)`). A route that needs only a sign-in (`requireActor('signedIn')`) names the kinds it admits (a member), so a kind added later is refused until decided. An action says where it is reachable with `expose`: `'app'` (the default) is in the app's API and for any caller its rules allow; `'internal'` is plumbing for jobs (a feed's last-read mark). An action (or a GET route) can also carry `defineApi` markers: it is then offered on the public API too (§15) and stays `app` for the web, so marking never changes who may run it. An internal action has no HTTP route and is left out of the OpenAPI document, and `admission` refuses a member (also inside a unit of work) and a display; only the system runs it, and the AI may read it (a read-only one) but never change through it, since a draft of it could not be approved. Actions that other extensions run for a person (a record's rename), the undo steps of drafts, the digests and AI contexts (people read them too) and anything the web app calls stay `app`. A token's limits live on the actor and are enforced by the runner, not only by the tool list of one door: `ai.scope` (`read` | `read_write`, set from an MCP token) makes `admission` refuse every action that is not read-only, and a `conversationOnly` action is refused to an AI that is not in `conversation` mode working for a member. The settings routes that are not actions yet (AI, backups, email, Telegram, the MCP switch, device updates) are reachable only through the session door and check a capability or `personPresent` on the cookie's actor; they become `core.*` actions as they are touched.

AI actors are checked like members: an AI actor may invoke an action directly only if it is `readOnly` and `access.can(aiActor, requires)` holds, so a read of an area that is off for the AI is refused with `forbidden`. Data-changing invocations by the AI keep becoming drafts. An action that sends data outside the household (a share link, a message, an email, a call to a third party) is marked `external: true`; the registry refuses `ai` hints on it at startup, so the AI can never propose it. Server routes that call outside (Telegram sending, push) are not actions and are not reachable by the AI.

## 8. Drafts (human in the loop)

AI must not change family data on its own: it proposes, and a person approves. A draft is a first-class row owned by core, not a suspended workflow, because a suspended workflow snapshot is tied to the code that created it and breaks across upgrades, while a row survives restarts and upgrades and can be queried, edited and audited. Expand-only input schemas keep pending drafts valid after an upgrade.

```
pending ──► approved ──► applied ──► undone
   │            └──────► failed (retryable)
   ├──────► rejected
   └──────► expired (its day has passed; also from failed)
```

A draft stores: source reference (inbox item, agent, member), action id, Zod-validated proposed input, edited input (if the user changed it), model and prompt version, confidence, uncertain fields, a dedupe key (so a job that proposes twice creates one draft), who decided and when, and the action's output. Applying is idempotent on `draft_id`. The UI renders a draft as a form generated from the action's Zod input schema, or with a presenter the extension contributes from its `./web`. Approving needs `core.drafts.approve` and the capability that would have let the change apply directly. The approve, reject and undo routes only need `core.drafts.propose`; the runner (`assertApprover`) then asks for `core.drafts.approve` and the action's own capability, except for the member a draft is addressed to, who decides their own.

**Who decides.** For an AI draft, the person behind it is `onBehalfOf` (assistant, MCP) or `DraftMeta.forMember` (Quick add). After auto-approval has been checked, a draft whose person could decide it themselves is addressed to them (below); otherwise it goes to the approvers, who are told. A draft a member proposed themselves (because the action needs approval for them) goes to the approvers, leaving the proposer out.

**Actions that AI may propose declare `undo`**, so that an approval can be taken back.

**Titles.** Every action that can become a draft (non-read-only, with `approval` other than `never`/`ai`, or with `ai` hints) names what it proposes with `draftTitle`, a key in its extension's catalog. A presenter or the draft's summary title a draft first; `draftTitle` (with the review `label` of the input) is the fallback in every draft card and the body of the "waiting" notification, so no card shows a raw action id. A test over the bundled extensions fails when a proposable action has no key.

**Withdrawing and closing.** The member behind a draft (the proposer, or the person an AI draft was made for) may reject it without `core.drafts.approve`: a withdrawn draft is `rejected` with `decided_by` = that member (the API shows `reason: 'withdrawn'`), audited as `rejected`. A status column is a `CHECK` constraint in a STRICT table, so no new status was added. When approving finds that the draft's subject no longer exists (`not_found` from the action), the runner stores the draft as `rejected` with `error = 'gone'` (`reason: 'gone'`) instead of leaving it pending forever. `core.countWaitingDrafts` counts, for a member, only the waiting drafts (pending or failed) `mayDecide` allows, and each draft the API returns says whether its reader may decide it (`canDecide`). Quick add is the one place where every waiting suggestion is decided: under **Waiting for you** it shows the captures with their suggestions and, beside them, the suggestions from anywhere else (an assistant answer, an MCP app key, a person sent for approval), grouped by where they came from. Its badge, Today's Needs you and the page count the same set (waiting, `canDecide`), and the "waiting" notification links there. The assistant also shows its own suggestions under the answer that made them. `core.listDrafts` likewise shows a member only the drafts they may decide or are the person behind, so no one reads another member's suggestions.

**Undo.** An action can declare `undo(output) → { actionId, input }`, its inverse computed from what it returned (`calendar.createEvent` → `calendar.deleteEvent`; `lists.addShoppingItems` removes only the items it created). `undoDraft` runs the inverse and marks the draft `undone` in one transaction. A stored output that no longer matches the action's output schema is simply not undoable.

**Duplicates.** A pending draft says "this may already be there" when its action's optional `alreadyThere(ctx, input)` finds the same thing (calendar: same title on the same day; tasks: an open task with the same title and due date; shopping: every item already on a list). It is computed when drafts are listed, so it stays current, and it never blocks approval.

**Doing it to what is there instead.** News that something changed often arrives as if it were new: "Regional gala moved to Sat 14 Nov 09:00" is read as a new event while the gala is on the calendar for 7 Nov. An action may declare `instead(ctx, input)`: the action and input that would apply the draft to the thing already on record (`calendar.createEvent` offers `calendar.changeEvent` of that event, and for a repeating event of its date nearest the new day). Teaching the extraction model to propose the change itself was tried and was not reliable (it looped, or proposed the change without the new date, and wording the shared rules for it broke unrelated cases), so the model's output stays as it is and the person chooses. The runner checks an offer the way it checks a proposal: a known, enabled, data-changing action, a valid input with names resolved, a target that exists, a change that changes something, and the draft's own words must name the target (`matchThing`, surely or as a match the person is asked to check, as an AI's `label` must), so a careless `instead` can never offer the closest thing. The calendar matches only events the new title surely names within a month (`matchThing`, `exact` or `strong`), or the one it names by the same code ("U13 fixture" for "U13 Eagles away game"), picks the one it names most, and offers nothing on a tie, a partial match, for a new repeating event, or when the event is already there at that time. A pending draft lists the offer as `instead` (computed when listed, like `mayExist`); `core.replaceDraft` turns the draft into it. Whoever chooses must be able to decide both the draft and the change it becomes; the draft stays `pending` under the same id, keeps who proposed it and whom it is addressed to, stores what it proposed before in `replaced`, and the audit log records `replaced`. It is then approved like any change, with that action's undo, so a supervised member's suggestion still waits for an approver. One mechanism serves Quick add, the assistant and MCP, because it works on drafts, not on where they came from. Telegram shows the same offer: the message says what is there (the alternative's `key`, a catalog line with `{{what}}`) so approving never adds a second one unseen, and a third button runs `replaceDraft` and puts the change's own buttons in place. A drafted `ActionResult` carries `instead` (the real name, `at` and `to`), and the agent's `say` line names it so the assistant and MCP clients tell the person; agents have no tool to choose it.

On a card the offered change is the main, filled button and **Add as new** is a secondary one that takes two taps (`draftButtons` in `@famos/ui`): the news means the move, and the layout must not push people to the duplicate. In a Quick add group, decided together, a suggestion with an offer or with `mayExist` starts unticked (`pickedByDefault`), because the group's one button would otherwise add it unseen; choosing the offer ticks the change. Today's Needs you row has no approve button for a suggestion with an offer; it is decided in Quick add.

**Replacing a whole thing, or changing some of it.** A form saves the whole thing, so its `update…` action replaces it: its input is `wholeRecord(fields)` from `@famos/sdk`, the create action's fields with every one required, null for one left empty and a defaulted one sent with its value. A body that leaves fields out is refused with `bad_request` naming them, because a replace that read a missing field as "empty" or "default" would quietly clear what a script or integration never meant to touch (a task's assignee, and with it who may change the task without approval). Changing some fields and keeping the rest is a separate action whose fields are optional and mean "keep as it is" (`lists.changeTask`, `calendar.changeEvent`, `home.updateItem`); that is the one the AI and agents get. A draft stored before an input became stricter must still approve with the meaning it had: an action declares `storedInput(input)`, which the runner applies to every stored draft input before it reads or validates it (approving, listing, the old → new and every hint), never to a new call; `storedAsWhole(fields, key)` is that upgrade for a whole-record input, filling a left-out field with null, or its default, as the replace read it before.

**What a change changes from.** An action that changes a thing may declare `currentValues(ctx, input)`: what the fields the input touches hold now, keyed like the input (`calendar.changeEvent` adds every field of when the event is as soon as one of them changes, so a new time reads against the old day; `lists.changeTask` does the same for a deadline). A waiting draft lists them as `before` (computed when listed, like `mayExist`, with a saved edit when there is one), and the presenter's `fields(input, context, before)` writes "old → new" (`changedValue` in `@famos/ui/slots`). Because it works on drafts, it is the same for Quick add, the assistant, MCP and a person's own request; a decided draft has no `before`.

**Expiry.** An action can declare `draftDate(input)`, the day (`YYYY-MM-DD`, family time) a draft is about (a planned meal, a one-off event's last day, a board note's last day; tasks and repeating events declare none). A waiting draft whose day is before today is listed as `expired`, is not counted as waiting, has no Telegram buttons and is refused on approval (`ActionRunner.passedCheck`); the daily job `core.expireDrafts`, a few minutes after midnight in the family's time zone, stores the status (`expirePassed`, idempotent). A Quick add item whose drafts all expired settles like one whose drafts were all decided. `saidDate(input)` is the day a suggestion is about for its words only (a task's due date: it never expires); a drafted result carries `date` (`saidDate`, else `draftDate`), and the assistant's fixed line and the tool's `say` keep it ("Add a task: Pack my football kit for Thursday, 22 October").

**Gone targets.** An action that changes or removes one row names it with `target(input)` (its own table, the id, and the column that is set once the row is archived or deleted). `ActionRunner.goneAmong` reads the targets of all waiting drafts in one query per table; a draft whose row is gone can never be applied, so `core.listDrafts` returns it as `expired` with `reason: 'gone'` (Quick add says **Can no longer be done**), and `core.countWaitingDrafts`, Today's Needs you, the digest and Telegram leave it out. Nothing is written: approving it still closes it as `gone`.

## 9. Jobs and events

Ingestion, AI calls, reminders and deliveries run in the background and must survive crashes and restarts, without Redis or a workflow engine on a Raspberry Pi. The queue is therefore a table in the same SQLite database. There is no exactly-once guarantee, so **job handlers and action `run` functions are idempotent**.

- **JobQueue port** with a SQLite table implementation in the same database: leases, retries with backoff, timeouts, dead-letter state visible in the UI.
- **Lanes.** The worker runs one loop per lane, one job at a time in each: `default` (the lane of every job unless it says otherwise) and `long` (`defineJob({ lane: 'long' })`, for jobs that can take minutes, such as backups and their uploads). Each loop claims only the job names of its lane; lease recovery is shared; `drain()` (tests, CLI) runs both lanes until both are empty. Both loops use the one SQLite connection: Kysely's SQLite driver hands it to one holder at a time (a mutex taken per query and held for a whole transaction), so queries of the two lanes interleave but their transactions never do. A long job that sits in a transaction makes the other lane wait for it, so long jobs keep transactions short.
- **Queue = outbox.** Any side effect that must survive a crash is written as a job in the same transaction as the data change. There is no separate outbox table.
- **Event bus** is in-process and emits only after commit. Payloads carry IDs only. It is used for UI invalidation and lightweight reactions, never for anything that must be durable.
- **Events have an audience, and the hub filters per socket.** The WebSocket (`/api/v1/ws`) is a feed of events, so it is held to the same access rules as the API. `defineEvent(name, payload, { audience })` names who may hear of it: a capability id, a member (`{ member }`, for what is one person's), everyone (`EVERYONE`, for what every screen shows: theme, language, family settings), any signed-in member (`ANY_MEMBER`), a list of these, or a function of the payload for row-level cases (a duty belongs to the area of its `audience` capability; an Inbox item is its sender's own; a draft addressed to one member is theirs). The hub sends an event to a socket only when the socket's actor passes `access.can` for the audience, so a member without `calendar.view` and a display that was not granted it hear nothing of the calendar, not even that something changed. The default is closed: an event with no audience goes only to those who hold its owner's view capability (`<owner>.view`, the owner being the part of the name before the first dot), a display only if that was granted to it, and nobody when the owner has no such capability. Payloads carry no text that the audience may not see (the calendar's tag event carries no tag name). Sockets are checked when they open, so the hub closes them whenever the actor behind one may have changed: a member's sockets on `core.member.changed` (archived, role or details changed) and `core.session.ended` (sign-out, sign out everywhere, a new password or PIN); a display's on `core.device.changed`, together with the PIN sessions of family devices. The client reconnects and is checked again. The upgrade also needs an `Origin` that is the base URL or one of `trustedOrigins` (the cookie is `SameSite=Lax`, so a page of another port on the same host would otherwise be sent it); a client that sends no `Origin` is no browser. Events of the host's own channels (`telegram.*`, `email.*`) are defined in `apps/server/src/http/host-events.ts`. A test fails for any registered event that declares no audience.
- Long processes are **chains of small idempotent jobs**, each keyed by its subject ID and persisting its result before enqueuing the next.

### The change log, versions and conditional writes

An app that was away needs to know what changed, what was removed, and whether the thing it is about to overwrite is still the one it read. Three pieces answer that, all written by the action runner so no extension can forget them.

- **The change log** (`core_changes`: `seq` autoincrement, `at`, `extension`, `entity`, `entity_id`, `op` `upsert|delete`, `audience`). An event that says what changed declares `changes` in `defineEvent` (a function of the payload that returns `{ entity, id, op }` for each thing). The runner writes those rows **in the transaction that emitted the event**, so a rollback leaves none and a commit leaves all of them; two events about the same thing in one transaction are one row. Events of things apps may read (events, tasks, shopping items and lists, chores, board notes, recipes and meals, homes, calendar subscriptions) carry precise ids and an `op`; `delete` means "gone for readers", so a soft delete or an archive is a `delete` too. The event's audience is stored with the row, so the log answers each actor only with what they may hear (`changesSince(seq, actor)`: a member or display by `access.can`, an app or agent as the member it works for; the cursor still moves past rows the actor may not hear). A read returns each thing once, in its latest state, with a cursor and `more`. **Retention is 30 days** (the daily job `core.pruneChanges`); a cursor older than the oldest kept row, or ahead of the log (a restored backup), is `gone` (HTTP 410) and the client reads everything again. A page's validator (`collectionTag(extension, actor, window)`) is a hash of the extension's newest seq, the actor's capabilities in it and the window the list is cut by (a range, "today"): a view that changes without a write, as a day passes or a role changes, changes the tag too.
- **Jobs that write their own tables** do it with `ctx.unit(async (uow) => …)` (`JobContext`): the same unit of work an action gets, run as the system, so the write and its change-log row share one transaction and events fire after the commit. The board's cleanup and the calendar's subscription refresh use it. A job that changes what apps may read never writes through `ctx.db` alone.
- **Versions.** Each table the public API exposes (calendar events, tasks, shopping items, shopping lists, chores, board notes) has an integer `version`, starting at 0, that goes up by one on **every** write of the row. A trigger does it (`addVersion` in a migration), so no code path can forget, and writes that leave `updated_at` alone (a board pin or reorder, a tag rename on events) still count: `updated_at` keeps guarding planned reminders and nothing else. A parent's version also goes up when a child its shape shows changes (`bumpParentVersion`): a shopping list when one of its items changes (it shows how many are open), a chore when its people or completions change, a board note when someone sees it. A task's completions, an event's tags and the like are columns or are not shown, so they bump nothing extra.
- **Conditional writes.** `ActionTarget.versionColumn` names the column. `invoke(…, { ifMatch })` makes the runner compare the row's version with the one the caller read, **inside the transaction of the write**, and refuse with `precondition_failed` (HTTP 412, `details.version` holds the current one) when it differs, `not_found` when the row is gone, `bad_request` when the action names no versioned row. The check applies to a direct run and to the proposal of a draft alike. Nothing on `/api/v1` sends it yet.
- **Hard deletes** of the exposed tables leave a tombstone through `op: 'delete'` (board notes are the only hard delete among them). Other hard deletes leave no trace and are not in the log: calendar tags, calendar subscriptions' external events, record documents, obligations and their history, pet treatments, vehicle logs, meal plan rows (their event says so, they are not versioned), ambient photos, assistant threads and Home Assistant items, people and switches, the chore assignee rewrite and a task completion taken back.

### Notifications

Every feature needs one way to tell a person something, and "tell whoever may approve" must be expressible without knowing devices or channels. So a notification is data: the in-app list is the record, and pushes and messages are copies of it, so the app can always show what was sent and a lost push loses nothing.


- **Telling people.** Actions call `uow.notify(request)`, jobs and routes call `ctx.notify(request)`. Either enqueues a `core.notify` job (in the action's transaction, so a rollback tells nobody). A request names a **kind** the extension declared with `defineNotificationKind` (undeclared kinds and unknown capabilities throw), recipients (member ids and/or a capability such as `core.drafts.approve`, optionally minus `except`), a title and body as translation keys with parameters, an in-app `url`, a `source`, a `dedupeKey` and an optional `delayMs`.
- **Audience.** A kind may name an `audience` capability (checked against the registry). Members without it do not see the kind in their preferences and cannot set it; delivery is unchanged, since recipients come from the notify call.
- **`core.notify`** resolves recipients when it runs (active members only, so changing a role changes who is told), writes one `core_notifications` row per recipient (`insert … on conflict do nothing` on member + dedupe key: a retried job or a repeated request never duplicates), emits `core.notification.created`, and enqueues one `core.deliver` job per recipient and channel the member has enabled and that is available for them. Kinds of a turned-off extension create nothing.
- **`core.deliver`** renders the text with `translate(locale, key, params)` (member locale, else family locale; the server builds it from English plus the language registry, English where a pack lacks the string), waits out the member's quiet hours (family time zone, may cross midnight) by re-enqueueing itself, skips rows already read, and calls `NotificationChannel.send`. `gone` ends it; a thrown error is retried by the queue. Titles and bodies are never logged.
- **Preferences** live in `core_notification_prefs` (per kind and channel, plus quiet hours); a kind's `defaultChannels` apply until the member chooses, and for a kind that names none, a channel is on unless it says `byDefault: 'off'`. The in-app list is always written; channels are copies of it.
- Channels are adapters wired in `apps/server` (`KernelOptions.channels`). The in-app list (Notifications page, unread badge on More) always works; Web Push is the first channel.
- **Extensions can add a channel** (`defineNotificationChannel`, `defineExtension({ channels })`), for a service the host should not know, such as a home automation hub. Its id is the extension's id or `<id>.<name>`, and the registry refuses a foreign prefix and any id a host channel or another extension already holds. The kernel binds it to its extension: `isAvailableFor` runs with the extension's own context, and `send` with the job context its jobs get (its tables, secrets, `http.post`, network and logger, held to the manifest), so a channel can do no more than the extension. The list is the host's channels followed by those of the installed, switched-on extensions; a delivery queued for a channel that is gone ends quietly. A check that throws means "not available" for that member and never stops the notification or the other channels, and a throwing `send` is retried like any. A channel may say `byDefault: 'off'` (a member opts in) and give a `hint` that the preferences page shows to members who cannot be reached through it yet. `NotificationMessage.link` is `url` made absolute with the family's public address (`FAMOS_BASE_URL`), or null without one.
- **Reminders** (`calendar.remind`, `lists.remind`). Only the **next** reminder of an item is scheduled, as a job with `runAt` = the reminder instant, enqueued in the transaction of every create, update, delete or completion (`uow.enqueue`; a job enqueues its follow-up with `ctx.enqueue`). The payload names the item, the occurrence and the item's `updated_at` (events also the planned instant); when it runs it reloads the item and does nothing if it is gone, done, changed or the occurrence was skipped, because the change planned its own reminder. A recurring event's job notifies and then schedules the following occurrence (an exdate is simply never produced by the expansion), a repeating task is planned again when its completion moves the due date. Instants are computed in TypeScript in the event's time zone (all-day: 09:00 local minus the lead, DST-safe); a reminder already more than 5 minutes past when planned is dropped, and one that waited past its event is not sent. The notification `dedupeKey` is `reminder:<id>:<occurrence>`, so a retried or duplicated job never notifies twice. Events store `reminder_minutes` plus `reminder_set` (0 = never chosen, the default applies; 1 = chosen, null minutes = none).
- **Web Push** (`@famos/adapters/webpush`, migration scope `webpush`). Our own VAPID (RFC 8292) and `aes128gcm` payload encryption (RFC 8291) on `node:crypto`, tested against the RFC 8291 Appendix A vector; no `web-push` dependency. The VAPID key pair is created on first use and **never rotated** (a new key would invalidate every subscription); the private key is sealed with `FAMOS_SECRET`, so backups carry it. The endpoint comes from the browser, so only `https:` endpoints on known push services are accepted (FCM, Apple, Mozilla, Windows) and the check is injectable for tests. 404/410 delete the subscription, 413 is skipped, 429/5xx/network errors throw so the queue retries. Subscription routes (`/api/v1/push/*`) are credential management and live outside actions. Browsers only allow push on **HTTPS** (or localhost), and iOS only in the Home Screen app, so a plain `http://` LAN address cannot receive phone notifications; the VAPID contact (`sub`) is the instance's base URL.
- **Telegram** (`@famos/adapters/telegram`, migration scope `telegram`). Families already chat in a messenger; long polling means no public URL or webhook is needed, so the bot works behind NAT and Tailscale. A bot is publicly discoverable, so strangers are ignored, and messages pass through Telegram's servers, which the settings page and the guide say. grammY core for the typed Bot API, but `getUpdates` is driven by our own small loop instead of `bot.start()`: it re-reads the settings every round (a token saved by the API process is picked up), persists the offset after each processed update, aborts the in-flight request on `stop()`, and backs off on HTTP 409 (another poller; shown in Settings → System → Telegram) and on network errors. It runs only in the worker role (`FAMOS_ROLES`) and idles while no token is saved. The bot token is sealed with `FAMOS_SECRET`; tokens, message text and file names are never logged. A member links their account with a one-time 8-character code (10 minutes) via `/start <code>`; unlinked senders are ignored, and archiving a member removes the link. The adapter imports neither core nor extensions: `apps/server/src/telegram.ts` supplies the callbacks. Shares go to the kernel's share target as the linked member (`kernel.share`, §10), approve/reject buttons call `approveDraft`/`rejectDraft` as that member, and notifications carry their `source` so the channel can add buttons for the pending drafts behind it (`a:<draftId>` / `r:<draftId>`, within Telegram's 64 bytes). Messages are HTML with escaped text; the "Open" button is a URL button only when the base URL is https, otherwise the link is appended as text. Routes (`/api/v1/telegram/*`) are credential management and live outside actions. **Typed text goes to the conversation; forwarded things are shared.** A plain text message from a linked member (not a command, not forwarded, no attachment) is a question to the kernel's conversation (`kernel.conversation`, §11), in one thread per member that the bot keeps; the answer is sent back when it is written, with approve and reject buttons for the drafts it made. Forwarded messages, photos, documents, voice notes and links are shared, and the share command (its name comes from the language packs) shares typed text. When there is no conversation, it is switched off or the member may not ask, typed text is shared too. The answer is transport, not a notification: the server listens to the member-addressed `core.conversation.answered` event and sends only answers to questions asked from Telegram, remembering the reply it waits for with the link so a restart still delivers it. One question at a time per member. The fake Bot API for tests is `@famos/adapters/telegram/fake-bot-api`.
- **Email** (`@famos/adapters/email`, migration scope `email`). Email is attacker-controlled (tracking pixels, HTML tricks, prompt injection), so FamilyOS reads only plain text from a dedicated mailbox the family forwards to, with an IMAP app password; accounts that require OAuth for IMAP are not supported, and the guide shows forwarding instead. Remote content is never loaded and HTML mail is never rendered. A dedicated mailbox read over IMAP with `imapflow` (TLS or STARTTLS only, certificates always verified, logging off) behind a four-call port (`MailboxSession`: select, list unread UIDs, fetch source, move), so the poller is tested with a directory of `.eml` files (`createDirMailbox`; the server uses it when `FAMOS_EMAIL_FAKE_DIR` is set, for tests only). The poll is the job `email.poll` (long lane, one attempt; failures are recorded in `email_settings`, not retried): a small scheduler in the worker enqueues it, deduplicated, whenever `poll_minutes` have passed since the last check, and "Check now" enqueues the same job. Each unread message is fetched without marking it read and parsed with `postal-mime`; the sender must be in `email_senders` (address, member), the topmost `Authentication-Results` header must not report SPF or DKIM `fail`, and a Message-ID already processed is not added again. Text comes from the plain part, else from HTML converted on the server by our own tag walker (no rendering, no fetching, hidden elements and invisible characters removed). Attachments are accepted by sniffed type (PDF, images, audio, plain text), then the message goes to the kernel's share target as the sender's member (`kernel.share`, §10, as from Telegram), so capabilities, quotas, feature switches and metadata stripping apply. Attachments are cut to the target's limits (`kernel.shareLimits()`) before they are handed over. Order per message: add to the Inbox, record in `email_seen` (UIDVALIDITY + UID, Message-ID, outcome), move to the processed folder; a failed move never adds the mail twice, a failed add is retried at the next check. Unknown senders are recorded as `unknown_sender` (left in place, counted) and reconsidered when a sender is added. Credentials are managed by routes outside actions (`/api/v1/email/*`, `core.settings.manage`); the password is sealed (`FAMOS_SECRET`, purpose `email`) and never returned or logged, and logs carry counts and codes only.

## 10. Quick add: the ingestion pipeline

Nobody should have to fill in forms: sharing a message, a photo of a school flyer, a voice note or a document is enough, the AI turns it into suggestions, and a person approves them. The extension's id is `inbox` (routes, tables, `sourceKind`); the product calls it **Quick add**.

**Quick add is personal.** What someone shares belongs to them: they see their own captures and nobody else does, except an approver who must decide a suggestion from it (a supervised member's). A shared list of everything that came in read like a shared mailbox and told the whole family about one person's note; things the family should know go on the family board instead. A capture leaves the waiting list on its own when its suggestions are all decided or expired, when it had nothing to add, or when it was filed into a record. In the app a capture shows its progress and then its suggestions, with no notification; from outside the app (Telegram, email, the phone's share sheet) the person gets one "ready" notification.


```
Share / upload ─► POST /api/v1/inbox/items ─► files stored ─► inbox.addItem [tx: inbox_item + job]
  worker: inbox.process ─► normalize (saved) ─► understand (LLM: mentions) ─► resolve (kinds' code)
          ─► actions.invoke(…, ai) per suggestion
          └► drafts (pending, sourceKind 'inbox') ─► WebSocket ─► Quick add UI
Person edits ─► core.editDraft ─► edited_input stored on the pending draft (any device, any approver)
Person approves ─► approveDraft (applies edited_input when there is one) ─► [tx: calendar | lists + draft=applied]
          └► event (after commit) ─► WebSocket invalidation ─► all devices
```

| Step | Input | Output (persisted on `inbox_items`) |
|---|---|---|
| `received` | shared title / text / URL / files | item row; files under `inbox/<item id>/` |
| normalize | item | `normalized_text`: shared text, text files and voice notes as text (`--- Voice note ---`; speech to text via `inbox.transcribe` when enabled), plus `transcript` → `normalized`. Nothing is saved until all transcriptions finish, so a retry never duplicates; an unreadable voice note (no model, voice off) is skipped when other text exists, else the item fails with `voice_not_read` |
| understand | normalized text, images/PDFs, today and the time zone, the family's names and descriptions (when names may be sent), the offered mention kinds with their examples, known names | the model's answer: a label, an intent (`actionable`, `question`, `nothing`) and mentions, read by `parseUnderstanding` |
| resolve and draft | the mentions, grouped by kind | one draft per suggestion (dedupe key `inbox:<item>:<extraction>:<n>`), skips with their reason and subject, `summary`, counts → `extracted` |
| failure | an `LlmError` a person must fix, or attempts used up | `failed` + error code; "Try again" bumps `extraction` and re-queues |

One job with saved steps replaces separate normalize/extract jobs: a model retry never repeats normalization, and future steps (OCR, link fetching, transcription) slot in before reading.

**The model reads, code works out the rest.** One model call reads the message into mentions (§6): names stay names, days stay day references (`DayRef`: the quoted words and the parts they give), existing things stay words. The prompt is built from parts (`extensions/inbox/src/server/understand/prompt.ts`): twelve short fixed rules, today, the family's names and descriptions, each offered kind with its slots and examples, and the household's known names. Its answer shape is small, flat and the same whatever is installed (the kind is an enum of the offered ids; no action schemas), in the output mode the adapter picks per model (`schema`, `json`, `text`). A misread is fixed in a resolver, an example or the parser, never by another rule in the prompt; drafts store `inbox.understand/<n>+<hash>`, the hash covering the fixed rules, the schema and every offered kind's text. Then, in code (`understand/pipeline.ts`):

1. `parseUnderstanding` reads the answer tolerantly: a bad field is dropped (and marked "check this" where it would have gone), a mention of a kind that was not offered is skipped as incomplete, and an answer cut off at the output cap keeps its complete mentions;
2. a mention the shared message does not hold is left out. Each mention carries a `quote`, the words it rests on; code finds them in the message (`understand/evidence.ts`: in order, loosely, so a mended typo still counts), and a quote found is the mention's evidence. Without one found, some telling word of what it names, or of its day, time or place, must be in the message's own text (forms that start the same count: "gezi", "gezisi"); titles are written in the family language, so when no mention is quoted or has its title in the message the reading was translated and cannot be checked this way. An exact repeat of a mention is one mention. With each kind's `limit`, text that tells the model to add things cannot pile suggestions up;
3. the answer also lists the sentences that speak to FamilyOS or an AI rather than to people (`addressed`: labelling them is reading, which models do reliably; obeying "ignore this" is not). A mention whose evidence begins in one is left out as an `instruction` (a quote that only runs on into one still rests on what the message states), so a note to the assistant inside a forwarded letter suggests nothing. When such sentences are nearly all of the message, it is the sharer's own request ("FamilyOS, add milk") and is read as usual. Notes that repeat what another mention of the reading is about, outside the mention's own quote, are that other mention's and are left out of it;
3a. a mention may say it is a detail of another mention of the same answer (`detailOf`, its place: something to bring to it, a rule for it, a fee for it). The model only says whose detail it is; code decides where it goes (`understand/fold.ts`): a detail with no day, repeat or person of its own goes into the notes of that mention when its kind takes notes, and is resolved on its own otherwise (a fee due Friday is a task). When the mention is refused, or its suggestion keeps no notes (a new event that turns out to move one already there), its details are resolved on their own after all. Without that link, the only lever was an example, and each example swung the model from one wrong place to another (the event's notes, shopping, a task, the board);
4. each kind's resolver turns its mentions into suggestions or refusals (`resolveMentions`), with the host's helpers for days (`resolveDay` in `@famos/time`), people (`resolvePeople`: names written in the message are matched to members at home, also when names are not sent), and which existing thing or record the words name (`findTarget`). Every "is this the same thing?" decision (the target of a change, a tick or a cancellation, a duplicate warning, an `instead` offer, the check of an AI's `label`) goes through one scorer, `matchThing` in the SDK: `exact` (the same words and codes), `strong` (one side's words all whole words of the other), `weak` (most of the words, the words in other forms, the same code of letters and digits with other words, or several equally good) or `none`, in the family language (case and accents by `Intl.Collator`, no plural rule of any language), and a code or number that differs ("1B" and "3B", two plates) is always `none`. `exact` and `strong` are acted on. The one thing named by other forms of the same words ("swim lessons" for "Swim lesson") or by the same code ("the U13 fixture" for "U13 Eagles away game") is acted on too, with its target marked uncertain (`id`, shown as "check this" on the card); every other `weak` match becomes an `ambiguous` refusal that names what the words may mean ("which one?");
4a. a guess is never silent: a kind declares in `decides` which input fields its resolver may settle without the message writing them (`defaulted`: the whole family when nobody is named, a default list, today, dinner; `inferred`: an occurrence of a series, a date from a weekday), and a proposal reports in `decided` how it settled each (`written`, `matched`, `defaulted`, `inferred`). The host adds every `defaulted` and `inferred` field to the proposal's `uncertain`, so the card shows "check this" there, even for a kind that forgot to list it (it is logged). A test fails for a bundled kind that does not declare `decides` (`{}` for a kind that never guesses);
5. the host checks what no resolver can: notes or tags that name a member the message never names are marked "check this";
6. each suggestion is invoked as the AI actor into a draft that keeps the message's own words its mentions were found at (`DraftMeta.quote`, shown on the card as "From the message"); what the runner refuses (invalid, already so, not allowed) becomes a skip, as does every refusal (`already`, `unknown`, `ambiguous`, `incomplete`, `not_allowed`, `instruction`), each with the words it was about.

Shared content is wrapped as data in the prompt, and AI can only ever create drafts.

Dates are read in code, not by the model: `resolveDay` turns the parts into a date in the direction the kind asks (future for plans, past for things done) with the family's region formats (numeric date order, week start), and checks them against the quoted words with the date words of every installed language (`dateWords`, `writtenDates`, `namedWeekdays` in `@famos/time`, from the shared `app:words_*` catalog keys). A weekday that names no week, a day whose parts disagree with its words, a span, a guessed year or words without parts are marked "check this". A day the words name by its distance ("tomorrow", "yarın") wins over a day number or weekday the model worked out, and a week or a month without a day is a span (`DayResult.to`), so a cancellation "this week" looks only at that week. The assistant uses the same words to find a weekday that does not fit its date in the person's message and puts that fact into the turn's prompt. An evaluation set of real-world shares (`extensions/inbox/eval`) is run for every change to the prompt, a kind's text or examples, or the parser, on a matrix of at least two models (`FAMOS_EVAL_MODELS`): the two free ones the baselines hold (`nvidia/nemotron-3-ultra-550b-a55b:free` and `nvidia/nemotron-3.5-super-vl:free` on OpenRouter), because a sound pipeline must work on free models; paid models may be added but are not required; `baseline.json` keeps what passed per model, and a change must not make a case fail that passed there unless the case is genuinely ambiguous. A case the provider itself broke off (an empty answer, a dropped connection, after the adapter asked once more) is an outage: it counts neither way, and the baseline keeps what it knew of that case. Each case runs on a household with every shipped extension installed, so the model is asked with every kind and example a family can be shown. The baseline also keeps a fingerprint of everything the model is asked (`promptHash` over the cases' prompts, rendered with placeholders for the family's data), and the answers of that run are kept in `eval/recorded/`: CI replays them through the real pipeline with the fake model and fails when a replay no longer passes, or when the fingerprint differs from the baseline's, so a prompt, kind or schema change cannot merge without a new run. The assistant has its own set (`extensions/assistant/eval`), on the same matrix and the same kind of household (every shipped extension installed): each case seeds a household, sends one message or a short conversation through the real turn job, and checks the tool calls, the drafts, the answer card and, loosely, the words of the answer. A question case says how it should be read (its days, topics and people) and is held to the card's gate: every fact the digests hold for those days is shown, nothing outside them is shown as in them, no ISO date, no wrong weekday, no "nothing" over a topic with things. Its baseline keeps a fingerprint of the reading's and the wording's prompts, the tool loop's prompt and every tool, and its recordings (readings, openings and tool loops) are replayed in CI through today's code (`extensions/assistant/test/golden.test.ts`), the gate never excused. Assistant prompt or tool changes run it (`pnpm --filter @famos/ext-assistant eval`), and every assistant mistake found in use becomes a case.

### Share targets

Channels outside the app (Telegram, email) receive things a member sends and must put them somewhere, but the host should not know which extension that is: an installation without Quick add, or with another extension in its place, must still start, and the channels must keep working the same way. So the place shared things go is a contract, `ShareTarget` (SDK), which one extension provides (`shareTarget` in its definition, `shareTarget` in its manifest's `provides`; the registry refuses two):

- `requires`: the capability a member needs to share (`inbox.share`); it must be the provider's own.
- `limits`: `{ maxFiles, maxBytes, accept }`, what one share may carry.
- `receive(ctx, actor, share)`: stores `{ channel, title?, text?, url?, files }` as the member; throws a `FamosError` to refuse.

Channels reach it only through the kernel: `kernel.share(memberId, share)` does what the HTTP layer does for an upload (the member is active, holds `requires`, the provider is switched on, the files are within the limits and of an accepted type) and then calls `receive`; it throws `feature_off` when no extension receives shares or it is off, `forbidden` for a member who may not share, `bad_request` beyond the limits. `kernel.shareLimits()` lets a channel trim before it sends (email drops attachments past them). Quick add implements `receive` with the same code as its upload route, so a share from Telegram gets the quota, metadata stripping and AI reading of an upload in the app.

## 11. AI layer

Families choose their own provider: a cloud one through OpenRouter or any OpenAI-compatible API, or a local one (Ollama and similar). Different tasks need different models, so calls name a **role**, and changing a model is a setting, not a deploy.

**The AI sandbox.** People who know the system uses AI will ask whether it could reach private records by accident and leak them. The question is fair: models are good at finding their way around systems, and shared content can carry instructions (prompt injection). There are three exposures: whatever goes into a prompt is seen by the provider; a shared document can tell a model to send records somewhere; and a tool-using assistant reads whatever its tools allow. A promise that "the AI will not look" is not enough, so the boundary is enforced where data and actions are reached, in several independent places, so that one mistake cannot open it:

1. **The AI never reads the database.** What it sees is gathered for it by code through the AI actor's access (below, "Prompt data"); what the AI actor may not read cannot end up in a prompt.
2. **AI access is a setting per area** (Off, Local only, Any provider), enforced by three checks that read the same setting (below, "AI areas").
3. **The AI has no way out.** Its output can only become drafts, and nothing it proposes can send data outside the household. A successful prompt injection can at worst produce a wrong draft, which a person sees before anything happens.
4. **Local only means local.** "Local" is decided by where the provider's address resolves, not by its kind, and there is no silent fallback: when no local model is available the area's AI work stops with a clear message instead of switching to a cloud provider.
5. **Transparency.** Every model call is listed for admins, without content.

The details:

- `LlmPort` (SDK) implemented with the AI SDK and one OpenAI-compatible client for OpenRouter, Ollama and compatible servers (`@famos/adapters/llm-aisdk`). Providers, keys (encrypted with a key derived from `FAMOS_SECRET`), role mapping and limits live in the `ai_*` tables and are edited in the admin UI (Settings → AI); `FAMOS_AI_*` environment variables define one provider (fixed id `ai_provider_env`) that the server keeps in line with them on every start; it is read-only in the UI, and roles the family pointed elsewhere are left alone.
- **Model roles**: `fast`, `vision`, `smart`, `transcribe` (speech to text) and `embed` (text embeddings for family search). Each role maps to `provider:model`. `transcribe` is not a chat call: `LlmPort.transcribe` posts the audio as multipart to the provider's OpenAI-style `POST {baseUrl}/audio/transcriptions` (OpenAI, Groq, OpenRouter, self-hosted Whisper servers; Ollama has none, so the role is `not_configured`). It follows the same rules as `generateObject`: job handlers only, explicit timeout, switches, monthly limits, one `ai_usage` row per call (role `transcribe`, cost when the provider reports it), `LlmError` codes, and no audio or transcript in logs.
- Every call is recorded in `ai_usage`: role, model, feature, member, job, tokens in/out, cost (when reported), latency, error code. Prompts and outputs are never stored or logged.
- Monthly limits per household: budget (reported costs) and call count, in the family's calendar month.
- **LLMs are never called inside an HTTP request.** A slow model call inside a request thread can take most pages down, so only job handlers receive `ctx.llm` (`JobContext`; route handlers get no `LlmPort`, so the rule is enforced by types); each call names a role and an explicit timeout. The one exception is the family search question (see Family search). The admin "test connection" lists the provider's models and never runs a model. `LlmError.retryable` tells the job whether the queue should retry or the family must act (no model, bad key, limit reached).
- Local inference (Ollama, Whisper, OCR) runs in optional compose profiles or on another machine, reached by URL.
- **Switches** (Settings → AI): a main switch and one per AI feature (the `feature` each call names; web extensions list theirs as `aiFeatures`). `LlmPort.policy(feature).enabled` lets a job hold its work (the Inbox keeps items unread, status `held`); the adapter refuses disabled calls with `disabled`.
- **Privacy** (Settings → AI, `LlmPort.policy()`): the family decides whether photos and documents, voice notes (`sendVoice`, default on; the adapter refuses `transcribe` with `disabled` when off), and member names with their "about" text, are sent. Without names the model is told nobody's name or description (not even who shared the item); the names the message itself writes are still matched to members at home, after the model has answered, so nothing about the family leaves the house. The assistant and MCP see members only by handle then. With `zeroRetention` on, OpenRouter requests ask for zero-data-retention endpoints (`provider: { zdr: true, data_collection: 'deny' }`); a model without one fails with `data_policy`, which every feature records with a reason that names the option. It is off for a new family, because it makes most free models unavailable and which model a family uses is its own choice; families that used AI before it changed keep the setting they had (migration `ai/0004_keep_zero_retention`). The connection test lists which OpenRouter models have such an endpoint (`/endpoints/zdr`), so the model picker can mark the others. Photos lose EXIF/XMP/IPTC (location) when they are uploaded, before storage and before any model call; the orientation is kept. Limitation: OpenRouter's `/audio/transcriptions` ignores provider routing, so zero data retention cannot be guaranteed for speech to text; the AI settings say so.
- **AI areas**: an area is an extension (`core` never is). Sensitive areas start Off because most installations (a Raspberry Pi) cannot run a useful local model, so the safe default is no AI there at all; filing a shared paper into an area by hand is the path that keeps working. Core stores `ai_areas` in `core_settings` (extension id → `off` | `local` | `any`; default `off` for extensions declared `sensitive: true`, otherwise `any`) and caches it like the feature switches (`kernel.aiAreas`, refreshed on `core.aiAreas.changed`); `core.setAiAreaAccess` changes it (`core.ai.manage`; opening a sensitive area to `any` needs `confirmSensitive`). Three checks read the same setting: `access.can` is false for AI actors in an `off` area, and in a `local` one for an actor whose model is not local (`actor.local`); `ctx.actions.aiCatalog({ local })` leaves out `off` areas and, unless `local` is true, `local` ones; and the adapter refuses a call whose `areas` (required on `generateObject` and `transcribe`) include an `off` area (`disabled`) or a `local` area when the role's provider is not local (`local_required`, recorded in `ai_usage`, never retried with another provider). `LlmPolicy.local` (from `policy(feature, role)`) says whether that role's provider is local: its base URL host resolves only to local addresses (the http guard's `isLocalAddress`, resolved at call time and cached for 60 s), whatever its kind.

- **AI modes**: an AI actor says how it works, `{ kind: 'ai', mode, source }`: `share` (it reads what a member shared, which is untrusted; Quick add), `conversation` (it answers a member in the app's own conversation; the assistant), `agent` (an agent of the family's own working from outside; MCP). Core decides by the mode, never by `source`, which only names the extension or door: only `conversation` is offered `conversationOnly` actions and reads the member's notes, and what a `share` proposed is the sharer's to withdraw. Drafts and audit rows stored before modes existed got theirs by core migration `0003_ai_mode`, the one place core names those extensions.
- **Prompt data**: data for a prompt comes from the job's own item or from read-only actions invoked as the AI actor (`ctx.actions.invoke(id, input, { kind: 'ai', mode, source })`), which `access.can` judges like any member and which an `off` area refuses. A job never queries another extension's tables for a prompt.
- **No way out**: AI output can only become drafts of registered actions, which a person approves; actions marked `external: true` cannot carry AI hints (registry check); the web app renders AI-provided text as text and never fetches a URL it contains (images and files shown come from the app's own stored files).
- **Output modes**: `generateObject` asks for structured output in one of three ways, chosen per provider kind and model id (`OUTPUT_DEFAULTS` in the adapter, kept in line with the Inbox evaluation): `schema` (the provider gets the JSON Schema and constrains decoding), `json` (a JSON object is asked for and the schema is written into the system prompt; the default, because constrained decoding makes some models loop or leave fields out) or `text` (no response format, for servers that refuse one). In every mode the adapter takes the JSON out of the answer itself and validates it with the request's Zod schema, so a caller makes its schema tolerant where one bad field must not cost the whole answer (the Inbox reads proposals one by one). A refused request steps down a mode (`schema` → `json` → `text`), and so does an unusable answer from `schema`; every attempt is an `ai_usage` row with its `output_mode`. A caller may force a mode (`output`), which then has no fallback; there is no setting for it.
- **AI activity** (Settings → AI → Usage & limits → "See what the AI did"): `ai_usage` also records `areas` (JSON array of the extensions that contributed data; refused calls are recorded with their areas). `GET /api/v1/ai/activity?limit=&before=` (`core.ai.manage`) returns calls newest first with feature, role, areas, provider, model, tokens, cost, latency, error code and the member's display name, plus a `next` cursor. No prompt or answer is stored, so none can be shown.

### The assistant

The `assistant` extension answers a member's questions in per-member chat threads (`assistant_threads`, `assistant_messages`; never shared).

**Questions are answered from facts code fetched.** A free-form tool loop asks one model to read the question, plan calls over every tool, merge results, decide what is not there and word it all under many rules; each of these jobs slipped on free models in use, and every fix that asked the model to behave recurred while every fix made in code held. So a turn first reads the message and, when it is a question, the model only reads and words; code does the rest, the shape Quick add already proved:

1. **Read** (`understand.ts`): one `generateObject` that gives the `parts` of the message in the order asked (`ReadingSchema`; a message of one thing is one part, and the old answer, one object, is read as one part), each with a small schema (`QuestionSchema`: its `quote` of the message, `intent` `ask | change | remember | other`, `topics` from `QUESTION_TOPICS`, a `span` of `DayRef`s, the `people` as said, the `about` words), about 25 lines of rules and a few examples, with only the message (and the person's previous two messages for context) and no family data (`areas: ['assistant']`). The schema is tolerant: one bad field never throws the reading away. An unusable reading (after the queue's retry) leaves the message to the tool loop.
2. **Resolve** (`question.ts`): the days with `resolveSpan` (none named: the coming seven days), the people with `resolveAskedPeople` (self-words from the catalog), the topics with `resolveTopics` (none named: calendar and tasks). The meal plan brings the calendar along, since a dinner elsewhere is an event. A topic that is not installed, closed to the AI, or not readable by the asker becomes a "not here" line with why.
3. **Fetch**: each open topic's digest (`ctx.actions.aiDigests`), invoked as the AI working for the asker (`ctx.actions.invoke(…, { kind: 'ai', … })`), with the days, the people and the `about` words (which rank, never filter).
4. **Render** (`card.ts`): the answer card (`AnswerCardSchema`, stored in `assistant_messages.card`): what was understood (topics, people, the span's label), each topic's items in the reader's language and date locale, or "Nothing this weekend; next: …", and the "not here" lines. Its plain lines (`card.text`) go to Telegram and into the model's history of the thread. The handles of what the card shows are kept with the thread, so "move it" in the next message points at it.
5. **Word** (`lead.ts`): one chat call with no tools, given only the card's lines, writes one or two sentences; the budget comes from the asker's `about` (an age up to 12, read by digits and the catalog's `assistant:words_age`, gets one sentence of at most 15 words) and the channel (a chat outside the app gets one). Code checks the words: no ISO date and no handle; every weekday next to a date is its own; every day named is one of the card's; every capitalised name is a word of the facts, the family or the question; and no "nothing" (`assistant:words_nothing`, `words_no`, `words_topic_*`) about a topic, or a thing, the card holds. Words that fail are dropped and the message records the check (`card.lead.check`); the card stands alone and is still correct.

So the facts shown are always right; the model can only misread what was asked, and the card's header shows what it read. A message with several parts runs each in code: every `ask` part goes through steps 2 to 5 and gets its own card, and all the other parts together go through one tool-loop call whose prompt names the parts the cards already answered, so it acts only on the requests. The reply is the openings of the cards, then the loop's words; the cards are stored in `assistant_messages.card` (one card as itself, several as a list, so no migration) and are in the order of the parts, with the suggestions under them; Telegram's plain lines follow the same order. A part never takes another down: when the question fails the request still runs and the reply says what was missed, and when the request fails the cards stand with a line saying so. `change`, `remember` and `other` keep the tool loop below. A change or a thing to remember offers only the tools of what it is about (`tool-scope.ts`): the draft and read tools of the areas of its `topics` (through `QUESTION_TOPICS`, so the assistant names no extension), those of the topics the answer just before it was about (a card, then "yes, move it"), or the calendar, tasks and shopping when neither says; core's reads always stay and its note to remember only for `remember`. That is a handful of tools, not every tool of the household, because a model picks well among a few and badly among forty. `other` keeps every tool. The loop offers one tool registry built from the actions, per turn:

- **Chat port.** `LlmPort.chat({ feature, role, areas, system, messages, tools, maxSteps, timeoutMs, onText, … })` runs the model's tool loop (AI SDK `streamText`, `stopWhen: isStepCount(maxSteps)`, tools from JSON Schema; the last step, and any step once 60% of `timeoutMs` is gone, gets no tools, so a model that keeps calling tools still ends with an answer instead of an empty turn or a timeout) and returns the final text, the tools used (name and outcome) and usage. It has the same switches, limits, `areas` checks and one `ai_usage` row (with areas) as `generateObject`. Job handlers only.
- **Read tools** are read-only actions with `ai` hints (`ctx.actions.aiReadTools`): `calendar.findEvents`, `lists.openTasks`, `lists.shoppingList`, `records.upcoming`, the `aiContext` actions of vehicles, pets and home. **Draft tools** are the AI-proposable actions (`aiCatalog`); running one creates a draft, never a change. `external` actions are never tools. AI-facing read actions declare `ai` hints and return handles, never ids.
- **The agent never exceeds the asker.** The turn's actor is `{ kind: 'ai', mode: 'conversation', source: 'assistant', onBehalfOf, roleId }`. `access.can` for it is true only when the AI's own rules allow (view level, area not `off`) and the member's role holds the capability; for a draft, the member must hold `requires` and be able to approve (`approval.unless`) or at least propose (`core.drafts.propose`). The same check (`mayUseAsAi`) filters the tool lists and refuses a direct call in the action runner. Drafts record the AI proposer with `onBehalfOf` in `proposed_by`; approving follows the normal rules.
- **Handles.** `createHandleTable` (SDK) gives members and records short handles (`member:1`, `vehicle:2`). Tool results go through `withHandles` (typed ids become handles); tool inputs go through `repairInput` (handles back to ids, `null` dropped, JSON text parsed) and are refused if they still hold an id the model was never shown. Ids never reach the model, not even their shape: `agentInputSchema` describes a typed-id field as a `shop_list:…` reference and drops its id pattern (a model that reads the pattern writes a made-up id that fits it). `resolveReferences` reads each typed-id field with `referenceId`: a handle as models miswrite it (`member_3`, `3`), and in a member field a person's name, matched at home like `resolvePeople`; an empty text there counts as left out (models fill every field they see), and anything else is refused as invented. The assistant and MCP share all of it.
- **People on a change.** A change to an existing record (a draft whose input has an `id`) takes a person field (`memberIds`, `assigneeId`, any member reference) only when the person's latest message names everyone in it: a whole word of their name, or for the asker a word of their own for themselves (`assistant:words_self`, every installed language). A message with a word for everyone (`assistant:words_everyone`: "everyone", "the whole family") takes an empty list or one of every member. Otherwise, and for an empty list, the field is left out and stays as it is, so a model that puts the asker into every person field never replaces who an event, task or chore is for.
- **One refusal vocabulary.** Every failed call tells the model why in the reasons Quick add uses for its skips (`RefusalReason`: `already`, `unknown`, `other_day`, `ambiguous`, `incomplete`, `not_allowed`, from `refusalOf`), as `Error (<reason>): <the shared words>. <what to do>`, worded by `refusalText`; the action's own message follows only when it explains the input (never for `not_found`, whose message may hold an id).
- **Filters say what they left out.** Models put the asker into every person filter they see. So a person filter is never silent: `lists.openTasks` with `assignee` keeps the tasks anyone may do (as `calendar.findEvents` keeps the family's events) and counts the others' (`otherTasks`); `calendar.findEvents` with `members` says how many events it left out, and when it left a search by `text` empty it lists the other members' matches (`forOthers`); `lists.shoppingList` refuses a list name that is no list with the real names, and shows an item found only on another list than the one named. Dates in these results come with their weekday (`weekday`, `dueWeekday`; `runAgentTool` adds `<field>Weekday` beside every date of a result that names none), because models work weekdays out of dates wrongly. The answer is checked too: a weekday the answer writes next to a date of another weekday ("Monday 20 October" for a Tuesday) is replaced by the real one before the answer is stored and the stream is reset (`correctWeekdays` from `@famos/time`, with the weekday names of the language the wrong word is in), unless the person wrote that mismatch themselves and the answer quotes it. A read tool that looks in a window and finds nothing there names the next thing after it (`calendar.findEvents` `nextMatch`, `records.upcoming` `nextAfter`), so "nothing this weekend" can go on with when the next one is.
- **What is not here.** `ctx.actions.aiMissingAreas({ local })` lists the areas the AI cannot look into on this server, with their English name, description and why: packages it can install that are not installed, installed extensions turned off, and areas closed to the AI. The assistant's prompt lists them, so a question about the flat after Home was uninstalled gets "Home is not installed here" instead of an empty answer from another area read as "there is none".
- **Never the closest thing.** A model that cannot find what the person named tends to act on the nearest real item. Actions that change or delete an existing thing declare `targetTitle`, and an AI actor must send `label`: the name the person used, in their words (the assistant refuses a `label` whose words were never said in the conversation, by the person or in the assistant's own earlier answers such as "did you mean the Dentist checkup?", so the title the model found in a tool result cannot pass). The runner refuses unless the significant words of one side (letters and digits, no bracketed text, numbers or words of one or two characters, a trailing plural `s` ignored) are all whole words of the other, so "the bread" meets "Bread" without any list of filler words, so the refusal names the real title and the model tells the person it is not there. The words come from the data, never from code. Every draft of such an action is then stored with the real title as `label` (a screen's draft too), so a card shows what will change. In one turn a second change to the same target under other words is refused, and `refuseProposal` lets an action refuse a pointless AI proposal (ticking off what is ticked). `lists.shoppingList` also returns what was bought in the last 7 days (`bought: true`), so a bought item is found as bought. An action may declare `resolveNames`, which turns a thing the caller named in words (a shopping list by its name) into the id before the input is judged and stored; an unknown name is refused with the real names, so a model cannot invent one. `resolveNames` also turns a date into the occurrence key of a repeating event (`calendar.changeEvent`, `calendar.deleteEvent`), and refuses a day the series does not have to the model, so a card never fails later on its key. The assistant offers the model every tool the person may use, with no cap: a cut once hid the change tool of a request, and the model then claimed a suggestion it could not make. If a cap is ever needed again it must work per area and never offer an area's read tools without its write tools, because a write tool's description sends the model to them. A drafted result carries `mayExist` (the action's `alreadyThere`) and a ready sentence built from the card title and the subject, and every failed agent call is logged with the action id, the error code and the names of its input fields, never their values.
- **Across turns.** The model sees only text of earlier turns, so the handles it was shown are kept with the thread (`assistant_threads.handles`: handle, id, title) and put back in the table of the next turn; the prompt lists the latest of them with their titles, so "move it" still means the same record. A change's tools include the areas of the latest answer's card, so a follow-up works across the question path and the change path.
- **Untrusted content.** A tool result is shown to the model inside a `<tool_result name="…">` block (the system prompt says it is data), cut at 4 KB, with any closing tag neutralised. A turn has at most 8 steps and 12 tool calls. A call the turn already made is answered from the turn, not run again (a suggestion made twice would be two); after two such repeats, or four failed calls in a row, the tools close and the model answers with what it has. A note to remember (`core.addMemory`) must be in the person's own words: when most of its words are not in what they wrote, it is refused. Answers are stored and shown as text; contents are never logged.
- **A turn is a job.** `assistant.sendMessage` stores the question and a pending answer and enqueues `assistant.turn`; the job streams text to the asking member with `assistant.delta { threadId, messageId, text }` and ends with `assistant.done { threadId, messageId, status }` and `core.conversation.answered { replyId }` (below). A failed answer keeps a code (`LlmError` codes, `no_answer` when the model ended with no words and no suggestion, `forbidden`). `assistant.summarize` folds older messages into the thread's `summary` (the last 12 stay verbatim). The AI feature id is `assistant.chat` (Settings → AI).
- **Private realtime.** `bus.publishTo(memberId, name, payload)` / `ctx.events.emitTo(memberId, event, payload)` reach only `bus.onMember` subscribers; the realtime hub delivers them to the sockets of that member (and only while that member is still in the event's audience), never to displays or other members, and nothing is stored or seen by `onAny`.

### Channels to a conversation

A channel outside the app (Telegram) lets a member ask a question and sends the answer back when it is written. Like shares, the conversation is a contract the host offers without knowing who provides it: `ConversationProvider` (SDK), from one extension (`conversation` in its definition and in its manifest's `provides`; the assistant):

- `requires`: the capability a member needs to ask (`assistant.use`).
- `ask(ctx, actor, { text, threadId })` → `{ threadId, replyId }`: takes the question as the member; a thread that is gone starts a new one; `conflict` while the last answer is being written.
- `answer(ctx, memberId, replyId)` → `{ status: 'done' | 'failed' | 'ai_off', text, draftIds }`, or null when the answer is not written yet or not this member's.
- When an answer is written, done or not, the provider emits `core.conversation.answered { replyId }` to the member (`emitTo`); ids only, so the event says nothing to whoever sees it.

Channels use `kernel.conversation.ask(memberId, question)` (the member must be active and hold `requires`, the provider must be on; `feature_off` or `forbidden` otherwise, so Telegram shares typed text instead) and `kernel.conversation.answer(memberId, replyId)` when the event arrives. The channel keeps which reply it waits for; the answer itself stays in the provider's tables.

### Member memory and addressed drafts

Core holds memory (`packages/core/src/memory.ts`); the assistant extension only carries it. Assistants never message each other or other members: agents that negotiate with each other bring loops, hidden decisions and leaks (one could reveal what the other's person may not see). To involve someone, a member or an agent creates a task or a draft for them, and they act on it in the app.

- **Addressed drafts.** `ai: { addressToMember: true }` on an action makes the assistant's proposal a draft with `core_drafts.for_member` set to the member it works for. Only that member sees it (`core.listDrafts`, the waiting count) or may approve, reject or undo it (`not_found` for anyone else, admins included, replays too); the addressee needs no `core.drafts.approve` for their own. No "draft waiting" notification is sent, and auto-approval skips it. `core.addMemory` uses it, so the approver is always the person the action acts for.
- **Drafts belong to the person behind them.** For every AI draft the person behind it is `onBehalfOf` (assistant, MCP) or `DraftMeta.forMember` (Inbox). After auto-approval has been checked, the runner stores `for_member` = that person when they are active and could decide the draft themselves (`core.drafts.approve` plus the action's `requires` and `approval.unless`; `deciderBehind`); nobody is told. Otherwise (a supervised member) the draft is unaddressed and the "draft waiting" notice goes to the approvers except that person. `ActionRunner.mayDecide(draft, actor)` answers the same question for an existing draft, and the read action `core.decidableSources` lists which items of a source (`inbox`) have a draft the member may decide, so an extension can show an item to its decider without reading `core_drafts`. Telegram buttons only list drafts the recipient may decide.
- **Memory.** `core_member_memory` (text up to 280 characters, at most 100 per member). `core.addMemory` / `updateMemory` / `deleteMemory` act on the caller's own notes only; `core.listMyMemories` lists them. `core.recallMemories` (read-only, no `ai` hints, so never a tool) returns the notes of the caller, or of the member the AI works for in the app's conversation (`mode: 'conversation'`); the turn job puts the newest 20 (1,500 characters at most) in the system prompt of that member's own threads, and only when `policy.sendPeople` allows. The Inbox and MCP never read them.
- **In the assistant.** The tool wrapper hides `source` from the model's schema and sets it itself (`ai`).

### Auto-approval

Some suggestions are routine (shopping items, tasks). Auto-approval lets a family approve those by themselves, and it is deliberately one small setting in core (`packages/core/src/auto-approval.ts`), not a rules engine: triggers, predicates and mapped inputs are attack surface and can loop, and the assistant and outside agents already cover "do X when Y" as drafts.

- **Opt-in where the action is defined.** `autoApprove: { label, capabilities }` on `defineAction` (`label` is an i18n key naming what is approved; `capabilities` are the ones a proposer may be required to hold, the first is the default). The registry refuses it on read-only, `external`, `core.*` and sensitive-extension actions and on unknown capabilities. `lists.addShoppingItems` and `lists.addTask` opt in.
- **Storage.** One `core_settings` row (`core.autoApproval`): action id to `{ proposerCapability, enabledBy, enabledAt }`. `core_drafts.auto_approved` marks drafts approved this way (`decided_by` is the member who enabled the setting); the draft API exposes `autoApproved` and `decidedBy`.
- **Setting it.** Action `core.setAutoApproval` (`{ actionId, setting | null }`) and route `core.listAutoApproval` (actions that opted in, their capability choices and current value), both under capability `core.autoApprove.manage` (critical: admins only). Settings → AI → Auto-approval.
- **Where approval happens.** When the action runner creates a draft for an opted-in action, it checks the setting and the proposer in the draft's own transaction: only AI drafts can qualify, and the person they were proposed for (`onBehalfOf`, or `DraftMeta.forMember` for the Inbox) must be active and hold `proposerCapability` (looked up through the role). A draft a person made themselves, drafts addressed to one member, system and display drafts never qualify (a person-made draft that would qualify cannot occur with the current approval policies). If it qualifies, the same transaction enqueues job `core.autoApprove` (deduped by draft) instead of the "draft waiting" notification (the queue is the outbox, so a crash loses nothing).
- **The job** re-checks everything, then calls `ActionRunner.approveDraft(draftId, enabler, undefined, { auto: true })` as the enabling member, so the runner enforces that member's capabilities at that moment. Idempotent: a draft that is no longer `pending` does nothing. If it cannot approve (the enabler is archived, no longer holds `core.autoApprove.manage`, or the runner answers `forbidden`), it stops the setting (removes the row if it is still the same `enabledAt`), notifies the enabler (everyone who manages auto-approval when they are gone; kind `core.autoApprovalStopped`, deduped) and sends the usual "draft waiting" notice, so the suggestion waits for a person.
- **Visible and reversible.** An auto-approved draft stays visible as approved by the setting, and undo works as for any approval (the draft is `applied` with its result).
- **No loops by construction.** Nothing publishes on a draft's approval except the usual UI events, and no handler reacts to them with actions.

### MCP server: bring your own agent

People who already use a personal agent (Claude Desktop, Claude Code, Hermes Agent, an IDE) would rather connect it than use a second assistant inside FamilyOS. FamilyOS is not an agent but a set of data and actions, so the protocol that fits is the Model Context Protocol, not an agent-to-agent protocol: an outside agent uses FamilyOS's tools as one member, sees only what that member may see in the areas open to the AI, and every change is a draft the member approves. A person's preferences live in their own agent's memory; FamilyOS's member memory is never given to it. FamilyOS never calls out to other agents.

Other AI apps get the assistant's tools through `/mcp` (`apps/server/src/mcp/`, mounted next to the API; no extension, no new core concept besides tokens).

- **Server.** `@modelcontextprotocol/server` 2.3.1 (`createMcpHandler`: spec 2026-07-28 per-request envelope, `server/discover`, and the SDK's stateless fallback for the 2025 handshake; GET/DELETE session operations answer 405) with `@modelcontextprotocol/hono` 2.0.2 (`createMcpHonoApp` parses the JSON body, capped at 256 KB). A new `McpServer` is built for every request from the token's principal: there are no sessions and nothing is kept between requests.
- **Tokens.** Personal API tokens, not OAuth: clients that support only the specification's OAuth flow cannot connect, and the guide says which kinds of client work. `core_api_tokens` (id `api_token_…`, member, name, SHA-256 of a 32-byte random secret with the prefix `famos_`, scope `read|read_write`, expiry (default 90 days, at most 365), `last_used_at` (updated at most hourly), `revoked_at`). `kernel.apiTokens` creates, lists and revokes them through routes under `/api/v1/mcp/` (credential management outside actions, like push subscriptions); creating needs `core.mcp.use` (level use, but not held by supervised members by default: a token carries what they can see to a provider the family never chose), listing or revoking everyone's needs `core.ai.manage`. Only a password sign-in creates one (`assertFullSignIn`, SDK): a PIN is short and works on shared devices, so it never mints a credential that works away from them; the same rule guards calendar feeds and Telegram links, and `/me` says `fullSignIn` so the UI shows a note instead of the button. Signing out everywhere, a new password and archiving a member end credentials durably: in the same transaction core revokes the member's tokens and enqueues `core.endCredentials` (before the sessions end, so a failure leaves the person signed in to try again), and that job calls the `endCredentials(ctx, memberId)` hook of every extension that declares one (the calendar's feeds) and is retried with backoff until it succeeds, so hooks are idempotent. The feed route's owner check is the backstop while the job is pending. `last_used_at` is written by `touch` after the `core.mcp.use` check, never by `authenticate`. The feature switch is the core setting `mcp` (`{ enabled }`, default off), changed with `PUT /api/v1/mcp/settings`.
- **Request path** (middleware on the parent app, before the body is read): switch on? else 404; no query parameter that looks like a token or starts with `famos_` (401); `Authorization: Bearer famos_…` only (cookies are never read, so there is nothing to forge and the CSRF check, which covers `/api/v1`, does not apply); token known, not revoked, not expired, member active (401 with a JSON-RPC error and `WWW-Authenticate`); the member's role still holds `core.mcp.use` (403); 60 requests per minute per token (429, `Retry-After`); 30 failed attempts per minute per client address (429).
- **Tools.** The actor is `{ kind: 'ai', mode: 'agent', source: 'mcp', onBehalfOf, roleId, scope }` (`mcpActor`), the token's `scope` on it so the action runner refuses a change from a `read` token even if a tool list were built wrongly. Tools are rebuilt on each request with `aiReadTools` (and `aiCatalog` for `read_write` tokens) with `local: false`: areas that are off or local-only are absent, because the client is outside the house; `external` actions cannot have AI hints; `conversationOnly` actions (personal memory) are offered to `mode: 'conversation'` only. Calling runs the same `runAgentTool` (SDK) as the assistant: handles to ids, the action runner (capabilities, sandbox, approval), a draft with `sourceKind: 'mcp'`, the result back to handles inside a `<tool_result>` block. An extra read tool `family_listPeople` exists when **Send names and descriptions** is on and the token's owner holds `core.members.view`. Annotations: read tools `readOnlyHint: true`; draft tools `readOnlyHint: false, destructiveHint: false, idempotentHint: false`; all `openWorldHint: false`, and a draft tool's description says it creates a suggestion a family member approves.
- **Stateless handles.** The assistant numbers records per turn (`vehicle:1`); MCP has no turn. A handle is `<kind>:<first 10 hex digits of HMAC-SHA256(tokenId, id)>`: stable for one token across requests, different for another token, and never an id. The mapping back is stored per token in `core_api_token_handles` (the newest 5,000 are kept; removed with the token). Before a call the handles found in its arguments are loaded; an id or handle the token was never shown is refused like an invented id. Handles are written after each call.
- **Audit.** Each `tools/call` writes one `ai_usage` row (feature `mcp`, provider `MCP`, model = the token's name, areas, member, error code `rejected` when the call failed); AI activity shows it with no content.

### Digests: the facts of a question

A model that chooses its own reads over many tools slips in ways no prompt rule fixes: it searches by the person's words and misses the event under another title, it reads an empty result as "there is none", it drops what a tool did not return. So the facts a question needs are fetched by code, one **digest** per topic, and the model only reads the question and words the answer.

- **Contract** (`@famos/sdk`, `digest.ts`). `defineDigest({ id, topic, title, description, requires, run })` is a read-only action with the digest's own Zod shapes and `ai: { digest: topic }`. The topics are `QUESTION_TOPICS` (calendar, tasks, shopping, meals, chores, records, pets, vehicles, home, board, suggestions), each kept by one area. The registry refuses a digest for a topic another area keeps, two digests for one topic, and a digest with other shapes.
  - Input `DigestInputSchema`: `{ from, to, memberIds?, about? }`, plain dates of the family's time zone, at most 62 days.
  - Output `DigestOutputSchema`: `{ items, truncated, nextAfter?, hidden? }`.
  - A `DigestItem` is `{ handle, kind, title, date, time?, end?, allDay?, people, notes?, status?, extra?, href? }`. `href` is a path inside the app that opens the item, written by the digest's own extension from its page routes (`/calendar?event=<id>&on=<day>`, `/lists/tasks?task=<id>`, a record's stored page); a digest is never read by a model, and `readableOutput` drops every `href` as well, so a model sees no id and no address. `handle` is the thing's typed id, which the host turns into a handle as for every AI read; `people` are member ids (empty: everyone, or anyone); notes are cut at 300 characters; `extra` holds a few facts of the kind as text (a place, a meal slot, the record a duty is for, how many things a list has). `date` is when the item happens or is due; something late keeps the day it was due; what stands over days (a note on the board, a waiting suggestion, a shopping list) has the span's first day it stands on.
- **Rules every digest keeps**, with the SDK's helpers:
  - the span bounds count both days, and repeating things are expanded on each of their dates in it;
  - `memberIds` keep what is for one of them and what is for everyone (`digestForPeople`), as person filters do everywhere;
  - `about` words only rank: items that meet more of them come first, the others follow in their order, and none is left out (`rankDigest`, by the read tools' word forms), because the person's words need not be the title's;
  - the list is cut after ranking at 60 items (`truncated`), so what the words name stays in;
  - when the span holds nothing, `nextAfter` is the first item after it for the same people (`digestOf` asks only then);
  - something late counts when the span holds today; a date that only passes (a warranty ends) is never late.
- **The digests**: `calendar.digest` (events with their notes, place and tags, subscribed calendars included; a timed event of today says whether it is over, on now or ahead); `lists.tasksDigest` (tasks due, and in a span that is not over the open ones with no due date, marked `undated`, after the rest: "the open tasks" are those too) and `lists.shoppingDigest` (one item per list with things to buy, its count and the first of them; the span and people never leave one out); `chores.digest` (each turn with whose it is or will be: fixed and round robin are known ahead, least done names everyone in the rotation); `kitchen.digest` (meals planned: an evening without one has nothing here, since a dinner elsewhere is an event in the calendar's digest); `records.digest` (every duty) and `pets.digest`, `vehicles.digest`, `home.digest` (their own record kinds, read through `records.dueBetween`; home services stay out as they do of every AI read); `board.digest` (notes up on some day of the span, pinned first); `core.suggestionsDigest` (what waits for the asker to decide, wherever it was made, and their own that wait for someone else, newest first, at most 15; it waits now, so span and people never leave one out).
- **What the AI may read.** Code finds the digests with `ctx.actions.aiDigests({ local, actor })`, filtered like the read tools: extensions turned on, areas open to the AI (local-only ones only for a local model), actions the asker may run. Digests are never read tools: the model does not choose them. They are invoked as the AI actor, so an area that is off refuses, and a digest of a local-only area refuses an actor whose model is not local. A digest that gathers things of several areas leaves out those the AI may not read and counts them in `hidden` (a pet's duty in `records.digest` when pets are off for the AI; a suggestion whose action's area is closed in `core.suggestionsDigest`), so the answer can say there is more it cannot see.

### Family search

The assistant answers from read tools, which cannot find "the paper about the boiler warranty" when the words differ, and meaning matters for languages with rich word endings. Core finds things by meaning with embeddings; there is no vector extension, because a family has at most tens of thousands of short texts, exact scoring is fast at that size, and a native SQLite extension would have to be built for arm64. Embedding sends family text to a model, so it follows the AI sandbox like every other model call. Without an `embed` model nothing is indexed and nothing changes. Code: `packages/core/src/search.ts`, `LlmPort.embed` in `@famos/adapters/llm-aisdk`.

- **Port.** `LlmPort.embed({ feature, area, texts, timeoutMs, memberId?, jobId? })` returns one `Float32Array` per text, the model key (`<provider id>:<model>`) and the dimensions. The adapter uses the AI SDK's `embedMany` on the OpenAI-compatible client (`POST {baseUrl}/embeddings`; OpenAI, OpenRouter, Ollama, any compatible server) for the `embed` role. Same rules as every call: main and feature switches, monthly limits, one `ai_usage` row (role `embed`, input tokens when reported), `LlmError` codes, and the area check: `area` Off refuses (`disabled`); Local only refuses unless the role's provider is local (`local_required`), with no fallback. `LlmPolicy.model` carries the same model key, so core can see a model change. The test fake (`createFakeLlm`) embeds with a hashed bag of words and checks areas the same way; `embeddingContract` is the port's contract suite.
- **What is indexed.** An extension opts in with `ai: { index: { kinds, list } }` (SDK `AiIndex`). Each kind (`<extension>.<kind>`, for example `kitchen.recipe`) names the capability that lets people find it, optionally a `viewAll` capability (for a kind whose items are otherwise only the owner's), and `load(ctx, id)`: one entity as `{ title, text, href, ownerMemberId?, capability? }` or null (gone, archived, filed, dismissed). `list(ctx, cursor)` walks every entity in pages, for rebuilds. Extensions say so after each change inside their transaction, `uow.ai.reindex(kind, id)` (enqueues `core.embed`, deduplicated per kind and id) or `uow.ai.remove(kind, id)` (deletes the chunks in the transaction); jobs and handlers use `ctx.ai`. Wired: Inbox items (summary and prepared text, not items filed by hand), kitchen recipes, home things and services (never serial or account numbers), calendar events (title, place, notes), records obligations and the names and labels of papers (a paper's own text stays out: filing keeps the AI from reading it). An obligation names the capability of its area as its audience, and search honours that like the AI context does.
- **Chunks.** Core cuts the text into pieces of about 800 characters with a 100-character overlap (paragraph, sentence or word boundaries; at most 40 per entity), prefixes each with the title, hashes it and embeds only the pieces whose hash or model changed (`core_embeddings`: extension, kind, id, capability, owner, title, href, a 240-character snippet, model, dimensions, hash, chunk index, the vector as unit-length little-endian float32, time). A change that arrives while the model works is deduplicated into the running job, so the job reads the entity again before it finishes. An error a person must fix (`LlmError` not retryable: no model, bad key, limit) is logged by code, kept in the search state (`core_settings` key `search_index`, shown by `GET /api/v1/core/search/status`) and not retried in a loop; retryable ones use the queue's backoff.
- **Settings follow.** `kernel.reconcileSearch()` enqueues `core.embedSync` at start and after a change of an AI area, a feature, a model or a provider (the AI settings routes call it). The sync job deletes the chunks of an area that is Off, or Local only while the `embed` provider is not local; for every other area whose index was not built with the current model it enqueues `core.embedRebuild` (long lane), which walks the extension's `list` page by page, embeds what is needed and finally drops chunks of older models. With no `embed` model (or AI off) the built-state is forgotten, so setting one later reads everything again (unchanged text costs nothing).
- **Asking.** `core.searchFamily` is a read-only action with `ai` hints (so the assistant and MCP get it as a read tool, only while an `embed` model is set) and the route `GET /api/v1/core/search?q=&limit=` for people (409 `not_configured` without a model). It needs a person: an AI with nobody to work for is refused. The question is embedded in the action's `prepare` step, which the runner calls after the permission checks and before the transaction opens (a unit of work holds the one database connection, so a model call must not run inside it); this is the one model call that runs inside an HTTP request (and an MCP request), with a 10 s timeout, a deliberate exception to the rule above for the short question of a person who is waiting. Then, in SQL and before any scoring: the model key and dimensions match, the kind's area is open to the asker (on, not Off, and Local only only for an AI whose model is local, `Actor.local`), the person (or the AI's member) holds the kind's capability and the row's capability, and the row is theirs (`owner_member_id` null, or their own, or the kind's `viewAll`). Rows are read in pages of 2,000 and scored with a dot product in TypeScript (unit vectors), keeping the best 5 × limit chunks; results are one per entity, best chunk first, with a positive score. A result is `{ id, kind, extension, title, snippet, href }`; for the AI `href` is null and `id` becomes a handle through `withHandles`, so the model opens the record with the area's own read tool and the permission check runs again.
- **Cost.** Scoring 50,000 × 768 floats takes about 40 ms in Node on a laptop (`FAMOS_BENCH=1 pnpm vitest run packages/core/test/search-bench.test.ts`); reading them from SQLite in pages takes about 750 ms, so the load, not the arithmetic, is the cost at that size. Beyond ~200,000 chunks, or when a search passes 200 ms on the target hardware, keep the vectors in memory or move scoring to `sqlite-vec` behind the same table shape.

## 12. Data, migrations and backups

- **SQLite only**, WAL mode, one writer connection, `busy_timeout`, `foreign_keys = ON`, STRICT tables. One family per installation means tiny write concurrency and little data; one database file makes installation one container and backup one consistent snapshot, with no per-dialect migrations or test matrix. Projects that supported several databases (Ghost, n8n, Directus) paid for it in migrations, tests and semantic drift. The API cannot scale horizontally, which a family does not need.
- Timestamps are epoch milliseconds (UTC); the family timezone is a setting. Date and recurrence math happens in TypeScript, not SQL.
- **Time and recurrence.** Every date computation uses the Temporal API (`temporal-polyfill`) through `@famos/time`, the one tested place for time math; extensions call it instead of hand-rolling dates. Timed instants are stored as epoch milliseconds with the IANA zone beside them; all-day dates are `YYYY-MM-DD` strings, never converted to instants, so they do not shift when viewed elsewhere. Recurrence is stored as RFC 5545 `RRULE` text plus `EXDATE`s (CalDAV-compatible) and expanded with `rrule-temporal` in the event's time zone, which handles daylight-saving changes. The family has one time zone; every expansion and "today" uses it unless an event carries its own.
- **Forward-only migrations** written by hand with Kysely, never generated, so every schema change is explicit and reviewed. An extension's migrations run with its scoped database, so they can create and change only tables with its prefix. There is no `down`: rolling back an upgrade means restoring the automatic pre-migration backup. Each extension has its own migration table and folder; core migrates first, then extensions in dependency order. Out-of-order migrations are rejected. A released migration is never edited; a change is a new migration.
- **Expand-only** within a major version: add tables, or nullable or defaulted columns. Renames and drops (of columns, tables or API fields) happen only in a major release, after deprecation, so that upgrades never break an installation and pending drafts and stored outputs keep validating. Unused columns may stay until the next major.
- On startup: if the database schema is newer than the code, refuse to start. Otherwise take an automatic pre-migration backup, then migrate.
- **Supported upgrade window**: any release in the previous major version. Migrations are squashed only at major versions, announced in advance.
- **Backups**: `famos-<timestamp>.tar` containing `manifest.json` (app version, schema versions, created at, checksums), a consistent `VACUUM INTO` snapshot, the `files/` directory, and the installed language packs, theme packs and extension store (`languages/`, `themes/`, `extensions/`, each when there is one; uploads not yet installed are left out). The format stays 1: these folders are only added, and a backup without one restores, leaving that folder as it is. On restore, a scope whose extension package the backup carries is not compared with this server's migrations (its own package comes back and is checked at the next start); an installed extension whose package is in neither the backup nor the server is refused at start, not fatal. Nightly schedule with retention; restore via CLI or the first-run screen. **Restore hygiene.** A restore copies the database back as it was, which would also bring back what the family ended since: sessions, an old password, revoked keys and devices, archived members, stopped feeds and unlinked chats. `restoreBackup` therefore moves the old database aside together with its journal files (`famos.db.pre-restore-<time>`, `…-wal`, `…-shm`, so it opens with every committed change) and writes `restore-pending.json` next to the database. The first start after it (`apps/server/src/restore-pending.ts`, after migrations and `kernel.start()`, before anything serves) calls `kernel.reconcileRestore(previous, hostSteps)` and removes the marker only when it succeeded; every step is idempotent and carries only what ends access, never what grants it, matched by id (a row the old database lacks is left as restored): all sessions are deleted (`IdentityAdmin.endAllSessions`; the step runs before the server listens, so no socket of the old data is open); `revoked_at` of keys and devices and `archived_at` of members are carried (a newly archived member goes through the same end of credentials as an archive: keys revoked and `core.endCredentials` queued, logins removed); newer password and PIN hashes of a login both databases have are taken (`IdentityAdmin.carryNewerLogins`); Telegram unlinks are carried by the adapter for members the old database knows; and every extension's `onRestore(ctx)` hook runs with `ctx.previous`, its own tables in the old database, read-only (the calendar stops the feeds stopped since). API tokens are not paused: their revocations are carried like the rest, which keeps working keys working and is safe because nothing a person revoked comes back. Admins get `core.backupRestored` saying how many such decisions stayed. A failing extension hook is logged and does not stop the others or the start; a failure in core's steps leaves the marker so the next start runs them again. Open limit: roles changed after the backup (a demotion) are not carried. Extensions may register pre/post-backup hooks.

  **Remote copies and encryption.** Nightly backups on the same disk as the data do not survive a failing SD card or a stolen device, so backups can be copied elsewhere, encrypted with `age` (a small, well-specified format with a standard CLI, so a backup stays readable with standard tools). `@famos/adapters/backup` (migration scope `backup`) holds the encryption choice, the targets and the upload. After each nightly or manual backup, one `backup.upload` job per enabled target is enqueued (deduplicated by target and backup name); `backup.run` ("Back up now") writes the backup in the worker, never in an HTTP request. These are *infrastructure jobs*: adapters hand them to the kernel through `KernelOptions.infrastructureJobs`, next to `infrastructureMigrations`. The upload streams the local `.tar` through `age` (passphrase via scrypt, or an `age1…` recipient) to a `BackupTarget` (`put`, `list`, `delete`, `test`): S3-compatible (`aws4fetch` for SigV4, our own single and 8 MiB multipart upload, so memory stays near one part) or WebDAV (plain `fetch`, `Content-Length` known because age's output size is computable). Targets use `fetch` directly instead of the guarded HTTP port: they are configured by an admin, may live on the LAN, need PUT/PROPFIND with large streamed bodies, and send credentials, so redirects are refused. Backups kept on the server stay unencrypted; nothing is uploaded until the admin has chosen an encryption mode (including an explicit "none"). Retries back off up to 5 attempts; on the last (or a non-retryable error) admins get `core.backupFailed` once and the target shows the result code. An upload holds the `long` lane while it runs (up to 50 minutes), so reminders and notifications on the default lane are not delayed. `restore` accepts `.tar.age` (passphrase from `FAMOS_BACKUP_PASSPHRASE` or a prompt, or `--identity`), decrypts streaming into a temporary folder in the data directory, then restores as usual. `FAMOS_SECRET` and the passphrase are never inside a backup.

### Connected apps

Programs outside FamilyOS (Home Assistant first, then scripts, Node-RED, Shortcuts) read and change family data with a key of their own. They are not people and not the AI, so they are their own principal: an admin registers an **app** with a role (a built-in or custom one), a **mode** (`apply`: its changes follow its role; `suggest`: every change is a draft a person approves) and the members it **may act for**. The reasons behind the choices:

- **Tables.** `core_apps` (id `app_…`, name, `role_id`, `mode`, `acts_for` as a JSON list of member ids, `created_by`, `revoked_at`, `paused_at`) and `core_app_tokens` (id `app_token_…`, `app_id`, name, SHA-256 of a 32-byte secret with the prefix `famos_`, `expires_at`, `last_used_at`, `revoked_at`). Keys are a sibling table, not a column on `core_api_tokens`: a personal key always belongs to a member and carries a scope and per-key handles, an app key never does, and a hash lookup in one table can never produce the other kind of caller, so an app key cannot open `/mcp` and a personal key cannot open the apps' door. Keys are long-lived: no expiry unless the admin sets one (a 90-day default would silently stop Home Assistant), at most five live keys per app so a rotation is "add one, switch the app over, revoke the old one", and the page warns two weeks before an expiry.
- **Management is credential management**, so it runs outside actions like personal keys and device trust (`kernel.apps`, routes under `/api/v1/apps`): it needs `core.apps.manage` (critical, so admins only and never on a PIN sign-in) and `assertFullSignIn`. The secret is shown once; lists never carry it.
- **Authenticating.** `kernel.apps.authenticate(secret, onBehalfOf)` returns the app actor, or, when `X-FamilyOS-On-Behalf-Of` names a member, the member with `via`. The member must be on the app's list and active, otherwise the call throws `forbidden` (never quietly served as the app itself, so a script is never "nobody" by mistake); the member's role is read on every request, so a lowered role or an archive applies at once. A revoked or paused app, a revoked or expired key, and an unknown key are all `null`. Authenticating changes nothing; `touch` records the use after the request was permitted.
- **Acting.** Decisions are the action runner's, as for a person (see §7); the member through an app is `personPresent` false, so deciding, editing or withdrawing drafts, credentials, devices, sessions, auto-approval, roles, members, extensions and managing apps are refused, in the runner and in every service that asks for a person present. An action run inside another one is decided for the same actor (`nested_needs_approval`). Idempotency keys are per principal (§14), so Home Assistant and a member never share a key space. The audit log stores the whole actor (the app, the member and the mode), a draft stores it as its proposer and the draft list adds the app's current name (`app`), so cards say "Home Assistant" or "Leo via Home Assistant"; a draft by an app alone is addressed to nobody, so the approvers see it.
- **Restore.** A restore pauses every live app (`paused_at`, in `reconcileRestore`) and carries revoked apps and keys over, so an old backup never brings a leaked key back to life; an admin resumes the apps they trust, and the admins who may manage apps get a notification. Personal keys keep their existing handling.
- **MCP keys are not folded into apps.** A personal key is bound to its member, shares that member's `core.mcp.use` check and per-token handles, and is already enforced as `{ kind: 'ai', mode: 'agent', scope }` by the runner (suggest-only by construction). Turning them into suggest-mode apps would have changed every existing key's actor, idempotency principal, handles and audit rows for no new protection; they stay as they are and are listed on the same page (Settings → Connected apps) beside the apps. A later change can fold them in without a change of behaviour.
- **Threat model.** A stolen app key does what the app's role allows and no more: never a critical capability, never deciding a suggestion, never creating a credential or managing people, devices or roles; it is revoked at once, its last use is shown, and a restore pauses it. An app naming a member is limited to its list and to what both hold. An AI behind an app is contained by `mode: 'suggest'`. The apps' door takes no cookie, so it is no CSRF target, and a bearer is refused at the app's own API.

## 13. Auth and RBAC

- First-run wizard creates the first admin.
- **Roles and capabilities.** Households differ (a couple of equals, an adult child running it for their parents, grandparents and a babysitter), so FamilyOS assumes no household shape. What a person may do (security) is separate from who they are (context for the AI). Core and extensions declare capabilities (`calendar.edit`, `core.drafts.approve` …) with a level (`view`, `use`, `edit`, `manage`); core maps levels to the built-in roles Admin, Member, Supervised and Guest. Custom roles are a built-in base plus overrides, stored in `core_roles`. Code only asks `can(actor, capability)`: routes declare `requires`, actions declare `requires` and/or `approval: { unless }` (people without the capability propose a draft). Critical capabilities stay with admins, and a PIN sign-in never holds them. An extension may declare defaults that only remove grants its level gives (§6). Members carry an optional free-text `about` ("9 years old", "Sam's partner", "visits on Tuesdays"), shown to the AI with the name instead of a role label; it has no security meaning.

  | Level | For | Admin | Member | Supervised | Guest |
  |---|---|---|---|---|---|
  | `view` | Seeing | ✓ | ✓ | ✓ | ✓ |
  | `use` | Doing one's own things (complete a task, share) | ✓ | ✓ | ✓ | – |
  | `edit` | Changing shared data | ✓ | ✓ | – (proposes a draft) | – |
  | `manage` | An extension's settings | ✓ | – | – | – |

  Mapping levels to roles in one table means every extension behaves alike and a new built-in role needs one change. Capability ids are namespaced by their owner (`calendar.…`); the registry refuses other ids and routes or actions that name an undeclared capability, so a typo fails at startup instead of silently allowing everyone. Capabilities added later take the base role's default, so custom roles stay correct; overrides of capabilities that are not registered (an extension turned off) are kept and apply again when it returns.
- **Guardrails.** At least one admin always exists. The Admin role cannot be edited and is not a base for custom roles. Critical capabilities (`core.members.manage`, `core.roles.manage`, `core.devices.manage`, `core.ai.manage`, `core.features.manage`, `core.settings.manage`, `core.autoApprove.manage`, `core.apps.manage`) exist only in the Admin role. Only admins assign roles, so nobody grants a capability they do not hold. A PIN sign-in never holds a critical capability, whatever the role: the session resolves to a member actor marked `pin`, and `access.can` refuses critical capabilities to it (so `core.getMe` lists none), so a guessed PIN never yields administration.
- Sign-in: any member may have an email + password, a PIN, or both (the members page sets them; `IdentityAdmin.signInMethods` says which exist, never the secrets). People with a PIN whose role holds `core.signIn.pin` (every built-in role; a custom role may drop it) pick their profile and enter the PIN on family devices (rate-limited, constant-time check, rechecked against the current role on every sign-in).
- **Trusted family devices.** An admin marks a device (a kitchen tablet, a shared phone) as a family device; it gets a random token in an httpOnly cookie (`famos_device`, ~400 days, refreshed on use), and only the token's SHA-256 is stored (`core_devices`). The profile picker (`core.listProfiles`, access `trusted-device`) and PIN sign-in work **only** from family devices, so names are never shown and PINs can never be guessed from outside the home: a 4 to 6 digit PIN is a weak secret, usable inside the home only. Admins list and revoke devices; revoking stops the picker and PIN sign-in on that device immediately.
- Identity operations share the single SQLite connection and must never run inside a unit of work (transaction).
- **Extensions hold capabilities through people, not on their own.** What an extension's code may reach (tables, files, secrets, other extensions' actions, the network) is fixed by its manifest and enforced by its context (§6 "Isolation"); what a person may do through it is decided by capabilities. Both apply: an action an extension may call still checks the actor.
- Capabilities are checked by the action runner and the HTTP adapter (route `requires`), never by comparing role names. Unauthenticated callers of public routes are a system actor (`anonymous`) that holds no capability.
- Route access levels: `public`, `trusted-device` (signed-in member or family device; never a display), `signedIn` (never a display), or a capability id (members by role; displays only for the `view` capabilities they were granted).
- Exception to "every state change is an action": credential management (passwords, PINs) and device trust are security/transport concerns (they set cookies or call the identity adapter outside a transaction) and are dedicated routes instead.
- **Distrusted CA roots.** At start, before any outbound connection (every command, so backup uploads and extension installs too), the server removes the roots in `apps/server/src/tls.ts` from Node's default CA store, matched by SHA-256 fingerprint (never by name) on top of whatever `NODE_EXTRA_CA_CERTS` or the system adds. Today that is the four eMudhra emSign roots, whose intermediate CAs were compromised in October 2026; the list goes once Node ships its own blocklist and the image's Node has it.
- **Family displays.** A wall tablet or an old TV shows the day without anyone signing in on it, so a display is not a member and not a family device: it is paired by a code, like a TV app, and can only show what it was granted. A display is a `core_devices` row of kind `kiosk` with `display_capabilities` (JSON, view-level ids chosen at pairing) and `display_show_names`; its requests resolve to the actor `{ kind: 'display', deviceId, capabilities, showNames }`. A member session always wins over the device cookie. `access.can(display, c)` is true only when `c` was granted, has level `view`, its extension is on, and (for `core.members.view`) names are allowed; the action runner and `signedIn` / `trusted-device` routes refuse displays outright, so a display never runs an action, never opens the profile picker and never enables PIN sign-in (`trustedDevice` and the device middleware count `family` devices only). The device is verified on every request, so revoking takes effect at once; WebSocket upgrades use the same resolution, and the realtime hub closes a display's open socket on `core.device.changed` (the display reconnects and is checked again).
- **What a display shows** is Today's composition for its style and palette in **family mode**: no person, no "needs you", no actions, no sidebar and no bell, larger type, the photo, and ambient mode after idle. The composition is gated by the display's grants (without `calendar.view` no hero and no day; without `chores.view` no rings; without `ambient.weather` no weather; without `ambient.photos` no photo), and with "show names" off the day has no per-person structure. Today for a person (`/`) is the same composition with the person added.
- **Pairing** follows RFC 8628 and lives beside device trust (routes outside the action runner, `apps/server/src/http/devices.ts`): `POST /core/displays/pair` (public; 5 per 10 minutes per client address, an IPv6 address counting as its /64, and at most 3 codes open at once per address on top of the 100 family-wide, so a few addresses cannot take every slot) returns a 256-bit device code (only its hash is stored) and an unambiguous `XXXX-XXXX` user code valid for 10 minutes; the display polls `POST /core/displays/pair/poll` (every 5 s; faster answers `slow_down`); an admin (`core.devices.manage`) confirms the code with a name and the capabilities it may show (`POST /core/displays/confirm`). The next poll creates the device and returns its token exactly once, as the httpOnly `famos_device` cookie. Five wrong codes end all open pairings; a code is single-use. `GET /core/displays/me` tells the display page its name, grants, time zone and which extensions are off. The display fits Today to its one screen by measuring plans in a fixed order of priority (`apps/web/src/lib/today/fit-plan.ts`): what it was granted (its widgets, who is home) is given up last. It tells what it still had no room for with `GET /core/displays/me/fit?leftOut=…` (the display itself only; a read like all of a display's requests, since it describes the screen and changes no family data), which the device service keeps in memory like a last-seen time and Settings → Devices shows; the display says it again on every fit and refresh, so a restart forgets it briefly at most. Widgets are `display.widget` slot contributions (with `requires`, an optional `labelKey` naming them on Devices, and a `rows` prop that shortens them before one is left out) and the pills in the clock row are `display.status` contributions, both from extension `./web` entries, so a display shows only what its extensions offer and its grants allow.
- **Display content: the `ambient` extension.** It holds the content displays show and every outbound call a display causes (the weather), so switching it off in Settings → Family → Extensions stops them all. Capabilities: `ambient.photos` and `ambient.weather` (`view`, grantable to displays) and `ambient.manage` (`manage`). Settings (weather, timing) live in one row of `ambient_settings` (JSON validated by Zod; a `version` that moves on every change). **Photos** are images the family uploads to FamilyOS (no photo service is needed, so there is no upstream API to follow): the settings UI shrinks each picture in the browser (canvas, longest side 1920 px, JPEG) and posts it to `POST /ambient/photos` (multipart, `ambient.manage`, 5 MB). The route checks the magic bytes and reads type and size from the header (the declared type is not trusted; only JPEG, PNG and WebP), stores the file with `ctx.files` and records it through the `ambient.addPhoto` action in `ambient_photos` (file key, type, width, height, byte size, uploader, created at; at most 500). `ambient.deletePhoto` removes the row and enqueues a job that deletes the file (idempotent). `GET /ambient/library` lists them for the settings grid; `GET /ambient/photos` returns up to 200 shuffled ids and the timing for the slideshow; `GET /ambient/photos/{photoId}` streams the stored file (`ambient.photos`, `cache-control: private, max-age=3600`). Photos are not an AI area and carry no `ai` hints. **Weather**: `GET /ambient/weather` asks Open-Meteo (no key, CC-BY, attribution shown on the display) for coordinates rounded to two decimals, cached 30 minutes; weather off or no place is `{ enabled: false }`, not an error. Caches are per running server, never persisted, and dropped when the settings version changes. Routes that call out use `ctx.http` directly (a bounded read-through a person is waiting for); never inside a transaction. **Ambient mode** is a `display.ambient` slot contribution of this extension: it watches pointer, touch and key activity, covers the widgets after `idleMinutes`, and leaves on any interaction. The weather also appears as a `dashboard.card` on Today (an animated sky from the WMO code and `isDay` from Open-Meteo, the same picture without motion under `prefers-reduced-motion`), and the extension contributes a `setup.step` ("Where do you live?", a city search with Skip) so first-run setup can offer a place without knowing about weather.

## 14. Realtime and offline

- The server is the source of truth. After commit, the server broadcasts `{ entity, id }` invalidations over one WebSocket; clients refetch.
- The PWA caches the app shell (including the SPA fallback `index.html`, which is not in `$app/manifest`) and the last read models. Every page the server answers is the shell, so each successful navigation refreshes the cached copy: an offline start sees the packages and the import map the server last wrote.
- Extension packages are kept in a cache of their own (`famos-extensions`). After it opens, the app posts `CACHE_EXTENSIONS` with every file of the listed packages (source maps aside); the service worker fetches the missing ones and drops the files of packages no longer listed. Their addresses carry the package's digest, so `/extensions/*` is served from that cache first, and a page of an extension never opened online still opens offline.
- Service-worker updates are pushed: the app asks a waiting worker to `SKIP_WAITING` and reloads on `controllerchange`, because display tabs are never closed.
- Web Share Target posts multipart data to the app; the service worker intercepts it, stores it, and redirects to the share screen, which uploads it to the inbox. CRDTs are deliberately avoided; the offline command queue below replays writes after a disconnect.

### Idempotency keys and the offline queue

The app is used in shops with poor reception. The common moments are small (tick off an item, mark a task done), and actions already carry everything needed to replay them: an id, a Zod input and a server-side permission check. So the server stays the only source of truth and the browser queues a few declared actions; there is no sync engine, no CRDT and no local database.


- Any action call may carry an `Idempotency-Key` header (1-100 characters of `A-Za-z0-9_-`), from a member or from an AI agent; the system and displays send none. The key space is per principal: `idempotencyPrincipal(actor)` is `principalOf(actor)`, for an app `app:<id>`, for an app acting for a member `app:<id>/member:<id>`, and for an AI also the member it works for (`ai:mcp:<tokenId>/member:<id>`), so the same key from a member's browser and from an agent working for that member are two unrelated keys and a stored answer is only ever returned to the principal that made the call. The action runner stores `(principal, key) -> action, status, response` in `core_idempotency` **in the action's own transaction**, so a failed action leaves no key and can be retried. The primary key stays `(member_id, key)` (expand-only): `member_id` holds the member's id for a member and the principal itself for anyone else, and the `principal` column (null on rows from before it, which count as `member:<member_id>`) records who asked. A repeated key returns the stored answer without running anything (`Idempotent-Replayed: true`); the same key for another action is `422 idempotency_mismatch`. Validation, forbidden and not-found answers are stored too, so a replay gives the same answer. Keys are kept 7 days (a daily core job deletes older ones). This also protects online double taps. The MCP door reads the same `Idempotency-Key` header on a tool call that proposes a change (a repeat returns the first suggestion's answer instead of proposing again); a malformed key is refused as a tool error, and read tools ignore it.
- `defineAction({ offline: true })` marks actions the web app may queue: idempotent for a repeated key and still meaningful minutes later. Today: add and check shopping items, complete and reopen a task, mark a chore done and undo it. Every such action has a replay test (same key twice, replay after a conflicting change).
- The web app (`apps/web/src/lib/offline*.ts`) gives extensions `app.runAction(id, input, { offline, label })` and `app.waiting()` through `useApp()`. A call that gets no answer is stored in IndexedDB with its key and resolves `{ queued: true }`; pages show it optimistically with a "waiting to send" mark. The queue logic (`offline-queue.ts`) is pure, with injected storage, network and clock, and unit tested. Replay runs in creation order on `online`, at start and every 30 s; a 4xx answer (except 401, 408 and 429) moves the change to the "could not be saved" list, anything else keeps it queued with backoff and stops the run so order is kept. The queue belongs to the signed-in member and is cleared on sign-out. Inputs are never logged.
- The service worker keeps the last answer of a short allow-list of read routes (who I am, members, family settings, calendar occurrences, tasks, shopping lists and items, chores): network first, the stored copy when offline or after 5 s without an answer, marked with `x-famos-offline: 1` and a message to the page that shows "Offline — showing what was last seen". Nothing else under `/api/` is cached. The server marks all API answers, and everything `/mcp` answers, `no-store` for browsers and proxies; this private copy for the allow-list is the one deliberate exception, and it is deleted on sign-out.

## 15. API contract

- Routes are defined framework-neutrally with `defineRoute` from `@famos/sdk` (Zod params, query, body, response, roles). The server's HTTP adapter turns them, and every action, into `@hono/zod-openapi` routes, so extensions never import an HTTP framework and route handlers are testable without HTTP.
- The running server serves the whole document at `/api/openapi.json` to signed-in members only (it names the installed extensions); `pnpm gen` builds it without the server. `pnpm gen` (`main.ts openapi openapi.json --extensions ../../extensions`) writes it split by owner, and every part is committed; CI regenerates them and fails on any difference:
  - `apps/server/openapi.json` holds core's and the app's own routes (members, settings, AI, backups, push, Telegram, email, MCP) and `/actions/core.*`;
  - `extensions/<id>/openapi.json` holds an extension's routes (`/api/v1/<id>/…`) and its actions (`/actions/<id>.*`), and `extensions/<id>/src/web/api.gen.d.ts` its types (`openapi-typescript`, written by `apps/server/scripts/api-types.ts`).
- `packages/api-client` (types from `openapi-typescript`, runtime `openapi-fetch`) is the only way `web` and extensions talk to the server. Its `paths` are the host's only. `createApiClient<Own>()` adds an extension's own `paths`, so an extension's web code (`src/web/api.ts`) is typed against the host's routes and its own, and builds without the rest of the app or any other extension's types. Future native clients use the same documents.
- An extension's types are its `./api` export (types only, nothing at run time). Another extension reads them only for a declared dependency (`dependsOn` or `optional`; ambient reads the calendar, kitchen the lists, pets and vehicles the records) and passes them to its client: `createApiClient<paths & calendar>()`. dependency-cruiser fails an undeclared one, and forbids `apps/web` from importing any extension's API types or client: the app talks to the host's routes only.
- All routes are versioned under `/api/v1`, and every operation has a stable `operationId` (for example `shopping.addItem`).

### The public API (`/api/public/v1`)

The way programs outside the family (Home Assistant first) read and change data. It is a third surface beside the app's own `/api/v1` and `/mcp`, and a contract other people's code depends on, so it is small, explicit and only grows.

- **Nothing is public unless it is marked.** An extension marks an action with `expose: defineApi({ name, method, path, summary, … })` (several for one action: `complete` and `uncheck` are one action with a `fixed` field each) and a GET route with `expose` too. The registry (`apiOperations`, `packages/core/src/api-operations.ts`) refuses a name outside the extension's own, a path or method used twice, a read offered as an action, a change offered as a GET, a PUT without a version-checked `target`, an external action, a route that is not plain JSON or not behind a capability, and an input that is not an object. Marking says nothing about who may call: the action's `requires`, its approval policy and the app's mode still decide, in the runner. Never mark everything: expose what a program has a reason to use.
- **The shapes are the action's and the route's own Zod.** The request body is the action's input minus what the path or `fixed` sets and minus `omit` (fields only a model fills, such as a review `label`), with `describe` to word a field for programs (the action's descriptions are written for a model and name its tools). The answer is the action's output, or the `output` projection (`apiOutput(schema, project)`) that drops undo and internal fields (`before`, `merged`, `previousKey`) and writes the wire rules: instants are RFC 3339 with the family time zone's offset (`apiInstant`), all-day values are plain dates, ids are typed, an occurrence is `{ eventId, recurrenceId }` with `seriesId` and `recurrenceKey`, the install-time shopping list is named in the family language with `isDefault: true`. Public schemas are named (`.meta({ id })`) so generated clients have readable types; a name is never put on a schema that is also used nullable, since the document then marks the component itself nullable.
- **One grammar:** `GET` list and get, `POST` create and named commands (`…/complete`), `PATCH` some fields, `PUT` the whole record (and `If-Match` is required), `DELETE`. Reads are GET routes because validators need GET. Every answer is `{ items, next, timeZone }`, `{ item, timeZone }` or `{ status: 'applied' | 'drafted', …, timeZone }`; errors are `{ error: { code, message, fields?, reason?, capability?, currentVersion? } }` with a closed `code` enum, our own `fields` for a refused request (not Zod's tree), `feature_off` as a 404 of its own, `precondition_failed` as 412 and `gone` as 410.
- **The door** (`apps/server/src/http/public/`, mounted below `/api/public/v1` as its own Hono app, so its OpenAPI registry is separate) reads the bearer through `authenticateApp` and nothing else: cookies are never read, so there is no request forgery to defend from and no CSRF check, and CORS is not enabled. A wrong key counts against the client address's IPv6 /64 (the limiter is shared with `/mcp`); each app has its own request limit; `touch` records a use only after it passed both. The extension must be switched on (`feature_off` otherwise).
- **Behaviour on the log of §9.** A list answers with `ETag` = `collectionTag(extension, actor, window)` (the window is the query, the page, the family's zone and language and the hour, since views change without a write) and a matching `If-None-Match` is a 304 before the handler runs; one thing answers with `"v<version>"`, and every write answers with the version it left in the `ETag` header and in the body (read from the row after the write, since the action returned what it saw before its last update). `If-Match` becomes the runner's `ifMatch`. `Idempotency-Key` is the runner's, keyed by principal. A list route is cut into pages of up to 500 by the door (`limit`, an opaque `cursor`). `GET /changes?since=` is `kernel.changes.since` for the caller, limited to the extensions that offer operations and are on; without `since` it gives the current cursor. `GET /drafts/{id}` is readable only by the principal that proposed it (the app, or the member through it), anyone else sees `not_found`, and an applied draft's `result` goes through the same projection as an applied change. `GET /drafts?status=waiting` lists the pending and failed drafts as Quick add does for the caller (the core list's own rules: `mayDecide`, `isProposer`, expiry, a vanished subject): an app alone sees the drafts its principal proposed, an app acting for a member sees that member's view (the member's own and those the member may decide) provided the app's role holds `core.drafts.propose`; `canDecide` is always false. Its validator is the `core` collection tag over the visible ids and states, since drafts that expire or fail are not written through the log; draft events are in the log (entity `draft`) but `GET /changes` leaves them out, as `core` offers no operation.
- **Discovery** (`GET /`) says the API and FamilyOS versions, the family zone and language, the installed extensions with whether each is on, and the operations this caller may use now: a route when the caller holds its capability, an action by `runner.decisions(actor)` (`apply` or `draft`, never a refusal).
- **The document** `apps/server/public-openapi.json` is generated from the marked set only (`main.ts public-openapi`, part of `pnpm gen`), committed, checked by CI like the others and by `apps/server/test/public-api.test.ts`; the running server serves its own at `GET /api/public/v1/openapi.json` (for a bearer). `familyos-client` is generated from it.
- **The contract rule.** Within `v1` it is expand-only: operations, response fields, optional request fields, enum values of answers and error codes may be added; nothing is renamed, removed, made required or given a new meaning. A client ignores what it does not know. Anything else is `/api/public/v2`, announced in advance and run beside v1. Removing an operation from an extension is therefore a major-version act, and a field of a marked output is part of the contract the day it ships.

## 16. Deployment

- One multi-stage Docker image (amd64 + arm64) on `node:24-bookworm-slim` (Debian rather than Alpine, to avoid musl edge cases with native modules on a Raspberry Pi). The SPA is built and served by the Hono server on a single port, so installation is one `docker compose up`. There is no server-side rendering; a client-rendered SPA suits PWA and display use.
- `FAMOS_ROLES=api,worker` (default both) lets heavy installations run a separate worker container from the same image. SQLite's single writer still keeps everything on one host.
- Local AI services (Ollama) run in an optional compose profile or on another machine, reached by URL.
- The image ships the extension packages in `/app/extensions` (built with `@famos/pack` and gathered by `scripts/collect-extensions.mjs`), beside the server bundle in `/app/server`.
- The entry point is `node /app/server/famos.mjs`, the supervisor that starts the server again when it asks to (installing an extension, Restart); `node /app/server/main.mjs <command>` runs any command without it. Compose's `restart: unless-stopped` still covers a crash of the supervisor itself.
- Volume `/data` holds `famos.db`, `files/`, `backups/`, installed language and theme packs, and the generated secret (unless `FAMOS_SECRET` is set). `FAMOS_SECRET` seals provider keys, bot tokens, mail passwords, subscription URLs and backup passphrases; it is never inside a backup, so restoring on new hardware needs it too.
- HTTPS is required for PWA Share Target; docs cover Caddy and Tailscale.

## 17. Verification strategy

- **Extension tests**: in-memory SQLite with real migrations; actions and routes tested end to end.
- **Port contract suites** for queue, files and LLM; every adapter and fake must pass them.
- **Architecture tests**: dependency-cruiser rules in CI.
- **Migration tests**: empty DB → current; previous-release fixture DB → current; refuse to start on a newer DB.
- **Backup tests**: backup → restore into an empty volume → data and files are equal.
- **Pipeline tests**: AI SDK `MockLanguageModel` for deterministic extraction; kill the worker mid-job → restart → completes without duplicate drafts.
- **The model evals** (`pnpm --filter @famos/ext-inbox eval`, `@famos/ext-assistant`; not in CI, they call real models). They measure what a single pass cannot:
  - *Runs.* `FAMOS_EVAL_RUNS=<n>` (default 1) runs each case n times on each model. A model that misreads a message one time in three is not told apart from one that always gets it right by a single run, so the report gives each case's pass count out of n, each model's median pass rate over the runs, and the baseline records the pass counts. A case that passed every baseline run is newly failing only when it fails most of its runs. Answers are recorded from the first run only.
  - *Missed or harmful.* A failed check is *missed* when the card refused, skipped, left something out or showed it as unsure, so a person sees there is more to do; it is *harmful* when the card shows a wrong value as if it were certain, or acts on the wrong thing, so a person may approve a mistake. A case's checks say which (`failure` on the check; the helpers `has`, `none`, `total` and `flagged` set it from what was proposed and what was marked "check this"; a check with none counts as missed). The report prints both counts per model, and the gate is harmful = 0.
  - *State.* A case may start from a household that already holds things (`fixture`, in `extensions/inbox/eval/household.ts`): lessons with one name for two people, a moved lesson, class and plate codes, two shopping lists. A message that sounds alike is then judged on which of the things it reaches.
  - *Replay.* CI replays the recorded answers through the real pipeline with the fake model (`golden.test.ts`). A case with no recording yet is skipped there until a full run records it; the code of such a case is held by tests that read it with the answer a careful model gives (`sim-cases.test.ts`).
- **API drift**: regenerate `openapi.json`, `public-openapi.json`, the extensions' documents and their types → the working tree must stay clean.
- **E2E (Playwright)**: a small set of essential flows and security boundaries: setup → share → draft → approve → undo; sign-in with a password, a PIN only on a family device; a supervised member's change becomes an approval; a display reads only what it was granted and follows live changes over the WebSocket. Layout and timing are unit-tested or reviewed in the sweep, not gated by e2e.
- **Docker smoke**: `docker compose up` → `/health`; arm64 image builds; backup and restore inside the container.
