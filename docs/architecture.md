# FamilyOS Architecture

How FamilyOS is built and the rules that keep it that way, each with its reason. [AGENTS.md](../AGENTS.md) is the short checklist; this is the long form. A rule can change, but deliberately: the change updates this document in the same pull request.

The goal is a foundation that is **loosely coupled, yet small enough for a small team to carry**. Many choices follow what comparable open-source projects chose or later regretted (Immich, Home Assistant, Medusa, Backstage, Directus, n8n, Ghost, Karakeep, LibreChat, Tandoor, Mealie, Actual Budget, Paperless-ngx).

## 1. Design principles

1. **Seams first, implementations on demand.** Infrastructure likely to change (job queue, file storage, LLM provider, identity) sits behind a port. A second implementation is written only when there is a real need.
2. **Extensions never import each other.** They communicate only through actions, events and typed IDs.
3. **Zod is the single source of truth.** One schema drives request validation, OpenAPI, LLM structured output, draft-card forms and the tools offered to the assistant and to MCP clients.
4. **Expand-only changes.** Database schema, configuration and API only grow in minor releases. Breaking changes happen only in a major release, announced in advance.
5. **AI proposes, people decide.** No model changes family data on its own; every change it suggests is a draft a person approves (§8, §11).
6. **Region-neutral, language-neutral.** Nothing in the product assumes a country, a language or a household shape (§6, §13).

### Scope

- **One installation is one family.** No multi-tenant hosting.
- **SQLite is the only database** (§12).
- **Extensions are packages the family installs.** The image ships the always set (calendar, lists, Quick add, the assistant, the board, chores, records) and the offered ones; an extension released on its own (Home Assistant) is installed from a signed package. There is no sandbox for package code, so code loads only from the image (trusted by place) or signed by a key in `TRUST_ROOTS`, today only the project's release key (§6 "Packages and installation"). Language packs and theme packs are data, validated and rendered as data, so they can be installed at runtime as well (§6).
- **FamilyOS does not replace Home Assistant.** It shows what the family chose from it and switches only those things, through Home Assistant, for the people allowed to (a capability); family displays and the AI never switch anything. It calls only the services of a fixed table (on and off, open and close, lock and unlock, run a scene), so the token, which Home Assistant cannot limit, can do no more through FamilyOS than that.

Reasons for the less obvious choices:

- **Kysely, not an ORM, and no repository layer.** Kysely is typed and transparent, and its migrations are explicit code; auto-generated SQLite schema diffs can rebuild tables, risky under a compatibility promise. With SQLite the only database, repositories would add an interface and an implementation per aggregate for a swap that will not happen; tests run on in-memory SQLite with real migrations instead. Hand-written table types sit next to their migration, and a test compares them with the migrated schema.
- **No dependency-injection framework.** `apps/server` builds every adapter once into a typed `ctx` whose shape the SDK defines; extensions get it in `register(ctx)` and their action and job handlers, tests build one from `@famos/testing`. Wiring stays plain TypeScript, and swapping an adapter is one line.
- **OpenAPI and a types-only client** (§15), so native clients can generate their own SDK and generator upgrades touch almost nothing.
- **better-auth behind an `Identity` port**, its tables created by our own committed migrations (the SQL was generated once and reviewed; a test checks it still matches what better-auth expects). Its runtime schema check is off because it would run before our migrations on first start. better-auth needs an email per user, so a PIN-only profile gets a synthetic, non-routable address with email sign-in disabled. No passkeys: for a self-hosted app they need HTTPS and break when the instance's address changes.
- **i18next**: one mature library for the web app and the server (notifications, Telegram and email texts), loading catalogs at runtime without a CDN or a compile step.

### Dependency policy

- Exact versions only; the lockfile is committed.
- Renovate opens grouped update PRs; security updates (especially better-auth advisories) are merged promptly.
- Small utilities are our own code, not a dependency: the JSON-lines logger (`packages/adapters/src/runtime/logger.ts`), the RFC 9562 UUIDv7 generator (`uuidv7.ts`), Web Push encryption, and the few UI primitives that would otherwise need a headless-UI library (avatar, label, separator).
- No feature depends on a third-party server's API except those the family configures (an AI provider, Telegram, a mailbox, remote backup targets, calendar feeds, the weather). Integrations that track an upstream API with its own release schedule are not bundled.
- Prefer dependencies with a small surface and low churn (`openapi-typescript` over full SDK generators).
- pnpm 12 runs dependency install scripts only for packages listed under `allowBuilds` in `pnpm-workspace.yaml`.
- Tool telemetry is disabled in CI (`TURBO_TELEMETRY_DISABLED=1`, `DO_NOT_TRACK=1`); contributors can run `npx turbo telemetry disable`.
- Watch items: SvelteKit 3 is new (expect patch releases); Kysely is pre-1.0; Vite 8's Rolldown has an open nondeterministic crash on Linux CI (rolldown#10860): pin rolldown via `pnpm.overrides` if it appears; revisit TypeScript 7 when 7.1 ships its API, and `node:sqlite` when it reaches Stability 2.

### Layers and responsibilities

- **apps/server** is the composition root and the only place that knows concrete libraries. It reads configuration, builds adapters and the typed `ctx`, registers extensions and starts the HTTP server and/or worker (`FAMOS_ROLES`).
- **Loading extensions.** The server names no extension: at start it loads the packages it finds (`apps/server/src/extensions/`) and hands their definitions to the kernel. Shipped packages are found only beside the server bundle (`/app/server` → `/app/extensions` in the image, `apps/server/dist` → `dist/extensions` in a checkout); that place is what makes them trusted, so no setting moves the folder. Every package its `extensions.json` lists is read; the installed ones run, as do signed copies from the store (§6 "Packages and installation"). Before the first package is imported, a synchronous resolve hook (`module.registerHooks`) takes over imports from inside a package folder: the shared modules (`@famos/sdk`, `zod`, `kysely`, `@famos/time`) resolve to the server's own instances (`shared/modules.json`), `node:` modules and the package's own files resolve as usual, and any other import (another bare package, a file outside the folder) is refused with an error naming the package. A package is also refused when its `famos-package.json` was built for another platform (`built.sdk` must be the host's `SDK_VERSION` or an earlier patch of the same minor; the manifest's caret is checked too) or when its code carries a manifest other than the one the package describes. In development and tests `FAMOS_DEV_EXTENSIONS=<workspace>/extensions` loads the source instead (set by `pnpm dev`, `pnpm gen` and `apps/server/test/support/extensions.ts`, with a warning in the log); it is refused when `NODE_ENV=production`.
- **Inbound adapters** (HTTP routes, WebSocket, CLI, MCP, Telegram) only validate input, resolve the `Actor` (who is calling, with which role) and call core or an action. They hold no business rules.
- **@famos/core** is the kernel (the boxes above).
- **Extensions** own features: each owns its tables, actions, routes, events, migrations and UI contributions.
- **@famos/sdk** is the contract between extensions and the host (beside `ui`, `time` and `i18n`, §5): port interfaces, `defineExtension`, `defineAction`, ID and slot types.
- **Adapters** implement ports.

Each extension is **one package** with subpath exports:

| Subpath | Contents | Who may import it |
|---|---|---|
| `./contract` | Zod schemas, route definitions, action input/output, event payloads | anyone (other extensions, web, server) |
| `./server` | action handlers, queries, job handlers, migrations | its own package build (the server loads the built module at start, §3) |
| `./web` | Svelte pages, widgets, draft-card renderers | its own package build (loaded by the app at run time) |
| `./api` | types of its routes and actions (`src/web/api.gen.d.ts`) | the `./web` code of an extension whose manifest names it (§5) |

**Extension packages.** `famos-pack` (`@famos/pack`, each extension's `build` script) builds an extension into `extensions/<id>/dist/`:

| File | Contents |
|---|---|
| `server/index.mjs` | the server code as one ES module (with its source map) |
| `web/index.js`, `web/chunks/` | the `./web` entry as ES modules (Vite, components with their CSS injected); each page is its own chunk, and what the entry and its pages share is one `common` chunk |
| `web/styles.css` | the Tailwind utilities its web code uses, in the `ext` cascade layer |
| `messages/*.json` | the extension's catalogs, English and its own translations |
| `openapi.json` | its routes and actions |
| `LICENSE` | the extension's license, or the repository's |
| `famos-package.json` | `format`, `manifest` (its package.json `famos` field, unchanged), `name`, `license`, `built` (`sdk`: the platform version, `svelte`), `entries` (`server`, `web`, `css`), `labels` (each language's `feature_name` and `feature_description`, as `name` and `description`) and `files`: every other file with its SHA-256 |

The server bundle leaves out only what the host shares with every package (`SHARED_SERVER`: `@famos/sdk`, `zod`, `kysely`, `@famos/time`) and `node:` modules, and inlines the rest (other extensions' `./contract`, `@famos/i18n`, libraries); the build fails, from the metafile, on any other import left to the host, even a builtin without `node:` or a subpath such as `zod/mini`. The web bundle leaves out `SHARED_WEB`: the browser subpaths of Svelte and the script subpaths of `@famos/ui` (read from their `package.json` exports), `@famos/sdk`, `zod`, `@famos/time` and `@famos/api-client`, which the app hands over at run time (§6, Web side). Icons are not shared: each package keeps the ones it uses.

`SDK_VERSION` is the platform version packages are built against; `packages/pack/platform.json` records it with Svelte's minor, zod's major, Kysely's minor and the export names of `@famos/sdk`, `@famos/time`, `@famos/api-client` and every `@famos/ui` subpath; a test fails when these change without `SDK_VERSION` being raised (its minor when something a built package may use changed or went away, at least its patch when names were only added). `pnpm --filter @famos/pack platform:update` rewrites the file once the version is raised.

`extensions.json` at the root says which packages the image ships: `always` (calendar, lists, inbox, assistant, board, chores, records: records because home, pets and vehicles need it), `offered` (ambient, kitchen, pets, vehicles, home), `default` (the offered ones a fresh family gets) and `independent` (released on their own and not in the image: homeassistant, §6). `pnpm build` runs turbo, then `scripts/collect-extensions.mjs` copies each shipped package and `extensions.json` to `dist/extensions/`; an extension folder the file does not name, or a named one without a built package, fails the build. The server loads these packages at start (§3, Loading extensions).

## 5. Dependency rules (enforced in CI)

- `sdk` depends only on `zod` (and Kysely *types*).
- `extensions/*` may import `sdk`, `ui`, `time`, `i18n` and other extensions' `./contract` only; their `./web` code may also import `api-client` and the `./api` types of an extension their manifest depends on (server and contract code may not).
- `core` may import `sdk`; never adapters or `db`.
- `web` may import `api-client`, `ui`, `sdk`, `time` and `i18n`; it depends on no extension and loads their `./web` at run time (only its dev server compiles their source), never server code or an extension's `./api`.
- `adapters` and `db` are imported only by `apps/server`; extensions get the database as `ctx.db`, typed by the SDK.
- `apps/server` imports no extension: it loads them from packages at start (§3).

dependency-cruiser fails the build on a violation.

**Why the boundaries are hard.** Without them, features import each other's internals and share tables until nothing can change: Medusa had to isolate its modules and forbid cross-module foreign keys in a major rewrite, and Backstage rewrote its plugin system because wiring was unstructured. With them any extension can be removed, turned off or rewritten without touching the others, as long as its `./contract` stays compatible. The price is that some reads are indirect (an action or a typed id instead of a join).

## 6. Extension contract

An illustrative extension (the real ones live in `extensions/`):

```jsonc
// extensions/shopping/package.json (the manifest, see "Manifest" below)
{
  "name": "@famos/ext-shopping",
  "version": "1.2.0",
  "famos": {
    "id": "shopping",
    "version": "1.2.0",
    "sdk": "^0.5.0",
    "capabilities": ["shopping.view", "shopping.edit"]
  }
}
```

```ts
// extensions/shopping/src/server/index.ts
import pkg from '../../package.json' with { type: 'json' };
import en from '../messages/en.json' with { type: 'json' };
import tr from '../messages/tr.json' with { type: 'json' };

export default defineExtension({
  manifest: pkg.famos,
  messages: { en, tr },                         // its texts, under its id (see Language packs)
  capabilities: [shoppingView, shoppingEdit],   // defineCapability(...), see §13
  actions: [addItem, checkOff],                 // see below
  routes: shoppingRoutes,                       // defineRoute(...) definitions; served under /api/v1/shopping
  events: { 'shopping.item.added': ItemAdded },
  migrations,                                   // Kysely migrations; tables prefixed shopping_*
  register(ctx) {
    // subscribe to events, register job handlers
  },
});

// extensions/shopping/src/actions/add-item.ts
export const addItem = defineAction({
  id: 'shopping.addItem',
  title: 'Add item to shopping list',
  input: AddItemInput,                          // Zod
  output: ShoppingItem,
  requires: 'shopping.view',                    // who may call it at all
  approval: { unless: 'shopping.edit' },        // others propose a draft instead
  ai: { description: 'Add things to buy…' },    // the AI may propose it (as a draft)
  undo: (item) => ({ actionId: 'shopping.removeItem', input: { id: item.id } }),
  async run(uow, input) {                       // one SQLite transaction
    const db = uow.db.withTables<ShoppingTables>();  // hand-written table types
    /* … */
  },
});

// extensions/shopping/src/web/index.ts
export default defineWebExtension({
  manifest: pkg.famos,                      // the same id as the server side
  messages: en,                             // English; other languages come with the pack
  nav: [{ id: 'shopping.nav', path: '/shopping', labelKey: 'shopping:nav', placement: 'primary' }],
  pages: [{ id: 'shopping.page', path: '/shopping', component: () => import('./ShoppingPage.svelte') }],
  slots: [{ slot: 'dashboard.card', id: 'shopping.list', component: () => import('./ListCard.svelte') }],
  drafts: [addItemPresenter],               // how proposed addItem drafts look in Quick add
});
```

- **Typed IDs**: UUIDv7 strings with an entity prefix (`shop_item_…`), so an ID names its owning extension.
- **No cross-extension foreign keys.** Another extension's data is referenced by its typed ID.
- **Configuration** is a Zod schema with defaults; changes are expand-only.
- **Database access**: `ctx.db` / `uow.db` are `Kysely<object>`; an extension adds its tables with `db.withTables<MyTables>()`. The types only help; the scope ("Isolation") keeps it to its own tables. Members and family settings come from `ctx.family` / `uow.family`.
- **Turning off** (Settings → Family → Extensions, `core.setFeatureEnabled`): everything an extension owns is namespaced by its id, so core can stop it without its help. Its data stays; its routes and actions answer `feature_off`, its actions leave the AI catalog, its jobs stay queued, its event handlers do not run, its capabilities are inactive and the web app hides its nav, pages and cards (`me.disabledExtensions`). Core cannot be turned off. Web entries name themselves for that page with `labelKey`/`descriptionKey`.

### Isolation

Each extension gets its own `ExtensionContext`, built from its manifest (`kernel.contextFor(id)`); its routes, jobs, event handlers (`register`), search loaders and the host contracts it provides receive it. The action runner builds each action's unit of work for the action's owner, and `uow.run` gives the called action its own extension's view of the same transaction. Core and the infrastructure adapters are the host and see everything; their names (`RESERVED_NAMES`: core, app, auth, identity, ai, queue, email, backup, telegram, webpush) cannot be an extension's id, and no table prefix may overlap theirs.

| | What it may | Enforced by |
|---|---|---|
| `db` | Only tables, indexes and views named with its `tablePrefix`, in queries, raw SQL and DDL, its migrations included; never the schema itself (`sqlite_master`, `pragma`) | A Kysely plugin (`scopePlugin` in core) that reads each query before it runs and throws `forbidden`; raw SQL is matched word by word against the names in the schema |
| `files` | Write and delete under `<id>/`; read those and keys another extension granted it | A scoped file store over `core_file_grants`; `uow.files.grant(key, toExtension)` is for the owner only and commits with the change (the Inbox grants each paper it files to records before `records.attachDocument`) |
| `secrets` | Open only what it sealed | A key of its own (`ext:<id>`, derived from `FAMOS_SECRET`); values are `v2.…`, and any other value opens as nothing (a calendar subscription sealed under the old shared key asks for its address again) |
| `actions` | Run its own actions and those in `calls`; as an AI actor also what the AI is offered (`aiCatalog`, `aiReadTools`, `aiContextActions`, `aiMissingAreas`), which is how the Inbox and the assistant act for the AI | The action runner, on `ctx.actions.invoke` and `uow.run`; anything else is `forbidden` with an error naming `famos.calls` |
| `http` | Reach `network.hosts`; any public address with `userUrls`; the home network (`allowLocal`) only with `local`; the same for GET and POST | A wrapper around the guarded HTTP port |

The guarded `http` runs in job handlers, or in a route as a bounded read-through (the weather): a timeout of a few seconds (never more than 15 s), a size cap, the answer cached and a failure shown as `unavailable`, so a slow or hostile server cannot hold a page load up or flood it, and nothing is written outside. Anything slow, repeated, or that changes data outside goes through a job. `post` (a JSON body of at most 64 KB, same checks) is for jobs only, so it runs after the change that asked for it has committed, and it never follows a redirect, because a POST sent again may act twice.

Better-sqlite3 has no authorizer hook, so the scope lives in Kysely: the plugin only reads the query tree (rebuilding it would cost three times as much), checks a raw template's text once per call site, and adds about half a microsecond to a query of twenty. In-process code could still reach around it (a database driver, `withoutPlugins()`, which a test forbids in extensions), so the scope guards against mistakes and is a contract the host can check, not a sandbox: extensions are official and signed.

### Manifest

Every extension describes itself in the `famos` field of its package.json (`ExtensionManifestSchema`) and passes it to `defineExtension` and `defineWebExtension` (`manifest: pkg.famos`), so both sides share the id. It is static JSON, so the host knows what an extension is and reaches before running its code:

| Field | Meaning |
|---|---|
| `id` | Lowercase letters and digits; the namespace of everything it declares and its API path segment |
| `version` | Its own version, the same as the package's |
| `sdk` | The SDK versions it was built for, as a caret range (`^0.5.0`) |
| `dependsOn` | Extensions that must be present; their migrations run first |
| `optional` | Extensions it works with when present and does without otherwise (Quick add files papers on records only when records is there). They do not change the load order |
| `tablePrefix` | The prefix of its tables; `<id>_` when left out |
| `capabilities` | The ids of every capability its code declares |
| `calls` | The exact ids of other extensions' (or core's) actions its code runs with `uow.run` or `ctx.actions.invoke` |
| `provides` | Host contracts it implements: `shareTarget` (receives what members share from outside the app, §10) and `conversation` (answers what they ask from there, §11) |
| `network` | What it may reach outside: `hosts` it calls, `userUrls` (addresses a person typed), `local` (the home network, when a person allows it) |

The registry refuses to start unless the manifest agrees with the code: the same capabilities; no overlapping table prefixes; the host's `SDK_VERSION` satisfies `sdk` (an in-house caret check, read as npm reads it); every `calls` entry belongs to core or to an extension in `dependsOn` or `optional`, and is an action of it when that extension is present; `provides` lists exactly the contracts the code implements, and no contract has two providers. A missing `dependsOn` extension stops the start; a missing optional one does not. What the inbox and the assistant run for the AI are not `calls`: they come from the AI catalog and are allowed only for AI actors.

The SDK's error classes (`FamosError`, `LlmError`, `ExternalHttpError`) are checked with `isFamosError`, `isLlmError` and `isExternalHttpError`, which read a `Symbol.for` brand, never with `instanceof`: an extension built on its own can carry another copy of the SDK, whose classes are different objects. A test fails on `instanceof` for them.

### Web side

The web app is a shell that knows no extension, so one can be installed or left out without changing it. Everything it shows of one comes from the extension's `./web` entry (`defineWebExtension`), registered once with `registerWebExtension` (`apps/web/src/lib/contributions.svelte.ts`); the app reads the reactive registry (`contributions`), never a list of its own. `scripts/shell-agnostic.test.ts` fails when `apps/web` depends on an extension, or `apps/web/src` names an extension's API (`/api/v1/<id>`), capability (`can('<id>.…')`), events or pages, or has a route folder named after one.

**Loading at run time.** The app's build contains no extension; the browser imports each package's `web/` at start.

- **One instance of what is shared.** The `sharedModules()` Vite plugin (`@famos/pack/vite`, client build) makes each `SHARED_WEB` specifier an entry chunk of the app with its exports kept exactly (`preserveSignature: 'strict'`) and writes `_app/shared-modules.json` (specifier → chunk), so packages and the app run one Svelte runtime, one `@famos/ui/app` context, one zod and one Temporal. A shared chunk holds the whole module, since a package may use any export; zod is shared without its `locales`, which no extension needs. `@famos/ui` compiles with `css: 'injected'` (`dynamicCompileOptions` in `apps/web/vite.config.ts`), so a component brings its styles even when no app page uses it.
- **The shell.** `mountSpa` (`apps/server/src/http/static.ts`) writes into `<head>` the import map from `shared-modules.json` (inline, so the policy's script hashes cover it), the package list (`<script type="application/json" id="famos-extensions">`: `fingerprint`, and per package `id`, `version`, `entry`, `css`, `files`), a `modulepreload` per entry and, last, each package's stylesheet; `/` and `/index.html` are always this shell. Package files are served at `/extensions/<id>/<digest>/<path>` (`mountExtensionAssets`; digest of `famos-package.json`, which lists every file's hash): cached for good, `nosniff`, only listed `web/` files. `GET /api/v1/core/extensions/loaded` (`core.loadedExtensions`, public) says which extensions run and their fingerprint.
- **Importing.** `apps/web/src/lib/extensions.ts` imports every entry at once (`Promise.allSettled`, top-level await, so readers of `contributions` wait); one that fails is logged and left out. The dev server compiles workspace source with a lazy glob filtered by `core.loadedExtensions`, which keeps hot reload.
- **Styles.** A package's `web/styles.css` holds its utilities in the `ext` layer, built against the app's theme, base and type roles by reference. Every sheet declares `@layer properties, theme, base, components, ext, utilities;`, and the app writes every theme variable (`theme(static)`). Layers cannot order a variant against a base class held in two sheets (`hidden md:inline` where only the package has `md:inline`), so the app's Tailwind also scans the bundled extensions' web source; for a package built after the app such a variant can lose.

An entry contributes:

- **Navigation and pages**: `nav` (tabs, More, the settings list, with `order` placing a settings page among the app's own), `pages` served by the catch-all route (patterns with `:name`), `shortcut` (the key after `g`) and `share`: the one entry where things are shared with the family (Quick add), linked from Today through `app.share()` and given the `n` key. Settings pages an extension owns are its pages (Photos and weather is ambient's); memory is core's, so its page is in the app (`/settings/memory`, `core.memory.use`).
- **Slots**: typed contribution points (plain data plus a component loader): the app's (`dashboard.card`, `today.atmosphere`, `today.capture`, `today.head`, `nav.action`, `display.widget`, `display.status`, `display.ambient`, `setup.step`, `settings.display`) and those an extension owns, declared in its contract by adding to the global `FamosExtensionSlots` interface (`record.section` in records, `inbox.fileTarget` in inbox), so renderer and contributors share one type. It is a global, not an augmentation of `@famos/ui/slots`, because a checker that reaches `@famos/ui` through a link can see a copy of the module an augmentation misses.
- **Today**: `timeline` (the day's things; its `page` is where the day links), `today` facets and `blocks` (below).
- **Draft presenters** for its own actions (core's are the app's, `apps/web/src/lib/app-slots.ts`), and `messages`, its English catalog ("Language packs").

**Today facets** are what Today draws in its own shapes rather than as a card, so each style draws them its way: `perMember` (counts per person: chores as rings, bars, "2 left", a display's total), `memberStatus` (a few words beside each name, already in the reader's language, such as who is home; never coloured; several stand side by side; none with names off), `photo`, `weather` (the next hours, for a style that draws them) and `setupHint` (a first step of a new family; a `fresh` step also says whether the family is new). A style shows a facet only when a turned-on extension provides it and the viewer holds its `requires`. **Blocks** are what "What Today shows" lists: the app's own (clock, greeting, weather and photo when provided, the next thing, the day, where everyone is, Needs you, the next days, done today), extensions' `blocks` (placed by `order`: chores, meals), and every card; a card or facet names its block with `block`. Block ids are what people hide, so they never change.

`requires` is mandatory wherever a family display reads (timeline contributions, facets, `today.atmosphere`, `display.*`, cards with a glance): a display has a day when it holds the `requires` of any timeline contribution, and pairing offers exactly the capabilities these name. App services (translation, members, time zone, realtime events, toasts, `share()`) come from `useApp()` (`@famos/ui/app`, Svelte context under `Symbol.for('famos.app')`). Extensions reach Svelte, `@famos/ui` and `@famos/sdk` only as packages, Svelte a peer (`scripts/extension-externals.test.ts`), so their bundles use the app's.

### Packages and installation

Each extension is a built package (`@famos/pack`). The image carries every one in `/app/extensions`; `extensions.json` says which are `always` installed, `offered`, and installed by `default` for a new family (ambient, so Today has weather and photos from day one and setup offers the weather place). Its `independent` list names extensions released on their own (tag `ext-<id>-v<x.y.z>`, only on the official index) that the image does not carry; shipped ones carry the product's version. The family chooses in Settings → Family → Extensions (`apps/web/src/routes/settings/extensions`).

- **The installed set** is `core_settings.extensions` (`packages/core/src/extension-state.ts`): `installed`, `known` (every extension that ever ran, with its table prefix and last version), `failed`, `restartRequestedAt` and `loaded` (what the last start ran), read before the kernel is built (`apps/server/src/extensions/installed.ts`). With no stored state, a database with data gets the always set plus every shipped extension with migrations there (an upgrade keeps everything), an empty one the always set and the defaults, and workspace source (`FAMOS_DEV_EXTENSIONS`) everything; the first start stores the choice.
- **One broken package never stops the rest.** A package that cannot be read or imported, whose database holds migrations it lacks (a newer version made them) or whose new migrations sort before applied ones, is left out with the reason, as is one the registry refuses: `createKernel` takes the ids it may leave out (`refusable`, all but the always set), drops the culprit and whatever `dependsOn` it, and builds again (`kernel.refused`). A failing migration (`MigrationFailedError` names the scope) or `register` of an offered package is recorded in `failed` (per version, so it does not loop; reinstalling retries) and the server exits with code 75 to start without it. A failing always installed extension stops the server.
- **Installing** is `core.installExtension` (with what it `dependsOn`, which must be at hand), **uninstalling** `core.uninstallExtension` (refused for the always set and for one another installed extension needs); both load at the next start. An uninstalled extension's data (tables, files, jobs, drafts) stays and comes back with it: its drafts wait unseen (nothing could apply them), its jobs are not claimed, the migrator reports its scope as orphaned. `core.setFeatureEnabled` stays the switch while it runs. `core.listExtensions` gives each extension's status (`loaded`, `pending_install`, `pending_uninstall`, `refused`, `failed`, `available`; refused or failed with an English `reason` and `reasonCode`/`reasonParams` from `EXTENSION_PROBLEMS` for the page to translate, as `ExtensionRefusedError` and `failed` carry them), what its manifest reaches (shown before Install), labels and `nextVersion` (a newer version from a file, loading at the next start). All three need `core.extensions.manage` (critical) and a person: the runner never lets the AI run or propose an action that requires a critical capability, so no agent with an API token can, even an admin's. Packages come through `ExtensionPackagesPort` (`list`, `place`, `stage`/`staged`): shipped ones are in place; a signed file is placed in the store.
- **Restarting.** `core.restartServer` records `restartRequestedAt` and emits `core.restart.requested`; the API process shuts down gracefully with exit code 75, and one serving no API (`FAMOS_ROLES=worker`) checks the stored time every 30 s. The image's entry point, the supervisor (`apps/server/src/supervisor.ts`, built as `famos.mjs`), runs `main.mjs serve` as a child and restarts it on 75 (backing off from 1 s to 30 s while starts keep ending quickly), passes other exit codes through and forwards SIGTERM and SIGINT. `/health` carries `boot`, an id of the process's start, so the page that asked reloads when it changes; other apps, when their live connection returns, compare their loaded fingerprint with `core.loadedExtensions`: a display reloads, a member gets a notice with Reload.
- **Signed packages and the store.** A family can also install a package from a file or from the official index. A `.famext` is a gzip tar of a built package folder (`famos-package.json`, every file it lists, nothing else) plus `famos-package.sig`, `{ keyId, sig }`: an ed25519 signature over the exact bytes of `famos-package.json`, which lists every file's SHA-256, so one signature covers the package. `@famos/pack/famext` makes one (`pack`, `sign`, `generateSigningKey`, `loadSigningKey` from a key file or environment variable); packing checks the hashes and writes entries in a fixed order with a fixed time, so a build always packs to the same bytes.
  - **Checks** (`apps/server/src/packages/`, `node:crypto` and `zlib`, `tar` only as a parser): at most 20 MB compressed, 60 MB unpacked (gunzip stops at the limit, so a small archive cannot expand without bound) and 2000 files; regular files only (a link, device or other entry refuses the archive) with plain relative paths (no absolute path, `..`, `.`, empty segment, backslash or control character: refused, where tar would strip them with a warning); signed by a key in `TRUST_ROOTS`; every listed file present with its hash and none unlisted; then `parseManifest`, `reservedClash`, the SDK caret, the platform it was built for (`built.sdk`) and its entries among its files.
  - **Trust roots** (`apps/server/src/packages/trust.ts`) are `{ keyId, kind: 'official', publicKey }` entries; a key's id is the first 16 hex digits of the SHA-256 of its public key (SPKI DER), so a signature cannot name a key it was not made with. The list holds the release key (`3bab2b9c2b26fecd`), whose private half exists only as the release workflows' secret (docs/releasing.md); several keys may be listed, so a key can be replaced without stranding what it signed. Third-party keys could later be another `kind`, with their own consent and warning. No setting or environment variable adds a key; tests pass their own roots to the store.
  - **The store** is `<data>/extensions/<id>/<digest>/` (`digest`: first 32 hex digits of the SHA-256 of `famos-package.json`, also the web files' path), holding the signed files and signature. `core.uploadExtensionPackage` (`POST /api/v1/core/extensions/packages`, multipart, one file, 20 MB, `core.extensions.manage`, a person only) checks a file and stages it in `<data>/extensions/.staging/<digest>/`, answering what it is (id, version, the server's current version, labels, reach, dependencies, signer) or, refused, `details` with a group `reason` (`unsigned`, `too_large`, `incompatible`, `invalid`; `older` as a conflict), a stable `code` and its values (`untrusted_key` with `keyId`, `file_mismatch` with `path`, `sdk` with `needs` and `has`, …), which the Extensions page (**Add from a file**) translates; the English message is for the log. Nothing is installed until `core.installExtension { staged: digest }`, which checks the staged copy again, moves it into the store and adds the id (with its `dependsOn`). Folders are written beside their target and renamed into place, so a half-written copy is never found.
  - **At every start** each stored copy is checked again (signature, files, links, platform) before its code is imported; a failing one is left out with a warning, and an installed extension with no other copy is refused, never the host. The highest version among shipped and stored copies runs; a shipped copy wins a tie (trusted by where it is), so a newer image replaces an older stored copy, and of two stored copies of one version the later placed wins. A stored copy of an always installed extension keeps `always`. Uploading an older version than the server has is refused (`conflict`, reason `older`); the shipped version installs without a file step. After a start the store keeps per extension the running copy and the newest other one (a display on the previous version can still fetch its files), and removes the rest and uploads not installed within a day.
- **The official index.** Releases publish on GitHub Pages: `https://onurceri.github.io/family-os/extensions/index.json`, signed by the release key in `index.json.sig` (`{ keyId, sig }` over its exact bytes), listing `{ format: 1, issuedAt, extensions: [{ id, version, sdk, url, sha256, size, labels, reach? }] }`. `reach` (`{ network: { hosts, userUrls, local }, capabilities: <count>, dependsOn }`, from the package's manifest, signed) is shown before Download, which is refused with `reach_changed` when the package's manifest differs; an entry without it is accepted. Each `url` is relative to the index (`<id>/<id>-<version>.famext`, on Pages, since release asset addresses redirect to another host). The server reads the index **only when an admin presses Look for more**, never on a schedule or at start, so a family that never asks makes no call. `core.findExtensions` enqueues `core.fetchExtensionIndex`, whose `ExtensionPackagesPort.findPackages` (`apps/server/src/packages/official.ts`) uses plain `fetch` to that fixed address (not `ctx.http`: it is the project's own host, not one a person typed): https only, a redirect refused, the index at most 1 MB and its signature 4 KB counted as they arrive, 20 s each. The signature must be by a `TRUST_ROOTS` key; an entry off the index's own host is left out. `FAMOS_EXTENSION_INDEX_URL` (https only) moves the address for tests; the same roots check it, so it adds no source of code. `issuedAt` (epoch ms, signed) orders indexes: the newest accepted is kept in `core_settings.extension_index` (`newestIssuedAt`), and an older index (`index_older`), one dated over a day ahead (`index_future`) or an undated one after a dated one is refused, so an old signed index cannot roll a family back. The listing is kept in `core_settings.extension_index`; `core.getFoundExtensions` answers the newest version of each id whose SDK caret this server satisfies and that is newer than what it has. `core.downloadExtension` enqueues `core.fetchExtensionPackage` (lane `long`): the file is downloaded (2.5 min), its size and SHA-256 checked against the index (`mismatch`), then staged like an upload, so every file check runs again; the admin installs it with `core.installExtension { staged }`. Failures are recorded with `details.reason` (`unreachable`, `unsigned`, `invalid`, `index_older`, `index_future`, `mismatch`, `reach_changed`, `gone`, or a package refusal) and never retried by themselves. All three need `core.extensions.manage` and a person.
- **The command line**: `famos extensions list`, `famos extensions install <id…>`, `<file.famext…>` or `--all-offered`, `famos extensions uninstall <id>`, run as the `cli` system actor on the same data; a running server loads the change at its next start.
- **Purging** an uninstalled extension's data is `famos extensions purge <id> [--yes]`, command line only: it is irreversible, so it is no action and no route, and nothing in the app or an agent can reach it. It refuses an always installed, installed or still loaded id (in its own process, or by the last start, `state.loaded`, which that server runs until it restarts, whatever its roles or address, so no network call is needed), one with no `known[id].tablePrefix` (it never ran here), and a prefix overlapping the host's (`RESERVED_TABLE_PREFIXES`, `sqlite_`) or another known or available extension's: the prefix is all that names the tables of an extension whose code may be gone, so it must name nothing else. It then writes a backup (stopping if that fails) and removes, in one transaction with foreign keys off and checked before the commit: the tables, views, indexes and triggers with the prefix; the scope's `_migrations` rows (a later install migrates from nothing); its jobs (`<id>.*`, and `core.notify` of its kinds); what core keeps about it, which core removes itself (`forgetExtension`, so a new core table or setting naming extensions is cleaned where it is defined): its drafts, notifications, idempotency answers and search entries; file grants to and of it; its keys in role overrides, notification preferences, display capabilities (devices and pairings), features, AI areas, AI switches, auto-approval, the search index state, Today's hidden blocks, and `known`/`failed`. Its files (`files/<id>/`) go after the commit. The audit log and AI usage are history and stay, as do API token handles (ids only) and a stored package of it (code, not data).

### Records and record pages

Vehicles, pets and the home each need recurring duties with reminders, papers, and a page showing both; three copies would drift apart, and one extension for all three would stop the family turning one off. So `records` owns what they share: **obligations** (a duty with a due date, an optional repeat of N months or years, a lead time, an assignee) and **documents** (links to files that arrived through the Inbox). It knows a record only by its typed id (`vehicle_…`), its kind (`vehicle`) and a name and page path the owner keeps current with `records.renameRecord`; it never reads a domain table. Domains call its actions (`records.addObligation`, `completeObligation`, `archiveForRecord`, …) with `uow.run` inside their own. A nested run is decided like any call (refused as `nested_needs_approval` when it would only be a suggestion), but records' actions are `nested: { governedBy: 'owner' }`: run by the domain that owns the record (its `recordIds`), they are covered by the domain action's permission and approval.

- **Domains own their data**: their own tables and fields, and presets (a neutral name and a suggested interval) as data in their contract. An archived or removed record archives its obligations through `records.archiveForRecord`; `records` hides ids it no longer knows.
- **Dates.** Obligations are by calendar date only: odometers and other units differ by country and vehicle, and a date is what families act on. A repeat is stored as an RFC 5545 rule (`FREQ=MONTHLY|YEARLY;INTERVAL=n`) but expanded from the first due date with month-end clamping (31 January → 28 February → 31 March; 29 February → 28 February → 29 February), so a duty "on the 31st" never skips short months. Completing records a history entry and moves the due date to the first occurrence after today (or after the due date when done early); a one-off is archived as done.
- **Reminders.** Kind `records.obligationDue`. Jobs `records.remind` are planned in every change's transaction at `due − lead days` and on the due date, at the family's `reminderTime`; a job carries the due date and `updated_at` it was planned for and does nothing when they no longer match. Recipients: the assignee, else everyone holding the obligation's `audience` capability (a domain passes its own, such as `vehicles.view`; default `records.view`). **Areas.** The same `audience` decides who reads a duty everywhere: the routes (`listObligations`, `getObligationHistory`, `listUpcoming`) and actions answer each caller only with duties whose capability it holds (an unknown one counts as `records.view`), whatever kind of caller it is. A paper keeps no area of its own: it follows its record's duties (a non-default `audience` among them, else among the duties of its record kind, else `records.view`), so `listDocuments` and `getDocumentFile` answer `not_found` for a paper of an area the caller may not see, search indexes the paper under that capability, and `records.document.changed` carries it as its audience.
- **AI.** `records.addObligation` and `records.completeObligation` carry `ai` hints; the model names records and obligations by handle ("AI record context"). `completeObligation` also takes `nextDueDate` (a renewed policy runs until…), which becomes a repeating duty's new anchor; asking for the date it already has does nothing, so approving twice is harmless. `label` is a reviewer-only copy of the entry's name, never stored.
- **Slots.** `setup.step` is an optional first-run step (`{ done }`), rendered one at a time once the founder's account exists and they are signed in, unfiltered by `requires` (capabilities are not loaded yet; the founder holds all); it must offer Skip and never block. A domain owns the record page and renders `<Slot name="record.section" props={{ recordId, recordKind, recordName, recordUrl, audience, presets }} />` (declared in the records contract); without `contributions` the slot asks the app (`useApp().slots(name)`) for the enabled ones the viewer may see. `records` contributes "What needs doing" and "Papers"; `presets` (`ObligationPreset[]`: id, title key, `every`, lead days) fill "what usually needs doing". `records` also contributes the Today card "Coming up" (30 days, across records, with name and page).
- **Filing without the AI.** Filing keeps a paper away from the model, for areas the AI may not read: the AI is never asked to sort shared items into areas, because sorting means reading them. A person files an item's files on a record: `inbox.createItem` with `fileToRecordId`/`fileToRecordKind` (and optionally a label), or `inbox.fileItem` for an existing item. Both call `records.attachDocument` through `uow.run` in the same transaction, so a refusal (no `records.edit`, a missing file, records off) rolls everything back. A filed item has status `filed`, no `inbox.process` job is enqueued, and a queued one finds the status and stops. The picker is the `inbox.fileTarget` slot (inbox contract), to which domains contribute their records; with none, "Add to…" is hidden. The file stays at `inbox/<item>/<n>`; `records.getDocumentFile` serves only keys linked to a record, sandboxed like the Inbox file route.

### Calendar feeds

Families live with calendars they do not own (the school year, public holidays, a club's fixtures) and want the family calendar on their phones. Both directions use ICS feeds, which need no account linking or OAuth; two-way CalDAV would need a sync engine with conflict handling and is not built.

- **Out: a secret feed** at `/api/v1/calendar/feed/<token>.ics`, of the whole family or one member's events (plus whole-family events). The long random token is the credential (only its hash is stored); the feed is read-only, has no session and carries notes only when its creator chooses. It acts for the member who made it, judged as they are today: each fetch resolves the owner with `credentialOwner` (active, holding `calendar.view`, or `calendar.manage` for a whole-family feed) and answers 404 otherwise. Only a password sign-in creates one (`assertFullSignIn`); the calendar ends its feeds through the `endCredentials` hook (§11).
- **In: read-only subscriptions** (`https:`, or `webcal:` meaning `https:`), refreshed by a job with conditional requests through the guarded HTTP port (size cap, timeout, no redirects across hosts, private addresses only when the admin allows them for that subscription, for a NAS). The URL is a credential (Google and iCloud secret addresses), sealed with `FAMOS_SECRET` and never returned in full. Events are parsed with `ical.js` into their own table keyed by subscription, UID and RECURRENCE-ID; a refresh replaces a subscription's events in one transaction, so a broken feed can be removed without side effects. They use the same recurrence code, cannot be edited, and do not remind unless the subscription says so.

### The family board

Families need a place for short, lasting notes everyone sees (the fridge door, a kitchen whiteboard), and on wall displays a board works where a chat would not. `board` holds short notes (up to 500 characters, an optional photo, an optional end day after which the note leaves, pinning, "seen" per person) on its own page, as a Today block and on displays. No replies, threads or chat: families already have a chat. Capabilities: `board.view`, `board.post` (write, edit and remove one's own notes), `board.manage` (remove anyone's note, pin). Its look comes from theme tokens; note colours are papers the author picks, never member colours. A read action with `ai` hints lets the assistant read the board, and the AI may propose a note like any other action.

### AI record context

The model can only point at records it was told about, by the household's names. So an extension may declare `defineExtension({ ai: { context: 'vehicles.aiContext' } })`: a **read-only** action of its own (the registry checks) returning `{ kind, label, items: [{ id, label, details?, url? }] }` (`AiContextSchema`); an area with several kinds of record lists one action per kind (`context: ['home.aiContext', 'home.aiContextItems']`). Quick add:

1. takes the areas of the mention kinds offered for the reading ("Mention kinds", already filtered like the AI catalog), so an area off for the AI, or local-only with a remote model, contributes nothing;
2. invokes each context action **as the AI actor** (`ctx.actions.invoke(id, {}, aiActor)`, local when the model is; `ctx.actions.aiContextActions()` lists those of turned-on extensions). Access control refuses a locked area even here, and the AI actor holds only `view` capabilities; at most 50 items per context action are used (`MAX_KNOWN`), those the message names first;
3. prints labels and details under "Known names" in the system prompt, never an id or a handle; each kind says which it points at (`knownFrom`);
4. keeps the items with their ids for the resolvers (`MentionContext.records`, `ctx.record(words, kinds)`): a resolver only emits an id it matched among them or read from its own tables, so a suggestion cannot name an unlisted record, and the record's kind, name and page come from the item, not the model.

Contexts: `calendar` (tags in use, and the family's own editable events of the next 28 days, at most 100; subscribed calendars left out), `vehicles` (name, plate, make, model, year, fuel; no VIN or notes), `pets` (name, species, breed; no chip number, vet or notes), `home` (homes by name and tenure; things by name, brand, model, room, home and warranty end; no address, serial or account numbers or notes; services not shared), `lists` (open shopping items with their list and open tasks with their due date, so "bought" or "done" can tick one off; at most 200 each) and `records` (open obligations: "Car insurance (Family car)", due date, repeat). `records.aiContext` lists an obligation to an AI actor only if it holds the obligation's `audience` capability (unknown counts as `records.view`); since a locked area's capabilities are removed from AI actors, its duties, record names and dates never reach a prompt even while `records` is open. People are not filtered. The context is prompt data only; changes still become drafts a person approves.

### Mention kinds: what the model may read for an extension

Models read language well and do the system's work (ids, dates from a table, which record is meant, which of 25 action schemas fits) badly and inconsistently. So the model reads a message into a small flat list of **mentions**, the same whatever is installed (`UnderstandingSchema` in `@famos/sdk`: a `kind` and shared slots such as `title`, `target`, `about`, `people`, `date` as a day reference, `time`), and code turns each into a suggestion or a refusal. An extension declares what may be read for it with `defineExtension({ ai: { kinds: [defineMentionKind({ … })] } })`:

- `id` (`<extension>.<kind>`), an English `describe`, the `slots` it uses with a line each, `variants` when it uses the `variant` slot, and English `examples` (`{ text, mentions, why? }`), region-neutral with days in words; every example mention carries its `quote` (the words it rests on), so the model learns to copy them;
- `actions`: the AI-proposable actions its resolver may suggest, its own or ones it `calls`;
- `knownFrom`: its own `ai.context` actions whose labels the model is shown as known names;
- `limit`: at most this many mentions of the kind are resolved per reading (default and maximum `MENTION_LIMIT`, 16);
- `handsOff`: kinds of other extensions (in `dependsOn` or `optional`) its resolver may hand a mention to when it states that kind's thing (a treatment still to come is an appointment, `calendar.event`);
- `resolve(ctx, mentions)`: returns per group of mentions `{ propose: { actionId, input, subject, targetTitle?, uncertain?, decided?, from } }`, `{ refuse: { reason, subject, from } }` with `reason` from `REFUSAL_REASONS` (`already`, `unknown`, `other_day`, `ambiguous`, `incomplete`, `not_allowed`, `instruction`), or `{ handOff: { kind, mention, from } }`, resolved once by that kind when it is offered and refused `incomplete` otherwise.

The registry refuses (`mentionKindProblems`) a kind not named for its extension, a duplicate id, a slot it does not know or describe, variants without the `variant` slot or the reverse, an action neither its own nor in `calls`, or read-only, or without `ai` hints, `knownFrom` that is not one of its context actions, and an example that does not strictly parse as a mention, names a kind the extension lacks, or fills a slot its kind does not use.

Quick add (§10) is the reader and never names a kind or an action. `ctx.actions.aiKinds({ local, actor })` lists the kinds offered for a reading: those of turned-on extensions whose area is open to the AI (local-only only for a local model) and whose actions are all in `aiCatalog` with the same options, so a kind disappears with any action it needs. `ctx.actions.resolveMentions(kind, mentions, env, actor)` runs a resolver for an AI actor only, while the kind is offered to it (`forbidden` otherwise); `env` is the reading (`text`, `sharer`, and the household `records` read as the AI actor). The resolver gets a `MentionContext`: its own tables **read-only** (a plugin refuses anything but a select), the family's region formats, and helpers bound to the reading (`day` via `resolveDay` with the date words of every installed language, `time`, `people` via `resolvePeople`, `target` and `record` via `findTarget`, checked against the shared text).

What a resolver returns is held to its mentions: each mention backs exactly one resolution, so mentions may be merged (shopping items into one list change) but never multiplied. A resolution naming no mention, one not given or one already held is dropped and logged; unheld mentions and those past `limit` are refused `incomplete`; a suggestion of an action the kind does not name is refused; a resolver that throws refuses all its mentions. So a reading never yields more suggestions than mentions, however the shared text tries, and what is proposed still goes through the runner as the AI actor and becomes a draft.

### Restrictive capability defaults

Every built-in role holds a `view` capability by default, right for calendars and lists and wrong for money, health or other private records. An extension may set `defaults` on a capability only to **remove** grants its level gives: each role's value is `false` or the level's own (`assertRestrictiveDefaults`, in `defineExtension` and again in the registry). It can never add a grant or declare a critical capability. `defaultGrant` alone reads the defaults, for built-in roles and for custom roles, which take their base's default unless overridden: for a `money.view` limited to Admin and Member, a custom role based on Member keeps it, one based on Supervised lacks it until the family grants it. No shipped extension needs this; Home Assistant's `homeassistant.control` (released on its own) starts with admins only, since a lock or garage door may be among what it switches.

### Region-neutral by default

FamilyOS is for families anywhere, so nothing is shaped by one country. Presets, defaults, enums, AI guidance, examples (in schema descriptions, prompts, guides and tests) and seed data make sense everywhere: presets have neutral names ("Home insurance", "Vehicle inspection", "Vaccination") and only *suggest* an interval, which the person sets; nothing is described as required by law, because legal rules belong to the family; the container's default time zone is UTC and the family's comes from the browser at setup. A test fails on non-ASCII letters in code strings, which catches most region- and language-specific words.

### Language and format locale

Language is not region: an English-speaking family in Berlin wants English words with 24-hour times and Monday weeks. So there are two settings. `locale` (a BCP 47 code with a language pack; `en` always) is the **language**: words (translations, the AI's answer language, day and month names). `formatLocale` (a tag such as `en-GB`) is the **region format**: date order and number and money marks, with `weekStart` (ISO 1 to 7), `hourCycle` (`h12`/`h23`) and `temperatureUnit` beside it, and `reminderTime` (`HH:MM`, 09:00 by default), the local time a reminder goes out for something with a day but no time (chores, duties, tasks without a time, all-day events). A tag carries a language too, so `sl-SI` alone would write "čet., 22. okt." for an English reader. Dates and times therefore use the **date locale**, `dateLocale(language, formatLocale, hourCycle)` in `@famos/time`: the reader's language with the format locale's region where `Intl` has that pair (English with `sl-SI` is `en-SI`: "Thu, 22 Oct", 22/10/2026), else the language alone (Turkish with `en-US` stays Turkish, since words of a language the reader did not choose are worse than another order), plus the hour cycle and the tag's calendar and digits. Numbers and money have no words and use `formatLocale` itself.

They live in `FamilySettings` (`ctx.family` / `uow.family`; in UIs `useApp()`: `dateLocale()`, `formatLocale()`, `weekStart()`, `hourCycle()`, `temperatureUnit()`); presenters and Today's format objects carry both `dateLocale` and `formatLocale`. On the server the reader is a person: a notification names a date or time as a `{ date }`, `{ time }` or `{ at }` parameter, written out per recipient when delivered or listed; Telegram writes dates in the linked member's language. Never pass `app.locale()` or `getLocale()` to `Intl`, `formatDate` or the money helpers, nor the format locale to a date or time formatter; `scripts/region-formats.test.ts` fails on either. Derivations from a tag (`defaultWeekStart`, `defaultHourCycle`, `numericDateOrder`, …) and `regionFormats()` (the regions `Intl` knows, offered in Settings) live in `@famos/time`. Defaults come from the browser at setup (its tag, `Intl.Locale` week info, `Intl.DateTimeFormat().resolvedOptions()`) and can be changed in Settings. Week views, repeat pickers and the prompts' date table start the week at `weekStart`, weather uses the chosen unit, and AI prompts state the date order and hour cycle, so the model knows whether "03/04" is 3 April or 4 March. Changing the language never changes the region formats.

### Language packs

Adding a language must need no code change, so English is the only language the app's code knows (`apps/web/src/messages/en.json`). Every other is a **pack**: `languages/<code>/` with `manifest.json` and one catalog per namespace (`app.json`, and `<extension id>.json` for an extension it translates). Turkish is bundled; the image copies `languages/` to `/app/languages` (`check-dockerfile` enforces it). Installed packs live in `<data>/languages/<code>/`, override a bundled pack of the same code (newer translations without a release), and are backed up (`languages/` in the tar). A pack is text, rendered as text everywhere, never HTML, which is why it is safe to install at runtime when code is not.

**Catalogs register themselves.** An extension keeps its texts in `src/messages/<code>.json`: `en.json` with every key, and the translations it ships (`tr.json`), passed as `defineExtension({ messages: { en, tr } })` and, English only, `defineWebExtension({ manifest: pkg.famos, messages: en })`; the namespace is the manifest's id (`app` is reserved). The host never names an extension's catalog: the server builds its English from the loaded extensions (`catalogsOf` in `apps/server/src/i18n.ts`), the web app in `registerWebExtension`. Key by key a language shows the **pack's string, then the extension's own translation, then English**, so a bundled pack holds only `app.json`, an extension ships its own translations, and a pack can still correct or add any extension's strings. A language is offered only when a pack exists; an extension's translation of a language without one waits.

- **Words code must recognize** (command names, weekdays, units, keywords) are comma-separated catalog strings, read with `ctx.vocabulary(key)` on the server (all installed languages) or `t(key)` in the UI; the Telegram share command accepts its English name and every pack's.
- **`@famos/i18n`** holds the format and rules, with no file access: `PackManifestSchema` (codes validated with `Intl.getCanonicalLocales`), `validatePack` against the installed English (unknown keys reported and ignored; a missing namespace only lowers coverage, one of an uninstalled extension is left out silently; a string whose `{{placeholders}}` differ from English is dropped; 2 MB per pack, 4 KB per string, plural forms of the language's CLDR categories), `withOwnTranslations` (lays a pack over the extensions' translations of its language, checked the same way), `coverage`, `negotiateLocale`, `satisfiesRange` for the `famos` range, and `createI18n`/`addCatalogs` with English as `fallbackLng`. `@famos/i18n/node` reads and writes pack folders.
- **The registry** (`apps/server/src/languages.ts`, on the pack registry `pack-registry.ts` that themes share) loads bundled then installed packs at start and on every install or removal, each over the loaded extensions' translations of its language; a broken pack is skipped and logged. Coverage and served catalogs are of the combination the family sees. Core sees it only through `LanguagePort` (`KernelOptions.languages`; without one English is listed and any well-formed code accepted, as in tests). `createTranslate(registry)` rebuilds its i18next instance on change and renders notification, Telegram, email and push texts; `kernel.translate`, `ctx.translate` and `uow.translate` expose it.
- **Codes are validated against the registry, not an enum**: family `locale`, a member's `locale`, `core.setMyLanguage` and setup refuse a code without a pack (`languages.assertKnown`). Removing an installed pack moves the family back to English and clears members who used it.
- **Routes and actions** (core): `core.listLanguages` and `core.getLanguageCatalogs` are public (setup and sign-in need them; catalogs are JSON text with an `ETag` of the pack version; English is not served). State changes are actions needing `core.settings.manage`: `core.installLanguagePack` (validates, writes the folder through the port, an idempotent write and its one effect outside the database, and records it in `core_settings.languages`), `core.removeLanguagePack`, and `core.installLanguagePackFromUrl`, which only enqueues `core.fetchLanguagePack` (guarded HTTP is for jobs), progress in `core_settings.languages.fetch`. `core.setMyLanguage` lets any member choose their own.
- **The web app** bundles English only, loads the chosen pack on demand (cached by version in `localStorage` for offline starts), sets `<html lang dir>` and follows `core.family.changed` and `core.languages.changed`. Signed out, the language is the device's choice or the browser's best match; signed in, the member's `locale`, else the family's. Setup starts with the language choice, which becomes the family's. Notifications and the assistant follow the member's language, displays the family's.
- **Prompts** name the language with `Intl.DisplayNames` (`languageName`), never a map. `scripts/language-branches.test.ts` fails on `=== 'tr'`-style comparisons and hard-coded locale lists outside tests and `languages/`.
- **Tools**: `pnpm lang:template <code>`, `pnpm lang:check <dir>` for a pack or an extension folder ([the guide](guide/languages.md)). CI requires each bundled pack to hold only `app.json` and each bundled extension to ship each bundled language, all valid and complete, so every bundled language is 100% complete as shown (`packages/i18n/test`).

### Appearance: styles and palettes

Appearance is two independent choices, and any style works with any palette:

- A **style** is code the app ships: how Today and the family display are composed, the type ramp (clock, countdown, big numbers, hero title, date, sentence, caps labels) and the default font per slot (`display`, `serif`, `body`). `@famos/ui` bundles three in `STYLES`: `broadsheet` (the default), `lanes` and `wall`. Styles are reviewed code added at build time; none is installable, because an arrangement needs components, and code from outside cannot be trusted.
- A **palette** is a theme pack: data only (below). It colours everything, may fill the font slots, and never arranges anything.

Other pages keep the design system's templates and take only the style's type ramp, fonts and accent, through the role classes in `packages/ui/src/type.css`. Navigation is not a style's. The style is set on the document (`data-style`) before first paint, like the palette, so the default never flashes. It is chosen like the palette, per family, member and display (`core.setFamilyStyle`, `core.setMyStyle`, `core.setDisplayStyle`); `GET /core/appearance` returns it beside the resolved theme. First match wins: the display's style, the member's, the family's, the preferred style of the resolved pack's manifest, `broadsheet`. The type ramp is deliberately not a token: sizes stay in a style's code, so a pack can never make text unreadable, hide a control or move anything.

**`accent`** is the one saturated surface a page may have: the next thing (the hero on Today, the calendar's next event) and nothing else. `on-accent` on `accent` must reach 4.5:1; `accent` is never text and never the only marker of "next" (the card also carries its time and label). Member colours mark people only: avatars, rings, rules, bars and a light tint behind `ink` text, never a surface, text or the hero; semantic colours are never used for people.

### Theme packs

The look is data, like words. A **theme pack** (a palette) is `themes/<id>/` with `manifest.json`, `tokens.json` (day and night values of the known tokens, `radius`, `font`) and optional `.woff2` files. Bundled: `themes/ev-isigi` (the default, the values of `packages/ui/src/theme.css`), `coast`, `forest`, `plum`, `paper` and `high-contrast`; the image copies the folder to `/app/themes` (`check-dockerfile` enforces it). Installed packs live in `<data>/themes/<id>/`, override a bundled pack of the same id, and are backed up (`themes/` in the tar).

A pack holds no CSS, selectors or scripts, because CSS can load images from outside servers (tracking the family), hide approval warnings or controls, and make text unreadable; values only, each parsed and checked, keep a theme as safe to install as a language. Besides colour tokens a pack may set `font-display` and `font-serif` next to `font` (a family the app bundles or one it ships as `.woff2`; a slot left out takes the style's default) and name a preferred `style` in its manifest, used only when the family never chose one. The app bundles Figtree, Barlow Condensed, Archivo and Instrument Serif (all SIL Open Font Licence) and serves them from its own origin; nothing loads from the network. Every token is pack contract: a new one needs a default in `themes/ev-isigi/tokens.json`, an entry in the token list and a line in the appearance guide, and removing one breaks packs.

- **`@famos/themes`** holds the contract and rules, with no file access in its main entry: the token list (`MODE_TOKENS`, `SHARED_TOKENS`, `CONTRAST_RULES`; the guide, the stylesheet, the validator and a test that keeps `theme.css` equal to the Ev Işığı pack derive from it), colour parsing (hex, `rgb()`, `oklch()` converted to sRGB) and WCAG contrast, the radius and shadow grammars, `validateThemePack` (all errors listed; unknown tokens ignored and reported; missing tokens from the default; fonts only WOFF2 from the pack, 400 KB each; 1.5 MB per pack; contrast on the pairs a pack changed) and `renderStylesheet`. `@famos/themes/node` reads and writes pack folders for `pnpm theme:check <dir>`.
- **The stylesheet is generated, never passed through**: `html:root, html .day { --wall: …; … }`, `html.dark { … }` and `@font-face` rules are built from the parsed numbers (colours re-serialized as `#rrggbb` or `rgb(r g b / a)`), so a pack's text never reaches a browser. The selectors are one step more specific than `theme.css`'s, so the theme wins wherever its sheet sits.
- **The registry** (`apps/server/src/themes.ts`, on the same `pack-registry.ts`) loads bundled then installed packs at start and on every change, behind `ThemePort` in core (`KernelOptions.themes`; without one only the default is listed). Bundled packs report contrast shortfalls as warnings; installed packs are strict (a failing contrast pair refuses the pack, listing the pairs).
- **Core** (`packages/core/src/themes.ts`): public routes `core.listThemes`, `core.getAppearance` (the caller's effective theme and style), `core.getThemeStylesheet` (`text/css`, ETag = pack version + content hash) and `core.getThemeFont` (`font/woff2`, same origin); actions `core.installThemePack`, `core.removeThemePack`, `core.installThemePackFromUrl` (enqueues `core.fetchThemePack`; guarded HTTP is for jobs), `core.setFamilyTheme` (all `core.settings.manage`), `core.setDisplayTheme` (`core.devices.manage`) and `core.setMyTheme` (any member). Installed packs and choices (family, member, display) are small JSON values in `core_settings`; unknown ids fall back to the family theme, then Ev Işığı. `core.themes.changed` makes open screens reload.
- **The web app** keeps `theme.css` as the baseline (first paint, offline), applies the generated sheet as `<style id="famos-theme">`, stores the last one in `localStorage` (applied by `app.html`'s inline script before first paint) and refreshes on `core.themes.*` events. Displays get theirs from `core.getThisDisplay`. `scripts/theme-colors.test.ts` fails on hard-coded colours in the web app, `@famos/ui` and extensions outside the token layer.

### Pages with parameters

A web extension's page `path` may contain `:name` segments (`/vehicles/:id`). The catch-all route matches exact paths first, then patterns, and passes the values to the page as `params`. A page without parameters takes no props.

### Who may open a page

A page declares the capability to open it with `requires`, the same as its navigation entry: the entry hides the way to a page, `requires` keeps a typed address, bookmark or shared link from opening it. The shell checks it for every page before it loads (`apps/web/src/lib/page-access.ts`, asked by the root layout): the app's settings pages by their settings entry (`APP_SETTINGS`), an extension's by its `PageContribution`. Someone without it gets one shared state, `NoAccess` (design system §3.8), never a redirect. The server still refuses every read and action they may not run; this only spares them a page of refusals. `scripts/page-access.test.ts` fails when an extension's page and its entry (on its path, or the one it lies under) ask for different capabilities, and when an app settings page sends people away by hand.

## 7. Actions: one definition, many surfaces

An action is the unit of change. One `defineAction` produces:

1. an HTTP endpoint (`POST /api/v1/actions/:id`) for the UI (unless it is `expose: 'internal'`, below),
2. a draft-card proposal the AI pipeline can create and a human can approve,
3. a tool for the built-in assistant and for MCP clients, inside the AI sandbox (§11).

One definition keeps validation, permissions, approval and side effects in one place, route handlers thin, and lets a new action with `ai` hints reach the AI pipeline, the assistant and MCP without agent code.

The **action runner** applies, in order: input validation → access (`requires`, judged by capabilities) → `prepare` (optional work outside the transaction, §11) → approval policy (execute now, or store a draft) → `run()` inside one SQLite transaction → audit log → events after commit.

**Audit log.** `core_audit_log` gets one row per change, in the change's transaction: `at`, the whole actor (the person with role and PIN flag, the app, the AI and its mode), the action id, its draft, the outcome (`applied`, `drafted`, `rejected`, `undone`, `replaced`) and `target`, the id from the action's own `target` (an app, a key, a device), so "who paused Home Assistant" has an answer (null for an action without one and for rows older than the column). A row never holds the input or a result, so nothing a person typed and no secret reaches it. A secret route (below) records itself once it succeeded with `kernel.audit.record(actor, operationId, target)`: one `applied` row with the route's operation id (`apps.createToken`, `core.trustThisDevice`), the id of what was made, and a `system` actor where nobody is signed in (setup, a display claiming its code).

**Secrets stay routes.** Creating or setting a secret is the one exception to "every state change is an action": passwords, PINs, AI provider keys, minting an app key or a personal (MCP) key, OAuth sign-in for AI apps (approving a sign-in, the token endpoints, setting up an app whose client secret is shown once), device trust and pairing, push subscriptions, a Telegram bot token or link code, a backup target's sealed credentials, the mailbox password and the long-lived token of Home Assistant. They set a cookie, show a secret once, or call the identity store or a network service, none of which belongs in a transaction or in an idempotency answer (an action's answer is kept for replays, §14). Everything around the secret is an action:

- apps and keys: the app's record (`core.createApp`, then its first key from `POST /api/v1/apps/{id}/tokens`), pausing, resuming and revoking it, revoking one of its keys or a personal key (`core.revokeApiToken`);
- MCP and OAuth: `core.setMcpEnabled`, `core.setMcpOAuth`, `core.deleteOAuthClient` (removing an app set up to sign in);
- devices: confirming a display's code, changing what it may show, revoking a device;
- the AI, except a provider's key: `core.addAiProvider`, `core.updateAiProvider`, `core.deleteAiProvider`, `core.setAiRoles`, `core.setAiLimits`, `core.setAiPrivacy`, `core.setAiSwitches`;
- backups, the mailbox and Telegram, except their secrets: `core.runBackup`, `core.setBackupEncryption`, `core.updateBackupTarget`, `core.deleteBackupTarget`, `core.disconnectEmail`, `core.addEmailSender`, `core.removeEmailSender`, `core.checkEmailNow`, `core.unlinkTelegram`.

Saving the Home Assistant connection is likewise one route of the extension (`PUT /api/v1/homeassistant/connection`, `homeassistant.manage`, a person at a password sign-in): it seals the token with `ctx.secrets` and records itself with `ctx.audit.record(actor, operationId, target)`, which an extension may call only for operation ids that start with its own id; pausing, checking and disconnecting stay actions. Saving the mailbox stays one route, since its test needs the password. These settings live in adapters on their own database handles, which would wait forever inside a unit of work, so core reaches them through the SDK ports `AiSettingsAdmin`, `BackupSettingsAdmin`, `EmailSettingsAdmin` and `TelegramLinkAdmin` (`in(uow.db)`, implemented by the adapters, handed to the kernel by `apps/server`), none of whose methods takes or returns a secret. A provider's key is set with `PUT /api/v1/ai/providers/{id}/key` (audited as `ai.setProviderKey`); changing a provider's address drops its key, since a key is only sent where it was entered for, and the answer says so (`keyDropped`). Their capabilities are critical, or for a person's own key `core.mcp.use`, which no app and no AI holds. A member's own Telegram link needs only `core.notifications.receive`; `core.unlinkTelegram` requires a person present and has no AI hints. The AI never runs or proposes any of these.

**Approval policy.** `approval` is `'never'`, `'always'`, `'ai'` (a draft when the caller is AI; the default for non-read-only actions), `{ unless: capability }` (holders apply directly, others holding `core.drafts.propose` propose a draft, the rest are refused) or a function. A non-read-only action must declare `requires`, `approval: { unless }` or both; the registry refuses one with neither. So a Supervised member's change to shared data becomes a draft for someone who may approve it, with no role names in the code. `{ unless }` may add `except(actor, input)` (a case that never needs approval) and `owner(ctx, input)` (whose own thing the input changes): that member applies directly when their role may propose the change or holds the action's `requires` (whoever may add a shopping item may remove the one they added); the AI never does.

**The access decision.** One pure function decides whether a call is applied, drafted or refused: `decide(action, actor, env, facts?)` (`packages/core/src/decide.ts`), covering the access checks (`requires`, displays, the AI's rules, critical capabilities, areas off for the AI, anonymous callers), an AI proposal that would change nothing (`refuseProposal`) and the approval policy. It answers `{ outcome: 'apply' | 'draft' | 'refuse', reason?, capability?, depends? }`; without a call's facts (its input, the owner the policy names) it answers for any input and marks `depends` where an input could change it. The runner acts on that answer alone and the app asks the same function, so a screen never offers what the runner would refuse: `GET /api/v1/core/access` answers for every data-changing action that is on, `POST /api/v1/actions/{id}/check` for one input (resolved like a call; nothing runs or is recorded; limited per person). A refusal is a `403` carrying `reason` (`capability`, `approval`, `display`, `sign_in`, `ai`, `critical`, `area`) and the `capability` that would allow it, so the app explains in the reader's words; its `message` never names an action. The web app reads the answers with the session and again when a role, member or extension changes or a change is refused (`apps/web/src/lib/access-book.ts`), as `app.access(actionId)`, `app.accessFor(actionId, input)` and `app.approval(actionId, input?)`; a refused control is not drawn, a suggestion says so under the form's title, and no page infers what a role may do from a capability name (design-system §4.8).

**Closed by default.** `admission`, `approval` and `access.can` are switches over every actor kind: an unknown kind is refused (`admission`, `can`) or needs approval (`approval`), and a new kind in `Actor` does not compile until each names it. Code never compares `actor.kind` to pick a field; it asks the SDK's helpers, so a caller without the property is never a free pass: `selfOf(actor)` (the member acting for themselves; null for the AI, a display and the system, so "self is not the assignee" refuses them), `memberBehind(actor)` (the member an act is done by or for, including the member the AI works for), `personPresent(actor)` (a human acting directly, required for deciding, editing and withdrawing drafts, credentials, devices, sessions, passwords, auto-approval, roles, members and extensions) and `principalOf(actor)` (a stable string for audit and attribution). The web has `memberBehindDraft` (`@famos/ui/slots`) for a draft's untyped `proposedBy`.

An action run inside another (`uow.run`) is decided like a call: one that would need approval for this actor is refused (`forbidden`, `details.reason` `nested_needs_approval`), never applied, so an outer action cannot give a person a change they could only suggest. Not asked again are an act a person already decided (applying an approved suggestion, or taking one back) and a service action marked `nested: { governedBy: 'owner' }` run by the extension owning its record. An extension declares its records' typed-id prefixes in `recordIds` (`vehicle` for `vehicle_<uuid>`); the runner reads the prefix from the id, never the caller's word, and the caller is the extension whose action is running. So whoever may manage the garage (`vehicles.edit`) also manages its duties and papers through records, while any other extension or record is held to the strict rule.

**Connected apps** (§12) add the actor `{ kind: 'app', appId, roleId, mode }` (an app acting for itself) and the property `via: { appId, appRoleId, mode }` on a member (a member an app acts for). For the latter, `selfOf` and `memberBehind` are the member, so their own things stay theirs and attribution and the notification `except` follow. `personPresent` is false for both; `principalOf` is `app:<id>` or `app:<id>/member:<id>`. `access.can` gives the app its role's capabilities, and the member through it only what both the member and the app's role hold; neither ever holds a critical capability, `core.drafts.approve`, `core.mcp.use` or `core.signIn.pin` (`appMayHold`), whatever role the admin picks. `approval` treats both like a member (the role's `unless`, the policy's `owner` and `except`), except that in `mode: 'suggest'` every non-read-only change becomes a draft, even for an action that never needs approval.

**Doors and what an action exposes.** Each way in reads one kind of credential and admits only the callers it can stand for (`authenticate(…, door)` in `apps/server/src/http/authenticate.ts`, `admits(door, actor)`):

- `/api/v1/*` and its socket take the session cookie (a member) or a paired display's device cookie, and refuse any `Authorization` header with `400`, so a bearer never reaches them by accident;
- `/mcp` takes a bearer only: a personal key, or an access token FamilyOS's own authorization server issued for `/mcp`; its caller is the token's AI actor;
- the OAuth endpoints (`/.well-known/oauth-*`, `/oauth/*`, the `oauth` door) read no cookie, admit no caller and run no action: they authenticate OAuth clients, never people. Approving an AI app's sign-in is a session route needing a person present, a password sign-in and `core.mcp.use`;
- the `api` door (`authenticateApp`, the public API) takes an app key as a bearer, never a cookie, and admits the app kind or a member with `via`; a signed-in member never gets in there, nor a member through an app at the session door.

A route that needs only a sign-in (`requireActor('signedIn')`) names the kinds it admits (a member), so a kind added later is refused until decided. The settings routes that are not actions (reads, and the secret routes above) are session-door only and check a capability or `personPresent` on the cookie's actor.

`expose` says where an action is reachable: `'app'` (the default) is in the app's API for any caller its rules allow; `'internal'` is plumbing for jobs (a feed's last-read mark): no HTTP route, not in the OpenAPI document, and `admission` refuses a member (also inside a unit of work) and a display. Only the system runs it; the AI may read through a read-only one but never change through it, since such a draft could not be approved. Actions other extensions run for a person (a record's rename), drafts' undo steps, digests and AI contexts (people read them too) and anything the web app calls stay `app`. `defineApi` markers on an action or a GET route also offer it on the public API (§15); it stays `app`, so marking never changes who may run it.

A token's limits live on the actor and the runner enforces them, not only one door's tool list: `ai.scope` (`read` | `read_write`, from an MCP token) makes `admission` refuse every action that is not read-only, and a `conversationOnly` action is refused to an AI not in `conversation` mode working for a member.

**AI actors** are checked like members: an AI actor may invoke an action directly only if it is `readOnly` and `access.can(aiActor, requires)` holds, so reading an area that is off for the AI is `forbidden`; its data-changing invocations become drafts. An action that sends data outside the household (a share link, a message, an email, a call to a third party) is marked `external: true`; the registry refuses `ai` hints on it at startup, so the AI can never propose it. Server routes that call outside (Telegram sending, push) are not actions, so the AI cannot reach them.

## 8. Drafts (human in the loop)

AI must not change family data on its own: it proposes, and a person approves. A draft is a first-class row owned by core, not a suspended workflow: a workflow snapshot is tied to the code that made it and breaks across upgrades, while a row survives restarts and upgrades and can be queried, edited and audited. Expand-only input schemas keep pending drafts valid after an upgrade.

```
pending ──► approved ──► applied ──► undone
   │            └──────► failed (retryable)
   ├──────► rejected
   └──────► expired (its day has passed; also from failed)
```

A draft stores its source (inbox item, agent, member), action id, Zod-validated proposed input, edited input, model and prompt version, confidence, uncertain fields, a dedupe key (a job that proposes twice makes one draft), who decided and when, and the action's output. Applying is idempotent on `draft_id`. The UI renders a draft as a form generated from the action's Zod input schema, or with a presenter from the extension's `./web`. The approve, reject and undo routes need only `core.drafts.propose`; the runner (`assertApprover`) then requires `core.drafts.approve` and the capability that would have let the change apply directly, except for the member a draft is addressed to, who decides their own.

**Who decides.** The person behind an AI draft is `onBehalfOf` (assistant, MCP) or `DraftMeta.forMember` (Quick add). After auto-approval is checked, a draft that person could decide is addressed to them; otherwise it goes to the approvers, who are told. A draft a member proposed (because the action needs approval for them) goes to the approvers, without the proposer.

**Actions that AI may propose declare `undo`**, so an approval can be taken back.

**Titles.** Every action that can become a draft (non-read-only, with `approval` other than `never`/`ai`, or with `ai` hints) names what it proposes with `draftTitle`, a key in its extension's catalog. A presenter or the draft's summary comes first; `draftTitle` (with the input's review `label`) is the fallback in every card and the body of the "waiting" notification, so no card shows a raw action id. A test over the bundled extensions fails when a proposable action has no key.

**Withdrawing and gone subjects.** The member behind a draft (its proposer, or the person an AI draft was made for) may reject it without `core.drafts.approve`: it becomes `rejected` with `decided_by` = that member (the API shows `reason: 'withdrawn'`), audited as `rejected`. The status column is a `CHECK` constraint in a STRICT table, so withdrawing is not a status of its own. When approving gets `not_found` from the action, the runner stores the draft as `rejected` with `error = 'gone'` (`reason: 'gone'`) rather than leave it pending forever.

**Who sees a draft.** `core.listDrafts` shows a member only drafts they may decide or are the person behind, so no one reads another's suggestions, and each says whether its reader may decide it (`canDecide`). `core.countWaitingDrafts` counts the waiting drafts (pending or failed) `mayDecide` allows. Quick add is the one place every waiting suggestion is decided: **Waiting for you** shows the captures with their suggestions and the suggestions from elsewhere (an assistant answer, an MCP app key, a person sent for approval), grouped by origin. Its badge, Today's Needs you and the page count the same set (waiting, `canDecide`), and the "waiting" notification links there; the assistant also shows its suggestions under the answer that made them.

**Undo.** An action can declare `undo(output) → { actionId, input }`, its inverse computed from what it returned (`calendar.createEvent` → `calendar.deleteEvent`; `lists.addShoppingItems` removes only the items it created). `undoDraft` runs the inverse and marks the draft `undone` in one transaction. A stored output that no longer matches the output schema is not undoable.

**Duplicates.** A pending draft says "this may already be there" (`mayExist`) when the action's optional `alreadyThere(ctx, input)` finds the same thing (calendar: same title on the same day; tasks: an open task with the same title and due date; shopping: every item already on a list). It is computed when drafts are listed, so it stays current, and never blocks approval.

**Doing it to what is there instead.** News of a change often reads as new: "Regional gala moved to Sat 14 Nov 09:00" becomes a new event while the gala is on the calendar for 7 Nov. An action may declare `instead(ctx, input)`: the action and input that would apply the draft to the thing on record (`calendar.createEvent` offers `calendar.changeEvent` of that event; for a repeating event, of its date nearest the new day). The model's output stays as it is and the person chooses, because a model taught to propose the change itself proved unreliable (it looped, dropped the new date, broke unrelated cases).

- **Checks.** The runner checks an offer like a proposal: a known, enabled, data-changing action, a valid input with names resolved, an existing target, a change that changes something, and the draft's own words naming the target (`matchThing`, surely or as a match the person is asked to check, as an AI's `label` must), so a careless `instead` never offers merely the closest thing. The calendar offers only an event within a month that the new title surely names (`exact` or `strong`) or names by the same code ("U13 fixture" for "U13 Eagles away game"), and nothing on a tie, a partial match, a new repeating event, or an event already at that time.
- **Choosing.** A pending draft lists the offer as `instead` (computed when listed, like `mayExist`); `core.replaceDraft` turns the draft into it, and whoever chooses must be able to decide both. The draft stays `pending` under the same id with its proposer and addressee, keeps what it proposed before in `replaced`, and the audit log records `replaced`. It is then approved like any change, with that action's undo, so a supervised member's suggestion still waits for an approver.
- **Everywhere.** Working on drafts, not on their origin, it serves Quick add, the assistant and MCP alike. Telegram's message names what is there (the alternative's `key`, a catalog line with `{{what}}`), so approving never adds a second one unseen, and a third button runs `replaceDraft`. A drafted `ActionResult` carries `instead` (the real name, `at` and `to`) and the agent's `say` line names it, so the assistant and MCP clients tell the person; agents have no tool to choose it.
- **Cards.** The offered change is the filled main button and **Add as new** a secondary one taking two taps (`draftButtons` in `@famos/ui`): the news means the move, so the layout must not push people to the duplicate. In a Quick add group decided together, a suggestion with an offer or `mayExist` starts unticked (`pickedByDefault`), since the group's one button would add it unseen; choosing the offer ticks the change. Today's Needs you has no approve button for a suggestion with an offer; it is decided in Quick add.

**Replacing a whole thing, or changing some of it.** A form saves the whole thing, so its `update…` action replaces it: its input is `wholeRecord(fields)` from `@famos/sdk`, the create action's fields all required, null for an empty one and a defaulted one sent with its value. A body that leaves fields out is refused with `bad_request` naming them, because reading a missing field as "empty" or "default" would quietly clear what a script or integration never meant to touch (a task's assignee, and with it who may change the task without approval). Changing some fields is a separate action whose optional fields mean "keep as it is" (`lists.changeTask`, `calendar.changeEvent`, `home.updateItem`); that is the one the AI and agents get. A draft stored before an input became stricter must still approve with its old meaning: an action declares `storedInput(input)`, which the runner applies to every stored draft input before reading or validating it (approving, listing, the old → new and every hint), never to a new call. `storedAsWhole(fields, key)` is that upgrade for a whole-record input: a left-out field becomes null, or its default, as the replace read it before.

**What a change changes from.** An action that changes a thing may declare `currentValues(ctx, input)`: what the fields the input touches hold now, keyed like the input (`calendar.changeEvent` adds every field of the event's time once one changes, so a new time reads against the old day; `lists.changeTask` likewise for a deadline). A waiting draft lists them as `before` (computed when listed, with a saved edit if any), and the presenter's `fields(input, context, before)` writes "old → new" (`changedValue` in `@famos/ui/slots`). It is the same for Quick add, the assistant, MCP and a person's own request; a decided draft has no `before`.

**Expiry.** An action can declare `draftDate(input)`, the day (`YYYY-MM-DD`, family time) a draft is about (a planned meal, a one-off event's or a board note's last day; tasks and repeating events declare none). A waiting draft whose day is before today is listed as `expired`, is not counted as waiting, has no Telegram buttons and is refused on approval (`ActionRunner.passedCheck`); the daily job `core.expireDrafts`, a few minutes after midnight family time, stores the status (`expirePassed`, idempotent). A Quick add item whose drafts all expired settles like one whose drafts were all decided. `saidDate(input)` is the day a suggestion speaks of, for its wording only (a task's due date: it never expires); a drafted result carries `date` (`saidDate`, else `draftDate`), and the assistant's fixed line and the tool's `say` keep it ("Add a task: Pack my football kit for Thursday, 22 October").

**Gone targets.** An action that changes or removes one row names it with `target(input)` (its own table, the id, and the column set once the row is archived or deleted). `ActionRunner.goneAmong` reads the targets of all waiting drafts in one query per table; a draft whose row is gone can never apply, so `core.listDrafts` returns it as `expired` with `reason: 'gone'` (Quick add says **Can no longer be done**), and `core.countWaitingDrafts`, Today's Needs you, the digest and Telegram leave it out. Nothing is written; approving it still closes it as `gone`.

## 9. Jobs and events

Ingestion, AI calls, reminders and deliveries run in the background and must survive crashes and restarts, without Redis or a workflow engine on a Raspberry Pi, so the queue is a table in the same SQLite database. There is no exactly-once guarantee, so **job handlers and action `run` functions are idempotent**.

- **JobQueue port**, implemented as a SQLite table in the same database: leases, retries with backoff, timeouts, dead-letter state visible in the UI.
- **Lanes.** The worker runs one loop per lane, one job at a time in each: `default` (every job unless it says otherwise) and `long` (`defineJob({ lane: 'long' })`, for jobs that can take minutes, such as backups and their uploads). Each loop claims only its lane's job names; lease recovery is shared; `drain()` (tests, CLI) runs both lanes until both are empty. Both loops share the one SQLite connection, which Kysely's driver hands to one holder at a time (per query, and for a whole transaction), so the lanes' queries interleave but their transactions never do. A long job inside a transaction makes the other lane wait, so long jobs keep transactions short.
- **Timeouts and leases.** Each attempt has its job's `timeoutMs`. A job is leased for its own `timeoutMs` plus a grace (30 s, `WorkerOptions.abortGraceMs`), never for the longest in the lane. When the timeout passes, the worker aborts the `signal` of the attempt's `JobRun`, then waits for the handler to stop (up to the grace, when its lease would run out) before recording the failure that schedules the retry, so a retry does not run beside the attempt it replaces. The job's `ctx.llm` and `ctx.http` calls end with that signal by themselves (reported like their own timeout), so a handler passes `run.signal` only to other things it waits on, and stops writing once it is aborted; one that ignores it is given up on after the grace, and idempotence is what keeps its late writes harmless.
- **Queue = outbox.** Any side effect that must survive a crash is written as a job in the same transaction as the data change. There is no separate outbox table.
- **Event bus**: in-process, emits only after commit, payloads carry IDs only. For UI invalidation and lightweight reactions, never for anything that must be durable.
- **Events have an audience, and the hub filters per socket.** The WebSocket (`/api/v1/ws`) is a feed of events, so it is held to the API's access rules. `defineEvent(name, payload, { audience })` names who may hear of it: a capability id, a member (`{ member }`, for what is one person's), everyone (`EVERYONE`: theme, language, family settings), any signed-in member (`ANY_MEMBER`), a list of these, or a function of the payload for row-level cases (a duty belongs to its `audience` capability's area; an Inbox item is its sender's; a draft addressed to one member is theirs). The hub sends an event to a socket only when its actor passes `access.can` for the audience, so a member without `calendar.view`, or a display not granted it, hears nothing of the calendar, not even that something changed. Closed by default: an event with no audience goes only to holders of its owner's view capability (`<owner>.view`, owner = the name before the first dot; a display only if granted), and to nobody when the owner has none. A test fails for any registered event without an audience. Payloads carry no text the audience may not see (the calendar's tag event carries no tag name).
  Sockets are checked when they open, so the hub closes them whenever the actor behind one may have changed: a member's on `core.member.changed` (archived, role or details changed) and `core.session.ended` (sign-out, sign out everywhere, a new password or PIN); a display's on `core.device.changed`, with the PIN sessions of family devices. The client reconnects and is checked again. The upgrade also needs an `Origin` that is the base URL or one of `trustedOrigins` (the cookie is `SameSite=Lax`, so a page on another port of the same host would otherwise get it); a client without `Origin` is no browser. The host's channel events (`core.telegram.status.changed`, `core.telegram.link.changed`, `core.email.status.changed`) are core events, emitted by the adapters' callbacks and the actions that change them.
- Long processes are **chains of small idempotent jobs**, each keyed by its subject ID and persisting its result before enqueuing the next.

### The change log, versions and conditional writes

An app that was away needs to know what changed, what was removed, and whether what it is about to overwrite is still what it read. The action runner writes all three pieces, so no extension can forget them.

- **The change log** (`core_changes`: `seq` autoincrement, `at`, `extension`, `entity`, `entity_id`, `op` `upsert|delete`, `audience`). An event declares `changes` in `defineEvent` (a function of the payload returning `{ entity, id, op }` per thing). The runner writes those rows **in the transaction that emitted the event**, so a rollback leaves none; two events about one thing in one transaction are one row. Events of things apps may read (events, tasks, shopping items and lists, chores, board notes, recipes and meals, homes, calendar subscriptions) carry precise ids and an `op`; `delete` means "gone for readers", so a soft delete or archive is a `delete`. The row stores the event's audience, so `changesSince(seq, actor)` answers each actor only with what they may hear (a member or display by `access.can`, an app or agent as the member it works for; the cursor still moves past the rest). A read returns each thing once, in its latest state, with a cursor and `more`. **Retention is 30 days** (daily job `core.pruneChanges`); a cursor older than the oldest row, or ahead of the log (a restored backup), is `gone` (HTTP 410) and the client reads everything again. A page's validator, `collectionTag(extension, actor, window)`, hashes the extension's newest seq, the actor's capabilities in it and the window the list is cut by (a range, "today"), so a view that changes without a write (a day passes, a role changes) changes the tag too.
- **Jobs that write their own tables** use `ctx.unit(async (uow) => …)` (`JobContext`): an action's unit of work, run as the system, so the write and its change-log row share one transaction and events fire after commit (the board's cleanup, the calendar's subscription refresh). A job that changes what apps may read never writes through `ctx.db` alone.
- **Versions.** Each table the public API exposes (calendar events, tasks, shopping items, shopping lists, chores, board notes) has an integer `version` from 0 that goes up by one on **every** write of the row. A trigger does it (`addVersion` in a migration), so no code path can forget, and writes that leave `updated_at` alone (a board pin or reorder, a tag rename) still count; `updated_at` only guards planned reminders. A parent's version also goes up when a child its shape shows changes (`bumpParentVersion`): a shopping list when an item changes (it shows the open count), a chore when its people or completions change, a board note when someone sees it. Children that are columns or not shown (a task's completions, an event's tags) bump nothing extra.
- **Conditional writes.** `ActionTarget.versionColumn` names the column. `invoke(…, { ifMatch })` makes the runner compare the row's version with the caller's **inside the write's transaction**: `precondition_failed` (HTTP 412, `details.version` holds the current one) when it differs, `not_found` when the row is gone, `bad_request` when the action names no versioned row. It applies to a direct run and to a draft's proposal alike. The public API sends it (`If-Match`, §15); nothing on `/api/v1` does.
- **Hard deletes** of the exposed tables (only board notes) leave a tombstone through `op: 'delete'`. Everything the public API reads is in the log: events (a deleted calendar tag is an `upsert` of each event it left), a subscribed calendar's occurrences (refresh and removal replace all its events at once, so one `subscription` row means "read the occurrences again"), tasks (a completion taken back is an `upsert`), chores (rewriting the people is an `upsert`), shopping, board notes, and waiting suggestions, whose expiry and failure are written in a unit of work like a decision. Other hard deletes leave no trace because no connected app reads those tables (record documents, obligations and their history, pet treatments, vehicle logs, ambient photos, assistant threads, Home Assistant items, people and switches). A thing that gets a public read first gets its events a `changes` entry, in the same change.

### Notifications

Every feature needs one way to tell a person something, and "tell whoever may approve" must be expressible without knowing devices or channels. So a notification is data: the in-app list (Notifications page, unread badge on More) is the record and always written; pushes and messages are copies, so the app can always show what was sent and a lost push loses nothing.

- **Telling people.** Actions call `uow.notify(request)`, jobs and routes `ctx.notify(request)`; either enqueues a `core.notify` job (in the action's transaction, so a rollback tells nobody). A request names a **kind** declared with `defineNotificationKind` (undeclared kinds and unknown capabilities throw), recipients (member ids and/or a capability such as `core.drafts.approve`, optionally minus `except`), title and body as translation keys with parameters, an in-app `url`, a `source`, a `dedupeKey` and an optional `delayMs`.
- **Audience.** A kind may name an `audience` capability (checked against the registry). Members without it do not see or set the kind in their preferences; delivery is unchanged, since recipients come from the notify call.
- **`core.notify`** resolves recipients when it runs (active members only, so a role change changes who is told), writes one `core_notifications` row per recipient (`insert … on conflict do nothing` on member + dedupe key, so a retry or repeated request never duplicates), emits `core.notification.created`, and enqueues one `core.deliver` job per recipient and channel the member enabled and that is available for them. Kinds of a turned-off extension create nothing.
- **`core.deliver`** renders the text with `translate(locale, key, params)` (member locale, else family locale; English where a pack lacks the string), waits out the member's quiet hours (family time zone, may cross midnight) by re-enqueueing itself, skips rows already read, and calls `NotificationChannel.send`. `gone` ends it; a thrown error is retried by the queue. Titles and bodies are never logged.
- **Preferences** live in `core_notification_prefs` (per kind and channel, plus quiet hours). A kind's `defaultChannels` apply until the member chooses; for a kind that names none, a channel is on unless it says `byDefault: 'off'`.
- **Host channels** are adapters wired in `apps/server` (`KernelOptions.channels`); Web Push is the first.
- **Extensions can add a channel** (`defineNotificationChannel`, `defineExtension({ channels })`) for a service the host should not know, such as a home automation hub. Its id is the extension's id or `<id>.<name>`; the registry refuses a foreign prefix and an id already held. The kernel binds it to its extension: `isAvailableFor` runs with the extension's context and `send` with its job context (its tables, secrets, `http.post`, network and logger, held to the manifest), so a channel can do no more than the extension. The list is the host's channels, then those of installed, switched-on extensions; a delivery for a channel that is gone ends quietly. A throwing check means "not available" for that member and never stops the notification or other channels; a throwing `send` is retried. A channel may say `byDefault: 'off'` (members opt in) and give a `hint` the preferences page shows to members it cannot reach yet. `NotificationMessage.link` is `url` made absolute with `FAMOS_BASE_URL`, or null without one.
- **Reminders** (`calendar.remind`, `lists.remind`). Only an item's **next** reminder is scheduled, as a job with `runAt` = the reminder instant, enqueued in the transaction of every create, update, delete or completion (`uow.enqueue`; a job enqueues its follow-up with `ctx.enqueue`). The payload names the item, the occurrence and the item's `updated_at` (events also the planned instant); the job reloads the item and does nothing if it is gone, done, changed or the occurrence was skipped, because that change planned its own reminder. A recurring event's job notifies, then schedules the next occurrence (an exdate is never produced by the expansion); a repeating task is planned again when its completion moves the due date. Instants are computed in TypeScript in the event's time zone (all-day: the family's `reminderTime` local minus the lead, DST-safe); a reminder more than 5 minutes past when planned is dropped, and one that waited past its event is not sent. A job recomputes its instant with the current `reminderTime` when it runs: when that is still ahead (the family moved the time later) it enqueues itself for it and returns; an earlier time applies to reminders planned afterwards. The `dedupeKey` is `reminder:<id>:<occurrence>`, so a retried or duplicated job never notifies twice. Events store `reminder_minutes` plus `reminder_set` (0 = never chosen, the default applies; 1 = chosen, null minutes = none).
- **Web Push** (`@famos/adapters/webpush`, migration scope `webpush`). Our own VAPID (RFC 8292) and `aes128gcm` encryption (RFC 8291) on `node:crypto`, tested against the RFC 8291 Appendix A vector; no `web-push` dependency. The VAPID key pair is created on first use and **never rotated** (a new key invalidates every subscription); the private key is sealed with `FAMOS_SECRET`, so backups carry it. The endpoint comes from the browser, so only `https:` endpoints on known push services (FCM, Apple, Mozilla, Windows) are accepted; the check is injectable for tests. 404/410 delete the subscription, 413 is skipped, 429/5xx/network errors throw so the queue retries. Subscription routes (`/api/v1/push/*`) are credential management outside actions and record themselves in the audit log (never the endpoint). Browsers allow push only on **HTTPS** (or localhost), and iOS only in the Home Screen app, so a plain `http://` LAN address cannot reach phones; the VAPID contact (`sub`) is the base URL.
- **Telegram** (`@famos/adapters/telegram`, migration scope `telegram`). Families already chat in a messenger, and long polling needs no public URL or webhook, so the bot works behind NAT and Tailscale. A bot is publicly discoverable, so strangers are ignored; messages pass through Telegram's servers, which the settings page and guide say. grammY core gives the typed Bot API, but our own `getUpdates` loop replaces `bot.start()`: it picks up a token the API process saved, persists the offset after each update, stops cleanly, and backs off on network errors and HTTP 409 (another poller, shown in Settings → System → Telegram). It runs only in the worker role (`FAMOS_ROLES`) and idles without a token. The token is sealed with `FAMOS_SECRET`; tokens, message text and file names are never logged.
  A member links with a one-time 8-character code (10 minutes) via `/start <code>`; unlinked senders are ignored, and archiving a member removes the link. The adapter imports neither core nor extensions; `apps/server/src/telegram.ts` supplies the callbacks. Shares go to the share target as the linked member (`kernel.share`, §10); approve/reject buttons (`a:<draftId>` / `r:<draftId>`, within Telegram's 64 bytes) call `approveDraft`/`rejectDraft` as that member, offered for the pending drafts behind a notification's `source`. Messages are HTML with escaped text; "Open" is a URL button only when the base URL is https, else the link is appended as text. Setting the token (`PUT /api/v1/telegram/token`) and making a link code are credential routes that record themselves in the audit log (never the token); ending a member's own link is the action `core.unlinkTelegram` (emits `core.telegram.link.changed`).
  **Typed text goes to the conversation; forwarded things are shared.** A plain text message from a linked member (not a command, not forwarded, no attachment) is a question to the kernel's conversation (`kernel.conversation`, §11), in one thread per member; the answer comes back with approve and reject buttons for the drafts it made. Forwarded messages, photos, documents, voice notes and links are shared, as is text after the share command (named by the language packs), and all typed text when there is no conversation, it is off, or the member may not ask. The answer is transport, not a notification: the server sends, from the member-addressed `core.conversation.answered` event, only answers to questions asked from Telegram, and stores the awaited reply with the link so a restart still delivers it. One question at a time per member. Tests use the fake Bot API `@famos/adapters/telegram/fake-bot-api`.
- **Email** (`@famos/adapters/email`, migration scope `email`). Email is attacker-controlled (tracking pixels, HTML tricks, prompt injection), so FamilyOS reads only plain text from a dedicated mailbox the family forwards to, with an IMAP app password (accounts that require OAuth for IMAP are not supported; the guide shows forwarding). Remote content is never loaded, HTML never rendered. `imapflow` (TLS or STARTTLS only, certificates always verified, logging off) sits behind a four-call port (`MailboxSession`: select, list unread UIDs, fetch source, move), so the poller is tested on a directory of `.eml` files (`createDirMailbox`, used when `FAMOS_EMAIL_FAKE_DIR` is set, for tests only).
  The poll is the job `email.poll` (long lane, one attempt; failures are recorded in `email_settings`, not retried), enqueued deduplicated by a worker scheduler every `poll_minutes` and by "Check now". Each unread message is fetched without marking it read and parsed with `postal-mime`. It is taken only when the sender is in `email_senders` (address, member), the topmost `Authentication-Results` reports no SPF or DKIM `fail`, and its Message-ID is new. Text comes from the plain part, else from HTML through our own tag walker (no rendering or fetching; hidden elements and invisible characters removed). Attachments are accepted by sniffed type (PDF, images, audio, plain text) and cut to `kernel.shareLimits()`; the message goes to the share target as the sender's member (`kernel.share`, §10), so capabilities, quotas, feature switches and metadata stripping apply. Order per message: add to the Inbox, record in `email_seen` (UIDVALIDITY + UID, Message-ID, outcome), move to the processed folder, so a failed move never adds it twice and a failed add is retried at the next check. Unknown senders are recorded as `unknown_sender` (left in place, counted) and reconsidered when a sender is added.
  Saving the settings is a route (`PUT /api/v1/email/settings`, `core.settings.manage`, recorded in the audit log) because it needs the password and the network to test the mailbox, and the saved `enabled` follows the test. Disconnecting, the allowed senders and "Check now" are the actions `core.disconnectEmail`, `core.addEmailSender`, `core.removeEmailSender` and `core.checkEmailNow` (queues `email.poll` in the unit of work); they emit `core.email.status.changed`. The password is sealed (`FAMOS_SECRET`, purpose `email`), never returned or logged; logs carry counts and codes only.

## 10. Quick add: the ingestion pipeline

Nobody should have to fill in forms: sharing a message, a photo of a school flyer, a voice note or a document is enough; the AI turns it into suggestions and a person approves them. The extension's id is `inbox` (routes, tables, `sourceKind`); the product calls it **Quick add**.

**Quick add is personal.** People see only their own captures, except an approver who must decide a suggestion from one (a supervised member's): a shared list of everything that came in reads like a shared mailbox and tells the family about one person's note, and what the family should know belongs on the board. A capture leaves the waiting list on its own when its suggestions are all decided or expired, when it had nothing to add, or when it was filed into a record. In the app a capture shows its progress, then its suggestions, with no notification; from outside the app (Telegram, email, the phone's share sheet) the person gets one "ready" notification.

```
Share / upload ─► POST /api/v1/inbox/items ─► files stored ─► inbox.addItem [tx: inbox_item + job]
  worker: inbox.process ─► normalize (saved) ─► understand (LLM: mentions) ─► resolve (kinds' code)
          ─► actions.invoke(…, ai) per suggestion
          └► drafts (pending, sourceKind 'inbox') ─► WebSocket ─► Quick add UI
Person edits ─► core.editDraft ─► edited_input stored on the pending draft (any device, any approver)
Person approves ─► approveDraft (applies edited_input when there is one) ─► [tx: calendar | lists + draft=applied]
          └► event (after commit) ─► WebSocket invalidation ─► all devices
```

| Step | Input | Output (persisted on `inbox_items`) |
|---|---|---|
| `received` | shared title / text / URL / files | item row; files under `inbox/<item id>/` |
| normalize | item | `normalized_text`: shared text, text files and voice notes as text (`--- Voice note ---`; speech to text via `inbox.transcribe` when enabled), plus `transcript` → `normalized`. Nothing is saved until all transcriptions finish, so a retry never duplicates; an unreadable voice note (no model, voice off) is skipped when other text exists, else the item fails with `voice_not_read` |
| understand | normalized text, images/PDFs, today and the time zone, the family's names and descriptions (when names may be sent), the offered mention kinds with their examples, known names | the model's answer: a label, an intent (`actionable`, `question`, `nothing`) and mentions, read by `parseUnderstanding` |
| resolve and draft | the mentions, grouped by kind | one draft per suggestion (dedupe key `inbox:<item>:<extraction>:<n>`), skips with their reason and subject, `summary`, counts → `extracted` |
| failure | an `LlmError` a person must fix, or attempts used up | `failed` + error code; "Try again" bumps `extraction` and re-queues |

One job with saved steps, not separate normalize and extract jobs, so a model retry never repeats normalization and future steps (OCR, link fetching) slot in before reading.

**The model reads, code works out the rest.** One model call reads the message into mentions (§6): names stay names, days stay day references (`DayRef`: the quoted words and the parts they give), existing things stay words. The prompt is built from parts (`extensions/inbox/src/server/understand/prompt.ts`): twelve short fixed rules, today, the family's names and descriptions, each offered kind with its slots and examples, and the household's known names. The answer shape is small, flat and the same whatever is installed (the kind is an enum of the offered ids; no action schemas), in the output mode the adapter picks per model (`schema`, `json`, `text`). A misread is fixed in a resolver, an example or the parser, never by another prompt rule. Drafts store `inbox.understand/<n>+<hash>`, the hash covering the fixed rules, the schema and every offered kind's text. Then, in code (`understand/pipeline.ts`):

1. `parseUnderstanding` reads the answer tolerantly: a bad field is dropped (and marked "check this" where it would have gone), a mention of a kind not offered is skipped as incomplete, and an answer cut off at the output cap keeps its complete mentions;
2. a mention the message does not hold is left out. Each mention carries a `quote`, the words it rests on; code finds them in the message (`understand/evidence.ts`: in order, loosely, so a mended typo still counts), and a found quote is its evidence. Without one, some telling word of what it names, or of its day, time or place, must be in the message's text (forms that start the same count: "gezi", "gezisi"). Titles are written in the family language, so when no mention is quoted or has its title in the message, the reading was translated and cannot be checked this way. An exact repeat of a mention is one mention. Each kind's `limit` keeps text that tells the model to add things from piling suggestions up;
3. the answer also lists the sentences that speak to FamilyOS or an AI rather than to people (`addressed`: labelling them is reading, which models do reliably; obeying "ignore this" is not). A mention whose evidence begins in one is left out as an `instruction` (a quote that only runs on into one still rests on the message), so a note to the assistant inside a forwarded letter suggests nothing. When such sentences are nearly all of the message, it is the sharer's own request ("FamilyOS, add milk") and is read as usual. Notes outside a mention's own quote that repeat what another mention is about belong to that other mention and are left out;
3a. a mention may say it is a detail of another mention of the same answer (`detailOf`: something to bring, a rule, a fee). The model only says whose detail it is; code decides where it goes (`understand/fold.ts`), because examples alone swung the model from one wrong place to another. A detail with no day, repeat or person of its own goes into that mention's notes when its kind takes notes, and is resolved on its own otherwise (a fee due Friday is a task). When the mention is refused, or its suggestion keeps no notes (a new event that turns out to move one already there), its details are resolved on their own;
4. each kind's resolver turns its mentions into suggestions or refusals (`resolveMentions`), with the host's helpers for days (`resolveDay` in `@famos/time`), people (`resolvePeople`: names written in the message are matched to members at home, also when names are not sent), and which existing thing or record the words name (`findTarget`). Every "is this the same thing?" decision (the target of a change, tick or cancellation, a duplicate warning, an `instead` offer, the check of an AI's `label`) goes through one scorer, `matchThing` in the SDK: `exact` (same words and codes), `strong` (one side's words all whole words of the other), `weak` (most words, words in other forms, the same letter-digit code with other words, or several equally good) or `none`, in the family language (case and accents by `Intl.Collator`, no plural rule of any language); a differing code or number ("1B" and "3B", two plates) is always `none`. `exact` and `strong` are acted on. So is the one thing named by other forms of the same words ("swim lessons" for "Swim lesson") or by the same code ("the U13 fixture" for "U13 Eagles away game"), with its target marked uncertain (`id`, shown as "check this"); every other `weak` match becomes an `ambiguous` refusal naming what the words may mean ("which one?");
4a. a guess is never silent: a kind declares in `decides` which input fields its resolver may settle without the message writing them (`defaulted`: the whole family when nobody is named, a default list, today, dinner; `inferred`: an occurrence of a series, a date from a weekday), and a proposal reports in `decided` how it settled each (`written`, `matched`, `defaulted`, `inferred`). The host adds every `defaulted` and `inferred` field to the proposal's `uncertain`, so the card shows "check this", even for a kind that forgot to list it (logged). A test fails for a bundled kind without `decides` (`{}` for a kind that never guesses);
5. the host checks what no resolver can: notes or tags that name a member the message never names are marked "check this";
6. each suggestion is invoked as the AI actor into a draft that keeps the message's words its mentions were found at (`DraftMeta.quote`, shown as "From the message"); what the runner refuses (invalid, already so, not allowed) becomes a skip, as does every refusal (`already`, `unknown`, `ambiguous`, `incomplete`, `not_allowed`, `instruction`), each with the words it was about.

Shared content is wrapped as data in the prompt, and AI can only ever create drafts.

**Dates are read in code, not by the model.** `resolveDay` turns the parts into a date in the direction the kind asks (future for plans, past for things done) with the family's region formats (numeric date order, week start), and checks them against the quoted words with the date words of every installed language (`dateWords`, `writtenDates`, `namedWeekdays` in `@famos/time`, from the shared `app:words_*` catalog keys). A weekday that names no week, parts that disagree with their words, a span, a guessed year or words without parts are marked "check this". A day the words name by distance ("tomorrow", "yarın") wins over a day number or weekday the model worked out, and a week or month without a day is a span (`DayResult.to`), so a cancellation "this week" looks only at that week. The assistant uses the same words to find a weekday in the person's message that does not fit its date, and puts that fact into the turn's prompt.

**Evaluations.** A set of real-world shares (`extensions/inbox/eval`) runs for every change to the prompt, a kind's text or examples, or the parser, on at least the two free models the baselines hold (`FAMOS_EVAL_MODELS`: `nvidia/nemotron-3-ultra-550b-a55b:free` and `nvidia/nemotron-3.5-super-vl:free` on OpenRouter), because a sound pipeline must work on free models; paid models are optional. `baseline.json` keeps what passed per model, and no case that passed there may fail unless it is genuinely ambiguous. A case the provider broke off (an empty answer, a dropped connection, after the adapter asked once more) is an outage: it counts neither way and the baseline keeps what it knew. Each case runs on a household with every shipped extension installed, so the model sees every kind and example a family can be shown. The baseline also keeps a fingerprint of everything the model is asked (`promptHash`, over the prompts rendered with placeholders for family data), and the run's answers are kept in `eval/recorded/`: CI replays them through the real pipeline with the fake model (§17) and fails when a replay no longer passes or the fingerprint differs, so a prompt, kind or schema change cannot merge without a new run.
The assistant's set (`extensions/assistant/eval`, `pnpm --filter @famos/ext-assistant eval`) uses the same matrix and household and runs for assistant prompt or tool changes; every assistant mistake found in use becomes a case. Each case seeds a household, sends one message or a short conversation through the real turn job, and checks the tool calls, the drafts, the answer card and, loosely, the answer's words. A question case says how it should be read (its days, topics and people) and is held to the card's gate: every fact the digests hold for those days is shown, nothing outside them is shown as in them, no ISO date, no wrong weekday, no "nothing" over a topic with things. Its baseline fingerprints the reading, wording and tool-loop prompts and every tool, and CI replays its recordings (readings, openings, tool loops) through today's code (`extensions/assistant/test/golden.test.ts`), the gate never excused.

### Share targets

Channels outside the app (Telegram, email) must put what a member sends somewhere, but the host should not know which extension that is: an installation without Quick add, or with another extension in its place, must still start, and the channels must work the same way. So the destination is a contract, `ShareTarget` (SDK), provided by one extension (`shareTarget` in its definition and in its manifest's `provides`; the registry refuses two):

- `requires`: the capability a member needs to share (`inbox.share`); it must be the provider's own.
- `limits`: `{ maxFiles, maxBytes, accept }`, what one share may carry.
- `receive(ctx, actor, share)`: stores `{ channel, title?, text?, url?, files }` as the member; throws a `FamosError` to refuse.

Channels reach it only through the kernel: `kernel.share(memberId, share)` makes the upload route's checks (the member is active and holds `requires`, the provider is switched on, the files are within the limits and of an accepted type), then calls `receive`. It throws `feature_off` when no extension receives shares or it is off, `forbidden` for a member who may not share, `bad_request` beyond the limits. `kernel.shareLimits()` lets a channel trim first (email drops attachments past them). Quick add's `receive` is the code of its upload route, so a share from Telegram gets an upload's quota, metadata stripping and AI reading.

## 11. AI layer

Families choose their own provider: a cloud one through OpenRouter or any OpenAI-compatible API, or a local one (Ollama and similar). Calls name a **role**, because different tasks need different models, so changing a model is a setting, not a deploy.

**The AI sandbox.** Families will fairly ask whether the AI could reach private records and leak them: models find their way around systems, and shared content can carry instructions (prompt injection). The provider sees whatever is in a prompt, a shared document can tell a model to send records somewhere, and a tool-using assistant reads whatever its tools allow. "The AI will not look" is no guarantee, so the boundary is enforced where data and actions are reached, in independent places, so that one mistake cannot open it:

1. **The AI never reads the database.** Code gathers what it sees through the AI actor's access ("Prompt data"), so what the AI actor may not read cannot reach a prompt.
2. **AI access is a setting per area** (Off, Local only, Any provider), enforced by three checks of the same setting ("AI areas").
3. **The AI has no way out.** Its output can only become drafts, and nothing it proposes sends data outside the household; a successful prompt injection at worst makes a wrong draft, which a person sees first.
4. **Local only means local.** "Local" is where the provider's address resolves, not its kind, and there is no silent fallback: without a local model the area's AI work stops with a clear message instead of switching to a cloud provider.
5. **Transparency.** Every model call is listed for admins, without content.

The details:

- `LlmPort` (SDK) is implemented with the AI SDK and one OpenAI-compatible client for OpenRouter, Ollama and compatible servers (`@famos/adapters/llm-aisdk`). Providers, keys (encrypted with a key derived from `FAMOS_SECRET`), role mapping and limits live in the `ai_*` tables (Settings → AI). `FAMOS_AI_*` environment variables define one provider (fixed id `ai_provider_env`), synced on every start and read-only in the UI; roles the family pointed elsewhere are left alone.
- **Model roles**: `fast`, `vision`, `smart`, `transcribe` (speech to text) and `embed` (embeddings for family search), each mapped to `provider:model`. `LlmPort.transcribe` is not a chat call: it posts the audio as multipart to `POST {baseUrl}/audio/transcriptions` (OpenAI, Groq, OpenRouter, self-hosted Whisper; Ollama has none, so the role is `not_configured`). Otherwise it keeps the rules of `generateObject` (role `transcribe` in `ai_usage`), and no audio or transcript is logged.
- Every call is recorded in `ai_usage`: role, model, feature, member, job, tokens in/out, cost (when reported), latency, error code. Prompts and outputs are never stored or logged.
- Monthly limits per household: budget (reported costs) and call count, in the family's calendar month.
- **LLMs are never called inside an HTTP request**, because a slow model call in a request thread can take most pages down. Only job handlers receive `ctx.llm` (`JobContext`; route handlers get no `LlmPort`, so types enforce it); each call names a role and an explicit timeout. The one exception is the family search question (Family search). "Test connection" lists the provider's models and never runs one. `LlmError.retryable` tells the job whether the queue retries or the family must act (no model, bad key, limit reached).
- Local inference (Ollama, Whisper, OCR) runs in optional compose profiles or on another machine, reached by URL.
- **Switches** (Settings → AI): a main switch and one per AI feature (the `feature` each call names; web extensions list theirs as `aiFeatures`). `LlmPort.policy(feature).enabled` lets a job hold its work (the Inbox keeps items unread, status `held`); the adapter refuses disabled calls with `disabled`.
- **Privacy** (Settings → AI, `LlmPort.policy()`): the family decides whether photos and documents, voice notes (`sendVoice`, default on; off, the adapter refuses `transcribe` with `disabled`), and member names with their "about" text are sent. Without names the model learns nobody's name or description (not even the sharer's); names the message writes are matched to members at home after the model answers, and the assistant and MCP see members only by handle. `zeroRetention` makes OpenRouter requests ask for zero-data-retention endpoints (`provider: { zdr: true, data_collection: 'deny' }`); a model without one fails with `data_policy`, recorded with a reason naming the option. It is off for a new family, because it rules out most free models and the model is the family's choice (`ai/0004_keep_zero_retention` keeps it on where it was). The connection test lists which OpenRouter models have such an endpoint (`/endpoints/zdr`) for the model picker. Photos lose EXIF/XMP/IPTC (location) on upload, before storage and any model call; orientation is kept. OpenRouter's `/audio/transcriptions` ignores provider routing, so zero retention cannot be guaranteed for speech to text; the AI settings say so.
- **AI areas**: an area is an extension (`core` never is). Sensitive areas start Off, because most installations (a Raspberry Pi) cannot run a useful local model; filing a shared paper into an area by hand keeps working. Core stores `ai_areas` in `core_settings` (extension id → `off` | `local` | `any`; default `off` for extensions declared `sensitive: true`, else `any`), cached like the feature switches (`kernel.aiAreas`, refreshed on `core.aiAreas.changed`); `core.setAiAreaAccess` changes it (`core.ai.manage`; opening a sensitive area to `any` needs `confirmSensitive`). The three checks: `access.can` is false for AI actors in an `off` area, and in a `local` one unless the actor's model is local (`actor.local`); `ctx.actions.aiCatalog({ local })` leaves out `off` areas and, unless `local`, `local` ones; the adapter refuses a call whose `areas` (required on `generateObject` and `transcribe`) include an `off` area (`disabled`) or a `local` area when the role's provider is not local (`local_required`, recorded in `ai_usage`, never retried elsewhere). `LlmPolicy.local` (from `policy(feature, role)`) is true when the provider's base URL host resolves only to local addresses (the http guard's `isLocalAddress`, at call time, cached 60 s), whatever its kind.
- **AI modes**: an AI actor says how it works, `{ kind: 'ai', mode, source }`: `share` (reads what a member shared, which is untrusted; Quick add), `conversation` (answers a member in the app's own conversation; the assistant), `agent` (the family's own agent working from outside; MCP). Core decides by the mode, never by `source`, which only names the extension or door: only `conversation` is offered `conversationOnly` actions and reads the member's notes, and what a `share` proposed is the sharer's to withdraw. Core migration `0003_ai_mode` gave older drafts and audit rows their mode; it is the one place core names those extensions.
- **Prompt data**: the job's own item, or read-only actions invoked as the AI actor (`ctx.actions.invoke(id, input, { kind: 'ai', mode, source })`), which `access.can` judges like any member and an `off` area refuses. A job never queries another extension's tables for a prompt.
- **No way out**: AI output can only become drafts of registered actions, which a person approves; `external: true` actions cannot carry AI hints (registry check); the web app renders AI text as text and never fetches a URL in it (images and files shown are the app's own stored files).
- **Output modes**: `generateObject` asks for structured output in one of three ways, per provider kind and model id (`OUTPUT_DEFAULTS` in the adapter, kept in line with the Inbox evaluation): `schema` (the provider constrains decoding to the JSON Schema), `json` (the default, schema in the system prompt, because constrained decoding makes some models loop or drop fields) or `text` (no response format, for servers that refuse one). In every mode the adapter extracts the JSON and validates it with the request's Zod schema, so a caller makes its schema tolerant where one bad field must not cost the whole answer (the Inbox reads proposals one by one). A refused request, or an unusable `schema` answer, steps down a mode (`schema` → `json` → `text`); every attempt is an `ai_usage` row with its `output_mode`. A caller may force a mode (`output`), with no fallback; there is no setting for it.
- **AI activity** (Settings → AI → Usage & limits → "See what the AI did"): `ai_usage` also records `areas` (JSON array of the extensions that contributed data, refused calls included). `GET /api/v1/ai/activity?limit=&before=` (`core.ai.manage`) returns calls newest first (feature, role, areas, provider, model, tokens, cost, latency, error code, member's display name) with a `next` cursor. No prompt or answer is stored, so none can be shown.

### The assistant

The `assistant` extension answers a member's questions in per-member chat threads (`assistant_threads`, `assistant_messages`; never shared).

**Questions are answered from facts code fetched.** A free-form tool loop asks one model to read, plan calls over every tool, merge, decide what is missing and word it all; each step slipped on free models in use, prompt fixes recurred and code fixes held. So for a question the model only reads and words, and code does the rest, as in Quick add:

1. **Read** (`understand.ts`): one `generateObject` that gives the message's `parts` in the order asked (`ReadingSchema`; a message of one thing is one part, and a single object is read as one part), each with a small schema (`QuestionSchema`: its `quote`, `intent` `ask | change | remember | other`, `topics` from `QUESTION_TOPICS`, a `span` of `DayRef`s, the `people` as said, the `about` words), about 25 lines of rules and a few examples. It sees only the message (and the person's previous two messages) and no family data (`areas: ['assistant']`). The schema is tolerant, so one bad field never discards the reading; an unusable reading (after the queue's retry) leaves the message to the tool loop.
2. **Resolve** (`question.ts`): days with `resolveSpan` (none named: the coming seven days), people with `resolveAskedPeople` (self-words from the catalog), topics with `resolveTopics` (none named: calendar and tasks). The meal plan brings the calendar along, since a dinner elsewhere is an event. A topic not installed, closed to the AI or not readable by the asker becomes a "not here" line with why.
3. **Fetch**: each open topic's digest (`ctx.actions.aiDigests`), invoked as the AI working for the asker (`ctx.actions.invoke(…, { kind: 'ai', … })`), with the days, the people and the `about` words (which rank, never filter).
4. **Render** (`card.ts`): the answer card (`AnswerCardSchema`, stored in `assistant_messages.card`): what was understood (topics, people, the span's label), each topic's items in the reader's language and date locale, or "Nothing this weekend; next: …", and the "not here" lines. Its plain lines (`card.text`) go to Telegram and into the thread's model history. The handles of what the card shows are kept with the thread, so "move it" next points at it.
5. **Word** (`lead.ts`): one chat call with no tools, given only the card's lines, writes one or two sentences; the budget comes from the asker's `about` (an age up to 12, read by digits and the catalog's `assistant:words_age`, gets one sentence of at most 15 words) and the channel (a chat outside the app gets one). Code checks the words: no ISO date and no handle; every weekday next to a date is its own; every day named is one of the card's; every capitalised name is a word of the facts, the family or the question; no "nothing" (`assistant:words_nothing`, `words_no`, `words_topic_*`) about a topic or thing the card holds. Failing words are dropped and the check recorded (`card.lead.check`); the card stands alone and is still correct.

So the facts shown are always right; the model can only misread the question, and the card's header shows what it read. In a message of several parts each `ask` part goes through steps 2 to 5 to its own card; all other parts go together through one tool-loop call whose prompt names the parts already answered, so it acts only on the requests. The reply is the cards' openings, then the loop's words; cards are stored in `assistant_messages.card` (one card as itself, several as a list) in part order, suggestions under them, and Telegram's lines follow that order. A part never takes another down: the reply says what failed and the rest stands.

`change`, `remember` and `other` use the tool loop. A change or a thing to remember gets only the tools of what it is about (`tool-scope.ts`), because a model picks well among a few tools and badly among forty: the draft and read tools of its `topics`' areas (through `QUESTION_TOPICS`, so the assistant names no extension), of the previous answer's topics (a card, then "yes, move it"), or else of calendar, tasks and shopping; core's reads always, its note to remember only for `remember`. `other` keeps every tool. Each turn builds one tool registry from the actions:

- **Chat port.** `LlmPort.chat({ feature, role, areas, system, messages, tools, maxSteps, timeoutMs, onText, … })` runs the tool loop (AI SDK `streamText`, `stopWhen: isStepCount(maxSteps)`, tools from JSON Schema) and returns the final text, the tools used (name and outcome) and usage. The last step, and any step once 60% of `timeoutMs` is gone, gets no tools, so a model that keeps calling tools still ends with an answer instead of an empty turn or a timeout. Same switches, limits, `areas` checks and one `ai_usage` row (with areas) as `generateObject`; job handlers only.
- **Read tools** are read-only actions with `ai` hints (`ctx.actions.aiReadTools`): `calendar.findEvents`, `lists.openTasks`, `lists.shoppingList`, `records.upcoming`, the `aiContext` actions of vehicles, pets and home. **Draft tools** are the AI-proposable actions (`aiCatalog`); running one creates a draft, never a change. `external` actions are never tools. AI-facing read actions declare `ai` hints and return handles, never ids.
- **The agent never exceeds the asker.** The turn's actor is `{ kind: 'ai', mode: 'conversation', source: 'assistant', onBehalfOf, roleId }`. `access.can` for it is true only when the AI's own rules allow (view level, area not `off`) and the member's role holds the capability; for a draft, the member must hold `requires` and be able to approve (`approval.unless`) or at least propose (`core.drafts.propose`). The same check (`mayUseAsAi`) filters the tool lists and refuses a direct call in the action runner. Drafts record the AI proposer with `onBehalfOf` in `proposed_by`; approving follows the normal rules.
- **Handles.** `createHandleTable` (SDK) gives members and records short handles (`member:1`, `vehicle:2`). Tool results pass `withHandles` (typed ids become handles); inputs pass `repairInput` (handles back to ids, `null` dropped, JSON text parsed) and are refused if they still hold an id the model was never shown. Not even an id's shape reaches the model: `agentInputSchema` describes a typed-id field as a `shop_list:…` reference without its id pattern, because a model that reads the pattern invents an id that fits it. `resolveReferences` reads each typed-id field with `referenceId`: a miswritten handle (`member_3`, `3`), or in a member field a person's name, matched at home like `resolvePeople`; empty text counts as left out (models fill every field they see); anything else is refused as invented. The assistant and MCP share all of it.
- **People on a change.** A change to an existing record (a draft whose input has an `id`) takes a person field (`memberIds`, `assigneeId`, any member reference) only when the person's latest message names everyone in it: a whole word of their name, or for the asker a word for themselves (`assistant:words_self`, every installed language). A word for everyone (`assistant:words_everyone`: "everyone", "the whole family") allows an empty list or one of every member. Otherwise, and for an empty list, the field is left out and stays as it is, so a model that puts the asker into every person field never replaces who an event, task or chore is for.
- **One refusal vocabulary.** Every failed call tells the model why in Quick add's skip reasons (`RefusalReason`: `already`, `unknown`, `other_day`, `ambiguous`, `incomplete`, `not_allowed`, from `refusalOf`), as `Error (<reason>): <the shared words>. <what to do>`, worded by `refusalText`; the action's own message follows only when it explains the input (never for `not_found`, whose message may hold an id).
- **Filters say what they left out**, because models put the asker into every person filter they see. `lists.openTasks` with `assignee` keeps tasks anyone may do (as `calendar.findEvents` keeps the family's events) and counts the others' (`otherTasks`); `calendar.findEvents` with `members` counts what it left out and, when a `text` search came back empty, lists other members' matches (`forOthers`); `lists.shoppingList` refuses an unknown list name with the real names and shows an item found only on another list. Dates in results carry their weekday (`weekday`, `dueWeekday`; `runAgentTool` adds `<field>Weekday` beside any date without one), because models work weekdays out wrongly. A weekday the answer writes next to a date of another weekday ("Monday 20 October" for a Tuesday) is replaced before the answer is stored and the stream is reset (`correctWeekdays` from `@famos/time`, in the wrong word's language), unless the person wrote that mismatch and the answer quotes it. A read tool that finds nothing in its window names the next thing after it (`calendar.findEvents` `nextMatch`, `records.upcoming` `nextAfter`).
- **What is not here.** `ctx.actions.aiMissingAreas({ local })` lists the areas the AI cannot look into here, with English name, description and why (installable but not installed, turned off, closed to the AI). The prompt lists them, so a question about the flat after Home was uninstalled gets "Home is not installed here", not another area's empty answer read as "there is none".
- **Never the closest thing.** A model that cannot find what the person named tends to act on the nearest real item. Actions that change or delete an existing thing declare `targetTitle`, and an AI actor must send `label`: the name the person used, in their words. The assistant refuses a `label` whose words were never said in the conversation, by the person or in its own earlier answers ("did you mean the Dentist checkup?"), so a title found in a tool result cannot pass. The runner refuses unless the significant words of one side (letters and digits; no bracketed text, numbers or words of one or two characters; a trailing plural `s` ignored) are all whole words of the other, so "the bread" meets "Bread" with no filler-word list; the refusal names the real title, so the model tells the person it is not there. The words come from the data, never from code. Every draft of such an action is stored with the real title as `label` (a screen's draft too), so a card shows what will change. Within a turn a second change to the same target under other words is refused, and `refuseProposal` lets an action refuse a pointless AI proposal (ticking off what is ticked). `lists.shoppingList` also returns items bought in the last 7 days (`bought: true`), so a bought item is found as bought. `resolveNames` on an action turns a thing named in words (a shopping list's name) into the id before the input is judged and stored, refusing an unknown name with the real names so a model cannot invent one; it also turns a date into a repeating event's occurrence key (`calendar.changeEvent`, `calendar.deleteEvent`), refusing a day the series lacks, so a card never fails later on its key. There is no count cap on tools: one once hid a request's change tool, and the model claimed a suggestion it could not make. Narrowing (`tool-scope.ts`, above) works per area and always offers an area's read and draft tools together, because a draft tool's description sends the model to the reads. A drafted result carries `mayExist` (the action's `alreadyThere`) and a ready sentence from the card title and subject. Every failed agent call is logged with action id, error code and input field names, never their values.
- **Across turns.** The model sees only the text of earlier turns, so the handles it was shown are kept with the thread (`assistant_threads.handles`: handle, id, title) and restored next turn; the prompt lists the latest with titles, so "move it" still means the same record. A change's tools include the latest card's areas, so a follow-up crosses from the question path to the change path.
- **Untrusted content.** A tool result is shown inside a `<tool_result name="…">` block (the system prompt says it is data), cut at 4 KB, any closing tag neutralised. A turn has at most 8 steps and 12 tool calls. A call the turn already made is answered from the turn, not run again (a suggestion made twice would be two); after two such repeats, or four failed calls in a row, the tools close and the model answers with what it has. A note to remember (`core.addMemory`) must be in the person's own words: when most of its words are not in what they wrote, it is refused. Answers are stored and shown as text; contents are never logged.
- **A turn is a job.** `assistant.sendMessage` stores the question and a pending answer and enqueues `assistant.turn`; the job streams text to the asker with `assistant.delta { threadId, messageId, text }` and ends with `assistant.done { threadId, messageId, status }` and `core.conversation.answered { replyId }` (below). A failed answer keeps a code (`LlmError` codes, `no_answer` when the model ended with no words and no suggestion, `forbidden`). `assistant.summarize` folds older messages into the thread's `summary` (the last 12 stay verbatim). A turn's job limit is the sum of its steps (`budget.ts`: reading, up to four openings, the tool loop, some room), so a step's own timeout cuts a slow model off first. The last failed try always finishes the answer as failed, and `assistant.sweep` (every ten minutes) finishes as failed any answer still `pending` or `streaming` after its job's longest life (a crash), so the thread takes a new question. The AI feature id is `assistant.chat`.
- **Private realtime.** `bus.publishTo(memberId, name, payload)` / `ctx.events.emitTo(memberId, event, payload)` reach only `bus.onMember` subscribers; the realtime hub delivers them only to that member's sockets (while the member is still in the event's audience), never to displays or other members; nothing is stored or seen by `onAny`.

### Channels to a conversation

A channel outside the app (Telegram) lets a member ask a question and sends the answer back when it is written. Like shares, the conversation is a contract the host offers without knowing who provides it: `ConversationProvider` (SDK), from one extension (`conversation` in its definition and in its manifest's `provides`; the assistant):

- `requires`: the capability a member needs to ask (`assistant.use`).
- `ask(ctx, actor, { text, threadId })` → `{ threadId, replyId }`: takes the question as the member; a thread that is gone starts a new one; `conflict` while the last answer is being written.
- `answer(ctx, memberId, replyId)` → `{ status: 'done' | 'failed' | 'ai_off', text, draftIds }`, or null when the answer is not written yet or not this member's.
- When an answer is written, done or not, the provider emits `core.conversation.answered { replyId }` to the member (`emitTo`); ids only, so the event reveals nothing to whoever sees it.

Channels call `kernel.conversation.ask(memberId, question)` (the member must be active and hold `requires`, the provider on; otherwise `feature_off` or `forbidden`, and Telegram shares typed text instead) and `kernel.conversation.answer(memberId, replyId)` when the event arrives. The channel keeps which reply it waits for; the answer stays in the provider's tables.

### Member memory and addressed drafts

Core holds memory (`packages/core/src/memory.ts`); the assistant extension only carries it. Assistants never message each other or other members, because negotiating agents bring loops, hidden decisions and leaks (one could reveal what the other's person may not see). To involve someone, a member or an agent creates a task or a draft for them, and they act on it in the app.

- **Addressed drafts.** `ai: { addressToMember: true }` on an action makes the assistant's proposal a draft with `core_drafts.for_member` set to the member it works for. Only that member sees it (`core.listDrafts`, the waiting count) or may approve, reject or undo it (`not_found` for anyone else, admins and replays included); the addressee needs no `core.drafts.approve` for their own. No "draft waiting" notification is sent, and auto-approval skips it. `core.addMemory` uses it, so the approver is always the person the action acts for.
- **Drafts belong to the person behind them.** For every AI draft that person is `onBehalfOf` (assistant, MCP) or `DraftMeta.forMember` (Inbox). After auto-approval is checked, the runner stores `for_member` = that person when they are active and could decide the draft themselves (`core.drafts.approve` plus the action's `requires` and `approval.unless`; `deciderBehind`); nobody is told. Otherwise (a supervised member) the draft is unaddressed and the "draft waiting" notice goes to the approvers except that person. `ActionRunner.mayDecide(draft, actor)` answers the same for an existing draft, and the read action `core.decidableSources` lists which items of a source (`inbox`) have a draft the member may decide, so an extension can show an item to its decider without reading `core_drafts`. Telegram buttons list only drafts the recipient may decide.
- **Memory.** `core_member_memory` (text up to 280 characters, at most 100 per member). `core.addMemory` / `updateMemory` / `deleteMemory` act on the caller's own notes only; `core.listMyMemories` lists them. `core.recallMemories` (read-only, no `ai` hints, so never a tool) returns the caller's notes, or those of the member the AI works for in the app's conversation (`mode: 'conversation'`); the turn job puts the newest 20 (at most 1,500 characters) in the system prompt of that member's own threads, only when `policy.sendPeople` allows. The Inbox and MCP never read them.
- **In the assistant.** The tool wrapper hides `source` from the model's schema and sets it itself (`ai`).

### Auto-approval

Auto-approval lets a family approve routine suggestions (shopping items, tasks) automatically. It is one small setting in core (`packages/core/src/auto-approval.ts`), not a rules engine, because triggers, predicates and mapped inputs are attack surface and can loop, and the assistant and outside agents already cover "do X when Y" as drafts.

- **Opt-in where the action is defined.** `autoApprove: { label, capabilities }` on `defineAction` (`label` is an i18n key naming what is approved; `capabilities` are those a proposer may be required to hold, the first is the default). The registry refuses it on read-only, `external`, `core.*` and sensitive-extension actions and on unknown capabilities. `lists.addShoppingItems` and `lists.addTask` opt in.
- **Storage.** One `core_settings` row (`core.autoApproval`): action id → `{ proposerCapability, enabledBy, enabledAt }`. `core_drafts.auto_approved` marks drafts approved this way (`decided_by` is the member who enabled the setting); the draft API exposes `autoApproved` and `decidedBy`.
- **Setting it.** Action `core.setAutoApproval` (`{ actionId, setting | null }`) and route `core.listAutoApproval` (opted-in actions, their capability choices and current value), both under `core.autoApprove.manage` (critical: admins only). Settings → AI → Auto-approval.
- **Where approval happens.** Creating a draft for an opted-in action, the runner checks the setting and the proposer in the draft's own transaction: only AI drafts qualify, and the person they were proposed for (`onBehalfOf`, or `DraftMeta.forMember` for the Inbox) must be active and hold `proposerCapability` (through the role). Drafts a person made, drafts addressed to one member, system and display drafts never qualify. A qualifying draft enqueues job `core.autoApprove` (deduped by draft) in the same transaction instead of the "draft waiting" notification; the queue is the outbox, so a crash loses nothing.
- **The job** re-checks everything, then calls `ActionRunner.approveDraft(draftId, enabler, undefined, { auto: true })` as the enabling member, so the runner enforces that member's capabilities at that moment. It is idempotent: a draft no longer `pending` does nothing. If it cannot approve (the enabler is archived, no longer holds `core.autoApprove.manage`, or the runner answers `forbidden`), it stops the setting (removes the row if `enabledAt` is unchanged), notifies the enabler (or, when they are gone, everyone who manages auto-approval; kind `core.autoApprovalStopped`, deduped) and sends the usual "draft waiting" notice, so the suggestion waits for a person.
- **Visible and reversible.** An auto-approved draft stays visible as approved by the setting, and undo works as for any approval (the draft is `applied` with its result).
- **No loops by construction.** Nothing publishes on a draft's approval except the usual UI events, and no handler reacts to them with actions.

### MCP server: bring your own agent

People with a personal agent (Claude Desktop, Claude Code, Hermes Agent, an IDE) would rather connect it than use a second assistant. FamilyOS is data and actions, not an agent, so the fitting protocol is the Model Context Protocol, not an agent-to-agent one: an outside agent uses the assistant's tools through `/mcp` (`apps/server/src/mcp/`, next to the API; no extension, no new core concept besides tokens) as one member, sees only what that member may see in the areas open to the AI, and every change is a draft the member approves. A person's preferences live in their own agent's memory; FamilyOS's member memory is never given to it, and FamilyOS never calls out to other agents.

- **Server.** `@modelcontextprotocol/server` 2.3.1 (`createMcpHandler`: spec 2026-07-28 per-request envelope, `server/discover`, and the SDK's stateless fallback for the 2025 handshake; GET/DELETE session operations answer 405) with `@modelcontextprotocol/hono` 2.0.2 (`createMcpHonoApp` parses the JSON body, capped at 256 KB). A new `McpServer` is built for every request from the token's principal: no sessions, nothing kept between requests.
- **Tokens.** Personal API tokens (the simple path) and, when an admin allows it, OAuth sign-in (below). `core_api_tokens`: id `api_token_…`, member, name, SHA-256 of a 32-byte random secret prefixed `famos_`, scope `read|read_write`, expiry (default 90 days, at most 365), `last_used_at` (at most hourly), `revoked_at`. `kernel.apiTokens` creates and lists them through routes under `/api/v1/mcp/` (creating shows the secret once, so it is a route, like push subscriptions, that records itself in the audit log); revoking is `core.revokeApiToken` (one's own, or anyone's with `core.ai.manage`). Creating needs `core.mcp.use` (level use, but not held by supervised members by default, because a token carries what they can see to a provider the family never chose); listing or revoking everyone's needs `core.ai.manage`. Only a password sign-in creates one (`assertFullSignIn`, SDK): a PIN is short and works on shared devices, so it never mints a credential that works away from them; the same rule guards calendar feeds and Telegram links, and `/me` says `fullSignIn` so the UI shows a note instead of the button. Signing out everywhere, a new password and archiving a member end credentials durably: in one transaction core revokes the member's tokens and enqueues `core.endCredentials` (before the sessions end, so a failure leaves the person signed in to try again); the job calls every extension's `endCredentials(ctx, memberId)` hook (the calendar's feeds) and retries with backoff until it succeeds, so hooks are idempotent. The feed route's owner check is the backstop while the job is pending. `last_used_at` is written by `touch` after the `core.mcp.use` check, never by `authenticate`. The switch is the core setting `mcp` (`{ enabled }`, default off), changed with `core.setMcpEnabled` (`core.ai.manage`), read by `/mcp` on every request.
- **Request path** (middleware on the parent app, before the body is read): switch on, else 404; no query parameter that looks like a token or starts with `famos_` (401); `Authorization: Bearer famos_…` only (cookies are never read, so there is nothing to forge and the CSRF check, which covers `/api/v1`, does not apply); token known, not revoked, not expired, member active (401 with a JSON-RPC error and `WWW-Authenticate`); the member's role still holds `core.mcp.use` (403); 60 requests per minute per token (429, `Retry-After`); 30 failed attempts per minute per client address (429).
- **Tools.** The actor is `{ kind: 'ai', mode: 'agent', source: 'mcp', onBehalfOf, roleId, scope }` (`mcpActor`); the token's `scope` is on it so the runner refuses a change from a `read` token even if a tool list were built wrongly. Tools are rebuilt per request with `aiReadTools` (and `aiCatalog` for `read_write` tokens) with `local: false`, so areas that are off or local-only are absent, because the client is outside the house; `conversationOnly` actions (personal memory) are offered to `mode: 'conversation'` only. A call runs the same `runAgentTool` (SDK) as the assistant: handles to ids, the action runner (capabilities, sandbox, approval), a draft with `sourceKind: 'mcp'`, the result back to handles inside a `<tool_result>` block. An extra read tool `family_listPeople` exists when **Send names and descriptions** is on and the token's owner holds `core.members.view`. Annotations: read tools `readOnlyHint: true`; draft tools `readOnlyHint: false, destructiveHint: false, idempotentHint: false`; all `openWorldHint: false`; a draft tool's description says it creates a suggestion a family member approves.
- **Stateless handles.** MCP has no turn to number records in, so a handle is `<kind>:<first 10 hex digits of HMAC-SHA256(tokenId, id)>`: stable for one token across requests, different for another, never an id. The mapping back is stored per token in `core_api_token_handles` (newest 5,000 kept; removed with the token). Before a call the handles in its arguments are loaded; an id or handle the token was never shown is refused like an invented id. Handles are written after each call.
- **Audit.** Each `tools/call` writes one `ai_usage` row (feature `mcp`, provider `MCP`, model = the token's name, areas, member, error code `rejected` when the call failed); AI activity shows it without content.

### OAuth sign-in for AI apps

Apps such as Claude and ChatGPT have no place for a key: they find an authorization server from the 401 of `/mcp`, send the person to it and keep refreshable tokens. FamilyOS is its own minimal authorization server (`packages/core/src/oauth.ts` for rules and storage, `apps/server/src/http/oauth*.ts` for the endpoints), off by default behind the admin switches of `core.setMcpOAuth` (sign-in, self-registration, plain http on a home network).

- **Address.** The issuer, the metadata documents and every redirect come from `FAMOS_BASE_URL` only, never from a request header, and it must be an origin without a path, https unless an admin allowed plain http for a home network. While OAuth or MCP is off, every OAuth endpoint and both metadata documents answer 404, like `/mcp`.
- **Endpoints.** `/.well-known/oauth-protected-resource[/mcp]` and `/.well-known/oauth-authorization-server`; `GET /oauth/authorize` checks the app and its return address before any redirect (a problem it cannot report to a trusted address is a plain page), stores a pending request and sends the browser to the web app's consent page `/connect/<id>`; `POST /oauth/token` (authorization code with PKCE S256, and refresh) and `POST /oauth/revoke` (always 200). Consent is never skipped, whatever `prompt` says.
- **Deciding** is a session route (`GET /api/v1/oauth/requests/{id}`, `POST …/approve`, `POST …/deny`): the person is always the one signed in, with a password (`assertFullSignIn`) and `core.mcp.use`; a display, an app and a PIN session are refused. The person may grant less than asked (`familyos.read`, or `familyos.suggest`, which adds `read_write`), never more. Connecting again replaces the earlier grant when the app exchanges its new code; an approval the app never comes back for leaves the earlier sign-in working.
- **Clients.** Pre-registered clients (Home Assistant, which cannot register itself and sends no PKCE) are set up by a member through `POST /api/v1/mcp/oauth-clients` (secret shown once; a known app is a `preset` from the table in `apps/server/src/http/oauth-presets.ts`: its name, return addresses and whether it can do PKCE, so the route names no app) and can be approved only by that member. Settings reads them with `GET /api/v1/mcp/oauth-clients` and the switches with `GET /api/v1/mcp/oauth`; removing one is `core.deleteOAuthClient`.
- **Apps that introduce themselves** are of two kinds, both public clients (no secret, PKCE S256 always) limited to `familyos.*` scopes.
  - A `client_id` that is an https address (in its one normalised form, with a path, no login or fragment) names a metadata document. `/oauth/authorize` reads it through `ctx.http`'s guard (https, public addresses only, no redirects at all (`redirects: 'none'`), 5 KB, 5 s), as a bounded read a person is waiting for, never inside a transaction. The document's `client_id` must equal its address exactly, it may not ask for a secret, and the requested return address must be one of its `redirect_uris` (https or a device address). It is kept as a `metadata` client row (`metadata_fetched_at`, `metadata_etag`) for as long as its `Cache-Control` says, at least five minutes and at most a day, then asked again with the validator; when it cannot be read the request is refused.
  - `POST /oauth/register` (RFC 7591) exists only while the admin switch is on (404 and no `registration_endpoint` otherwise): public clients with https or device return addresses, a name cleaned to 60 printable characters, every other field dropped; ten registrations an hour per client address (an IPv6 /64 counts as one) and at most 50 waiting `dynamic` clients; no audit row, because no person is acting.
  - Waiting `dynamic` and `metadata` clients nobody approved are purged after a day by the daily cleanup. The consent page tells the three kinds apart (set up by you, identified by its address, registered itself), always shows where the answer goes back to, and warns when an address-named app sends it to another host. A device return address (`localhost`, `127.0.0.1`, `[::1]`) matches exactly except the port.
- **Storage.** `core_oauth_clients`, `core_oauth_requests`, `core_oauth_codes`, `core_oauth_tokens`. A grant is a `core_api_tokens` row with `oauth_client_id`, so listing and revoking it (`core.revokeApiToken`), handles, scope and actor are those of a personal key; its expiry slides to 90 days after last use. Access tokens (`famos_at_…`, one hour) and refresh tokens (`famos_rt_…`, rotating; a replay beyond a short grace ends the grant) are opaque and kept only as SHA-256; there are no JWTs.
- **Rule 13 holds.** An OAuth client is not a person or an app: its token is the same AI actor as a personal key for the member who approved it. FamilyOS accepts at no door a token another issuer made. The member is notified of every new connection, with a way to revoke it.

### Digests: the facts of a question

A model choosing its own reads over many tools slips in ways no prompt rule fixes: it searches by the person's words and misses the event under another title, reads an empty result as "there is none", drops what a tool did not return. So code fetches the facts a question needs, one **digest** per topic, and the model only reads the question and words the answer.

- **Contract** (`@famos/sdk`, `digest.ts`). `defineDigest({ id, topic, title, description, requires, run })` is a read-only action with the digest's own Zod shapes and `ai: { digest: topic }`. The topics are `QUESTION_TOPICS` (calendar, tasks, shopping, meals, chores, records, pets, vehicles, home, board, suggestions), each kept by one area. The registry refuses a digest for a topic another area keeps, two digests for one topic, and a digest with other shapes.
  - Input `DigestInputSchema`: `{ from, to, memberIds?, about? }`, plain dates of the family's time zone, at most 62 days.
  - Output `DigestOutputSchema`: `{ items, truncated, nextAfter?, hidden? }`.
  - A `DigestItem` is `{ handle, kind, title, date, time?, end?, allDay?, people, notes?, status?, extra?, href? }`. `href` is an in-app path to the item from the extension's own page routes (`/calendar?event=<id>&on=<day>`, `/lists/tasks?task=<id>`, a record's stored page); a model never reads a digest, and `readableOutput` drops every `href` as well, so a model sees no id and no address. `handle` is the typed id, which the host turns into a handle as for every AI read; `people` are member ids (empty: everyone, or anyone); notes are cut at 300 characters; `extra` holds a few facts as text (a place, a meal slot, a duty's record, a list's count). `date` is when it happens or is due (something late keeps its due day); what stands over days (a board note, a waiting suggestion, a shopping list) has the first span day it stands on.
- **Rules every digest keeps**, with the SDK's helpers:
  - span bounds count both days, and repeating things are expanded on each of their dates in it;
  - `memberIds` keep what is for one of them and what is for everyone (`digestForPeople`), as person filters do everywhere;
  - `about` words only rank: items meeting more of them come first, the rest follow in order, none is left out (`rankDigest`, by the read tools' word forms), because the person's words need not be the title's;
  - the list is cut after ranking at 60 items (`truncated`), so what the words name stays in;
  - when the span holds nothing, `nextAfter` is the first item after it for the same people (`digestOf` asks only then);
  - something late counts when the span holds today; a date that only passes (a warranty ends) is never late.
- **The digests**: `calendar.digest` (events with notes, place and tags, subscribed calendars included; a timed event today says whether it is over, on or ahead); `lists.tasksDigest` (tasks due and, in a span not yet over, the open undated ones last, marked `undated`) and `lists.shoppingDigest` (one item per list with things to buy: its count and first thing; span and people never drop one); `chores.digest` (each turn and whose it is or will be: fixed and round robin known ahead, least done names the whole rotation); `kitchen.digest` (planned meals; a dinner elsewhere is a calendar event); `records.digest` (every duty) and `pets.digest`, `vehicles.digest`, `home.digest` (their own record kinds, through `records.dueBetween`; home services stay out, as from every AI read); `board.digest` (notes up on some day of the span, pinned first); `core.suggestionsDigest` (what waits for the asker to decide, wherever made, and their own waiting on someone else, newest first, at most 15; span and people never drop one).
- **What the AI may read.** Code finds the digests with `ctx.actions.aiDigests({ local, actor })`, filtered like the read tools: extensions on, areas open to the AI (local-only ones only for a local model), actions the asker may run. Digests are never read tools: the model does not choose them. They are invoked as the AI actor, so an off area refuses, and a local-only area's digest refuses an actor whose model is not local. A digest spanning several areas leaves out those the AI may not read and counts them in `hidden` (a pet's duty in `records.digest` when pets are off for the AI; a suggestion of a closed area in `core.suggestionsDigest`), so the answer can say there is more it cannot see.

### Family search

Read tools cannot find "the paper about the boiler warranty" when the words differ, and meaning matters for languages with rich word endings, so core finds things by meaning with embeddings. There is no vector extension: a family has at most tens of thousands of short texts, exact scoring is fast at that size, and a native SQLite extension would have to be built for arm64. Embedding sends family text to a model, so it follows the AI sandbox like every other call. Without an `embed` model nothing is indexed and nothing changes. Code: `packages/core/src/search.ts`, `LlmPort.embed` in `@famos/adapters/llm-aisdk`.

- **Port.** `LlmPort.embed({ feature, area, texts, timeoutMs, memberId?, jobId? })` returns one `Float32Array` per text, the model key (`<provider id>:<model>`) and the dimensions, using the AI SDK's `embedMany` (`POST {baseUrl}/embeddings`; OpenAI, OpenRouter, Ollama, any compatible server) for the `embed` role. Same rules as every call (switches, limits, one `ai_usage` row with role `embed`, `LlmError` codes) and the area check: Off refuses (`disabled`), Local only refuses unless the role's provider is local (`local_required`), with no fallback. `LlmPolicy.model` carries the model key, so core sees a model change. The test fake (`createFakeLlm`) embeds a hashed bag of words and checks areas the same way; `embeddingContract` is the port's contract suite.
- **What is indexed.** An extension opts in with `ai: { index: { kinds, list } }` (SDK `AiIndex`). Each kind (`<extension>.<kind>`, e.g. `kitchen.recipe`) names the capability that lets people find it, optionally a `viewAll` capability (for a kind whose items are otherwise only the owner's), and `load(ctx, id)`: one entity as `{ title, text, href, ownerMemberId?, capability? }` or null (gone, archived, filed, dismissed). `list(ctx, cursor)` walks every entity in pages, for rebuilds. After each change, in its transaction, the extension calls `uow.ai.reindex(kind, id)` (enqueues `core.embed`, deduplicated per kind and id) or `uow.ai.remove(kind, id)` (deletes the chunks at once); jobs and handlers use `ctx.ai`. Wired: Inbox items (summary and prepared text, not items filed by hand), kitchen recipes, home things and services (never serial or account numbers), calendar events (title, place, notes), records obligations and papers' names and labels (a paper's own text stays out, since filing keeps the AI from reading it). An obligation's audience is its area's capability, and a paper's area is its record's; search honours both like the AI context does.
- **Chunks.** Core cuts text into pieces of about 800 characters with 100 characters of overlap (paragraph, sentence or word boundaries; at most 40 per entity), prefixes each with the title, hashes it and embeds only pieces whose hash or model changed (`core_embeddings`: extension, kind, id, capability, owner, title, href, a 240-character snippet, model, dimensions, hash, chunk index, the vector as unit-length little-endian float32, time). A change arriving while the model works is deduplicated into the running job, which reads the entity again before it finishes. An error a person must fix (`LlmError` not retryable: no model, bad key, limit) is logged, kept in the search state (`core_settings` key `search_index`, `GET /api/v1/core/search/status`) and not retried in a loop; retryable ones use the queue's backoff.
- **Settings follow.** `kernel.reconcileSearch()` enqueues `core.embedSync` at start and after a change of an AI area, feature, model or provider (a kernel listener on `core.aiAreas.changed` and `core.aiModels.changed`, emitted by the actions and the key route). The sync deletes the chunks of an area that is Off, or Local only while the `embed` provider is not local; every other area not built with the current model gets `core.embedRebuild` (long lane), which walks the extension's `list`, embeds what is needed and then drops older models' chunks. With no `embed` model (or AI off) the built state is forgotten, so a later model reads everything again (unchanged text costs nothing).
- **Asking.** `core.searchFamily` is a read-only action with `ai` hints (a read tool for the assistant and MCP while an `embed` model is set) and the route `GET /api/v1/core/search?q=&limit=` for people (409 `not_configured` without a model). It needs a person: an AI with nobody to work for is refused. The question is embedded in the action's `prepare` step, after the permission checks and before the transaction opens, because a unit of work holds the one database connection. This is the one model call inside an HTTP (or MCP) request, with a 10 s timeout: a deliberate exception for the short question of a person who is waiting. Then, in SQL before any scoring: model key and dimensions match, the kind's area is open to the asker (not Off; Local only only for an AI whose model is local, `Actor.local`), the person (or the AI's member) holds the kind's and the row's capability, and the row is theirs (`owner_member_id` null, their own, or the kind's `viewAll`). Rows are read in pages of 2,000 and scored by dot product in TypeScript (unit vectors), keeping the best 5 × limit chunks; results are one per entity, best chunk first, positive score only. A result is `{ id, kind, extension, title, snippet, href }`; for the AI `href` is null and `id` becomes a handle (`withHandles`), so the model opens the record with the area's own read tool and the permission check runs again.
- **Cost.** Scoring 50,000 × 768 floats takes about 40 ms in Node on a laptop (`FAMOS_BENCH=1 pnpm vitest run packages/core/test/search-bench.test.ts`); reading them from SQLite in pages takes about 750 ms, so loading, not arithmetic, is the cost at that size. Beyond ~200,000 chunks, or when a search passes 200 ms on the target hardware, keep the vectors in memory or move scoring to `sqlite-vec` behind the same table shape.

## 12. Data, migrations and backups

- **SQLite only**, WAL mode, one writer connection, `busy_timeout`, `foreign_keys = ON`, STRICT tables. One family per installation means tiny write concurrency and little data; one database file makes installation one container and backup one consistent snapshot, with no per-dialect migrations or test matrix (Ghost, n8n and Directus paid for several databases in migrations, tests and semantic drift). The API cannot scale horizontally, which a family does not need.
- Timestamps are epoch milliseconds (UTC); the family time zone is a setting. Date and recurrence math happens in TypeScript, not SQL.
- **Time and recurrence.** Every date computation uses the Temporal API (`temporal-polyfill`) through `@famos/time`, the one tested place for time math; extensions call it instead of hand-rolling dates. Timed instants are epoch milliseconds with the IANA zone beside them; all-day dates are `YYYY-MM-DD` strings, never converted to instants, so they do not shift when viewed elsewhere. Recurrence is RFC 5545 `RRULE` text plus `EXDATE`s (CalDAV-compatible), expanded with `rrule-temporal` in the event's time zone, which handles daylight-saving changes. The family has one time zone; every expansion and "today" uses it unless an event carries its own.
- **Forward-only migrations**, hand-written with Kysely, never generated, so every schema change is explicit and reviewed. There is no `down`: rolling back an upgrade means restoring the automatic pre-migration backup. Core and each adapter or extension are a scope with their own folder, recorded in one `_migrations` table; core migrates first, then extensions in dependency order. An extension's migrations run with its scoped database, so they create and change only tables with its prefix. Out-of-order migrations are rejected (`OutOfOrderMigrationError`). A released migration is never edited; a change is a new migration.
- **Expand-only** within a major version: add tables, or nullable or defaulted columns. Renames and drops (of columns, tables or API fields) happen only in a major release, after deprecation, so upgrades never break an installation and pending drafts and stored outputs keep validating. Unused columns may stay until the next major.
- On startup: a scope with migrations the code does not know means the database is newer than the code, and the server refuses to start (`SchemaNewerThanCodeError`); a whole scope the code does not know is an extension that is not installed, reported and left untouched. Otherwise take an automatic pre-migration backup, then migrate.
- **Supported upgrade window**: any release in the previous major version. Migrations are squashed only at major versions, announced in advance.
- **Backups**: `famos-<timestamp>.tar` holding `manifest.json` (format, app version, schema versions, created at, checksums), a consistent `VACUUM INTO` snapshot, the `files/` directory, and the installed language packs, theme packs and extension store (`languages/`, `themes/`, `extensions/`, each when present; uploads not yet installed are left out). The format stays 1: these folders are only added, and a backup without one restores, leaving that folder as it is. On restore, a scope whose extension package the backup carries is not compared with this server's migrations (the package comes back and is checked at the next start); an installed extension whose package is in neither the backup nor the server is refused at start, not fatal. Nightly schedule with retention; restore from the command line only (`restore <file>`, server stopped). Extensions take part in a restore only through `onRestore`.

  **Restore hygiene.** A restore never leaves the data half replaced: it first copies the backup's database, files and packs next to where they live (`*.restoring`), so a full disk or a bad file fails with the live data untouched; then it moves each existing item aside and renames its replacement in, and when any step fails (the marker included) it renames everything back. A restore copies the database back as it was, which would also bring back what the family ended since: sessions, an old password, revoked keys and devices, archived members, stopped feeds, unlinked chats, narrowed access. So `restoreBackup` moves the old database aside with its journal files (`famos.db.pre-restore-<time>`, `…-wal`, `…-shm`, so it opens with every committed change) and writes `restore-pending.json` beside it. The first start after (`apps/server/src/restore-pending.ts`, after migrations and `kernel.start()`, before anything serves) calls `kernel.reconcileRestore(previous, hostSteps)` and removes the marker only on success. Every step is idempotent, carries only what ends access, never what grants it, and matches by id (a row the old database lacks stays as restored):
  - all sessions are deleted (`IdentityAdmin.endAllSessions`; nothing listens yet, so no socket of the old data is open);
  - `revoked_at` of keys and devices and `archived_at` of members are carried (a newly archived member goes through an archive's end of credentials: keys revoked, `core.endCredentials` queued, logins removed); API tokens are not paused, since nothing a person revoked comes back;
  - newer password and PIN hashes of a login both databases have are taken (`IdentityAdmin.carryNewerLogins`); the adapter carries Telegram unlinks for members the old database knows;
  - every extension's `onRestore(ctx)` runs with `ctx.previous`, its own tables in the old database, read-only (the calendar stops feeds stopped since);
  - narrowed access (`carryNarrowerAccess` in `packages/core/src/restore.ts`): for each custom role in both databases the capabilities both give are kept (judged by `roleGrants`, never by names); each member in both keeps the role that grants less, and when each of two roles grants something the other does not, gets the role granting exactly what both give if one exists, else keeps their pre-restore role and is logged as undecided. Promotions and widenings after the backup are lost, like the rest of that day; members added after it are not brought back. A custom role the backup lacks comes along only when a member demoted into it needs it.

  A restore never leaves the family without a holder of `core.settings.manage`: when the backup and these carries leave nobody, the members who held it before the restore, were not archived and are in the backup keep their earlier role and active state (`access.keptForAdmin`). Because the restore runs from the command line with the server stopped, no signed-in person is identifiable and nobody else is exempted. Admins get `core.backupRestored` with how many ended decisions stayed, and a second one with how many people kept their current access. A failing extension hook is logged and stops neither the others nor the start; a failure in core's steps leaves the marker and stops the start (the server does not serve with the restored sessions alive), so the next start runs them again.

  **Remote copies and encryption.** Nightly backups on the data's disk do not survive a failing SD card or a stolen device, so backups can be copied elsewhere, encrypted with `age` (a small, well-specified format with a standard CLI, so a backup stays readable with standard tools). `@famos/adapters/backup` (migration scope `backup`) holds the encryption choice, the targets and the upload. After each nightly or manual backup, one `backup.upload` job per enabled target is enqueued (deduplicated by target and backup name); `backup.run` ("Back up now", the action `core.runBackup`, which queues it deduplicated in the unit of work) writes the backup in the worker, never in an HTTP request. Actions: choosing no or public-key encryption (`core.setBackupEncryption`), a target's name, retention and switch (`core.updateBackupTarget`), removing a target (`core.deleteBackupTarget`). Routes that record themselves in the audit log: the passphrase (`PUT /api/v1/backups/encryption/passphrase`), adding a target and its address and keys (`PUT /api/v1/backups/targets/{id}/config`), and saving the server's key file (`POST /api/v1/backups/key-file`). The key file is the master key, so it needs `core.settings.manage`, a person at a password sign-in and the password typed again (checked by the identity adapter against the sign-in locks), and answers as an attachment, `no-store` and `nosniff`.
  These are *infrastructure jobs*, handed to the kernel through `KernelOptions.infrastructureJobs`, next to `infrastructureMigrations`. The upload streams the local `.tar` through `age` (passphrase via scrypt, or an `age1…` recipient) to a `BackupTarget` (`put`, `list`, `delete`, `test`): S3-compatible (`aws4fetch` for SigV4, our own single and 8 MiB multipart upload, so memory stays near one part) or WebDAV (plain `fetch`, `Content-Length` known because age's output size is computable). Targets use `fetch`, not the guarded HTTP port: an admin configures them, they may live on the LAN, need PUT/PROPFIND with large streamed bodies and send credentials, so redirects are refused. Backups kept on the server stay unencrypted; nothing is uploaded until the admin has chosen an encryption mode (an explicit "none" included). Retries back off up to 5 attempts; on the last (or a non-retryable error) admins get `core.backupFailed` once and the target shows the result code. An upload holds the `long` lane (up to 50 minutes), so the default lane's reminders and notifications are not delayed. `restore` accepts `.tar.age` (passphrase from `FAMOS_BACKUP_PASSPHRASE` or a prompt, or `--identity`), decrypts streaming into a temporary folder in the data directory, then restores as usual. `FAMOS_SECRET` and the passphrase are never inside a backup.

### Connected apps

Programs outside FamilyOS (Home Assistant, scripts, Node-RED, Shortcuts) read and change family data with a key of their own. They are neither people nor the AI, so they are their own principal: an admin registers an **app** with a role (built-in or custom), a **mode** (`apply`: its changes follow its role; `suggest`: every change is a draft a person approves) and the members it **may act for**.

- **Tables.** `core_apps` (id `app_…`, name, `role_id`, `mode`, `acts_for` as a JSON list of member ids, `created_by`, `revoked_at`, `paused_at`) and `core_app_tokens` (id `app_token_…`, `app_id`, name, SHA-256 of a 32-byte secret with the prefix `famos_`, `expires_at`, `last_used_at`, `revoked_at`). Keys are a sibling table, not a column on `core_api_tokens`: a personal key belongs to a member and carries a scope and per-key handles, an app key never does, and a hash lookup in one table never yields the other kind of caller, so an app key cannot open `/mcp` nor a personal key the apps' door. Keys are long-lived: no expiry unless the admin sets one (a 90-day default would silently stop Home Assistant), at most five live keys per app so a rotation is "add one, switch over, revoke the old", and the page warns two weeks before an expiry.
- **Management.** An app's record is changed by actions (`core.createApp`, `core.updateApp`, `core.pauseApp`, `core.resumeApp`, `core.revokeApp`, `core.revokeAppToken`), so the runner decides who may and the audit log names the app or key. Minting a key is a route (`POST /api/v1/apps/{appId}/tokens`), since its secret is shown once and an action's answer is kept for replays; the page runs it right after `core.createApp` for the first key. All of it needs `core.apps.manage` (critical, so admins only and never on a PIN sign-in) and `assertFullSignIn`. Lists never carry a secret.
- **Authenticating.** `kernel.apps.authenticate(secret, onBehalfOf)` returns the app actor, or, when `X-FamilyOS-On-Behalf-Of` names a member, the member with `via`. The member must be on the app's list and active, otherwise the call throws `forbidden` (never quietly served as the app itself, so a script is never "nobody" by mistake); the member's role is read on every request, so a lowered role or an archive applies at once. A revoked or paused app, a revoked or expired key, and an unknown key are all `null`. Authenticating changes nothing; `touch` records the use after the request was permitted.
- **Acting.** Decisions are the action runner's, as for a person (see §7); the member through an app is `personPresent` false, so deciding, editing or withdrawing drafts, credentials, devices, sessions, auto-approval, roles, members, extensions and managing apps are refused, in the runner and in every service that asks for a person present. An action run inside another one is decided for the same actor (`nested_needs_approval`). Idempotency keys are per principal (§14), so Home Assistant and a member never share a key space. The audit log stores the whole actor (the app, the member and the mode), a draft stores it as its proposer and the draft list adds the app's current name (`app`), so cards say "Home Assistant" or "Leo via Home Assistant"; a draft by an app alone is addressed to nobody, so the approvers see it.
- **Restore.** A restore pauses every live app (`paused_at`, in `reconcileRestore`) and carries revoked apps and keys over, so an old backup never brings a leaked key back to life; an admin resumes the apps they trust, and the admins who may manage apps get a notification. Personal keys keep their existing handling.
- **MCP keys are not folded into apps.** A personal key is bound to its member, shares that member's `core.mcp.use` check and per-token handles, and is enforced as `{ kind: 'ai', mode: 'agent', scope }` by the runner (suggest-only by construction); as suggest-mode apps they would change actor, idempotency principal, handles and audit rows for no new protection. They are listed beside the apps (Settings → Connected apps).
- **Threat model.** A stolen app key does what the app's role allows and no more: never a critical capability, never deciding a suggestion, never creating a credential or managing people, devices or roles; it is revoked at once, its last use is shown, and a restore pauses it. An app naming a member is limited to its list and to what both hold. An AI behind an app is contained by `mode: 'suggest'`. The apps' door takes no cookie, so it is no CSRF target, and a bearer is refused at the app's own API.

## 13. Auth and RBAC

- The first-run wizard creates the first admin.
- **Roles and capabilities.** Households differ (a couple of equals, an adult child running it for their parents, a babysitter), so FamilyOS assumes no household shape, and what a person may do (security) is kept apart from who they are (context for the AI). Core and extensions declare capabilities (`calendar.edit`, `core.drafts.approve` …) with a level (`view`, `use`, `edit`, `manage`); core maps levels to the built-in roles Admin, Member, Supervised and Guest. Custom roles are a built-in base plus overrides, stored in `core_roles`. Code only asks `can(actor, capability)`, never compares role names: routes declare `requires` (checked by the HTTP adapter), actions declare `requires` and/or `approval: { unless }` (checked by the action runner; people without the capability propose a draft). An extension may declare defaults that only remove grants its level gives (§6). Members carry an optional free-text `about` ("9 years old", "Sam's partner", "visits on Tuesdays"), shown to the AI with the name instead of a role label; it has no security meaning.

  | Level | For | Admin | Member | Supervised | Guest |
  |---|---|---|---|---|---|
  | `view` | Seeing | ✓ | ✓ | ✓ | ✓ |
  | `use` | Doing one's own things (complete a task, share) | ✓ | ✓ | ✓ | – |
  | `edit` | Changing shared data | ✓ | ✓ | – (proposes a draft) | – |
  | `manage` | An extension's settings | ✓ | – | – | – |

  One table from levels to roles makes every extension behave alike, and a new built-in role needs one change. Capability ids are namespaced by their owner (`calendar.…`); the registry refuses other ids and routes or actions that name an undeclared capability, so a typo fails at startup instead of silently allowing everyone. A capability added later takes the base role's default, so custom roles stay correct; overrides of capabilities not registered now (an extension turned off) are kept and apply again when it returns.
- **Guardrails.** At least one admin always exists. The Admin role cannot be edited and is not a base for custom roles. Critical capabilities (`core.members.manage`, `core.roles.manage`, `core.devices.manage`, `core.ai.manage`, `core.features.manage`, `core.extensions.manage`, `core.settings.manage`, `core.autoApprove.manage`, `core.apps.manage`) exist only in the Admin role. Only admins assign roles, so nobody grants a capability they do not hold. A PIN sign-in never holds a critical capability, whatever the role: the session resolves to a member actor marked `pin`, and `access.can` refuses critical capabilities to it (so `core.getMe` lists none), so a guessed PIN never yields administration.
- **Sign-in.** Any member may have an email + password, a PIN, or both (set on the members page; `IdentityAdmin.signInMethods` says which exist, never the secrets). People with a PIN whose role holds `core.signIn.pin` (every built-in role; a custom role may drop it) pick their profile and enter the PIN on family devices (rate-limited, constant-time check, rechecked against the current role on every sign-in). Wrong secrets are counted in memory (a restart clears them), with IPv6 addresses keyed by their /64 and every map capped:
  - a PIN locks the account after 5 (it is only tried on family devices);
  - a password locks only the address that sent 5 for that account, so a stranger cannot keep a person out (OWASP's device-cookie pattern), and an account-wide backstop (20 in an hour) refuses only devices the family does not know (like Entra's smart lockout).

  A known device is a family device or a browser holding the account's entry in the `famos_signed_in` cookie (HttpOnly, SameSite=Strict, path `/api/auth`, an HMAC with a key derived from `FAMOS_SECRET`, naming the account by a keyed hash), set on every successful password sign-in. The HTTP layer decides it and tells the identity adapter in the `x-famos-known-device` header, which it strips from every incoming request first, as it does the client address.
- **Trusted family devices.** An admin marks a device (a kitchen tablet, a shared phone) as a family device; it gets a random token in an httpOnly cookie (`famos_device`, ~400 days, refreshed on use), and only the token's SHA-256 is stored (`core_devices`). The profile picker (`core.listProfiles`, access `trusted-device`) and PIN sign-in work **only** from family devices, so names are never shown and PINs never guessed from outside the home: a 4 to 6 digit PIN is a weak secret, usable inside the home only. Admins list and revoke devices; revoking stops the picker and PIN sign-in on that device at once.
- Identity operations share the single SQLite connection and must never run inside a unit of work (transaction).
- **Extensions hold capabilities through people, not on their own.** What an extension's code may reach (tables, files, secrets, other extensions' actions, the network) is fixed by its manifest and enforced by its context (§6 "Isolation"); what a person may do through it is decided by capabilities. Both apply: an action an extension may call still checks the actor.
- Unauthenticated callers of public routes are a system actor (`anonymous`) that holds no capability.
- Route access levels: `public`, `trusted-device` (signed-in member or family device; never a display), `signedIn` (never a display), or a capability id (members by role; displays only for the `view` capabilities they were granted).
- Creating or setting a secret (passwords, PINs, keys, device trust and pairing) is a dedicated route that records itself in the audit log, not an action (§7 "Secrets stay routes"). Revoking a device is the action `core.revokeDevice`: the device is revoked in its transaction (it stops verifying at once, and every PIN session asks whether its device is still active), and its sessions end in the job `core.endDeviceSessions` enqueued with it, since identity calls never run inside a unit of work.
- **Distrusted CA roots.** At start, before any outbound connection (in every command, so backup uploads and extension installs too), the server removes the roots listed in `apps/server/src/tls.ts` from Node's default CA store, matched by SHA-256 fingerprint (never by name), on top of whatever `NODE_EXTRA_CA_CERTS` or the system adds. Today that is the four eMudhra emSign roots, whose intermediate CAs were compromised in October 2026; the list goes once the image's Node ships its own blocklist.
- **Family displays.** A wall tablet or an old TV shows the day without anyone signing in on it, so a display is neither a member nor a family device: it is paired by a code, like a TV app, and shows only what it was granted. It is a `core_devices` row of kind `kiosk` with `display_capabilities` (JSON, view-level ids chosen at pairing) and `display_show_names`; its requests resolve to the actor `{ kind: 'display', deviceId, capabilities, showNames }`. A member session always wins over the device cookie. `access.can(display, c)` is true only when `c` was granted, has level `view`, its extension is on, and (for `core.members.view`) names are allowed. The action runner and `signedIn` / `trusted-device` routes refuse displays outright, so a display never runs an action, never opens the profile picker and never enables PIN sign-in (`trustedDevice` and the device middleware count `family` devices only). The device is verified on every request, so revoking takes effect at once; WebSocket upgrades resolve the same way, and the realtime hub closes a display's open socket on `core.device.changed` (the display reconnects and is checked again).
- **What a display shows** is Today's composition for its style and palette in **family mode**: no person, no "needs you", no actions, no sidebar and no bell, larger type, the photo, and ambient mode after idle. Its grants gate the composition (without `calendar.view` no hero and no day; without `chores.view` no rings; without `ambient.weather` no weather; without `ambient.photos` no photo), and with "show names" off the day has no per-person structure. Today for a person (`/`) is the same composition with the person added.
- **Pairing** follows RFC 8628 and lives beside device trust (routes outside the action runner, `apps/server/src/http/devices.ts`):
  - `POST /core/displays/pair` (public) returns a 256-bit device code (only its hash is stored) and an unambiguous `XXXX-XXXX` user code valid for 10 minutes. Limits: 5 per 10 minutes per client address (IPv6 as its /64), at most 3 open codes per address and 100 family-wide, so a few addresses cannot take every slot; an address on the family's own network (private, loopback, link-local, unique-local, CGNAT) may also use 100 more that no other address can, so a flood from the internet never blocks pairing at home.
  - The display polls `POST /core/displays/pair/poll` every 5 s (faster answers `slow_down`). An admin (`core.devices.manage`) confirms the code with a name and the capabilities it may show (`core.confirmDisplayPairing`; the code is looked up in its `prepare`, outside the transaction, so a wrong code is counted even though the confirmation is refused). The next poll creates the device and returns its token exactly once, as the httpOnly `famos_device` cookie. Five wrong codes end all open pairings; a code is single-use.
  - `core.updateDisplay` renames a display or changes what it may show, and tells its open screens (`core.device.changed`). `GET /core/displays/me` tells the display page its name, grants, time zone and which extensions are off.
  - The display fits Today to its one screen by measuring plans in a fixed order of priority (`apps/web/src/lib/today/fit-plan.ts`): what it was granted (its widgets, who is home) is given up last. It reports what it had no room for with `GET /core/displays/me/fit?leftOut=…` (the display itself only; a read, like all of a display's requests, since it describes the screen and changes no family data) for Settings → Devices; the device service keeps it in memory like a last-seen time, and the display repeats it on every fit and refresh, so a restart forgets it briefly at most.
  - Widgets are `display.widget` slot contributions (with `requires`, an optional `labelKey` naming them on Devices, and a `rows` prop that shortens them before one is left out) and the clock row's pills are `display.status` contributions, both from extension `./web` entries, so a display shows only what its extensions offer and its grants allow.
- **Display content: the `ambient` extension.** It holds what displays show and every outbound call a display causes (the weather), so switching it off in Settings → Family → Extensions stops them all. Capabilities: `ambient.photos` and `ambient.weather` (`view`, grantable to displays) and `ambient.manage` (`manage`). Settings (weather, timing) are one row of `ambient_settings` (JSON validated by Zod; a `version` that moves on every change).
  - **Photos** are images the family uploads (no photo service, so no upstream API to follow). The settings UI shrinks each picture in the browser (canvas, longest side 1920 px, JPEG) and posts it to `POST /ambient/photos` (multipart, `ambient.manage`, 5 MB). The route reads the upload with `readUploadedImage` from `@famos/sdk` (the one image upload path of board notes, recipes and these photos: it checks the size by claim and by bytes, reads type and size from the header, never trusting the declared type (only JPEG, PNG and WebP), and strips EXIF/XMP/IPTC so no stored photo keeps its location, however it was sent), stores the file with `ctx.files` through `storeThenRun` (removed again when the action fails) and records it through `ambient.addPhoto` in `ambient_photos` (file key, type, width, height, byte size, uploader, created at; at most 500). `ambient.deletePhoto` removes the row and enqueues an idempotent job that deletes the file. `GET /ambient/library` lists them for the settings grid; `GET /ambient/photos` returns up to 200 shuffled ids and the slideshow timing; `GET /ambient/photos/{photoId}` streams the file (`ambient.photos`, `cache-control: private, max-age=3600`). Photos are not an AI area and carry no `ai` hints.
  - **Weather**: `GET /ambient/weather` asks Open-Meteo (no key, CC-BY, attribution shown on the display) for coordinates rounded to two decimals, cached 30 minutes; weather off or no place is `{ enabled: false }`, not an error. Caches are per running server, never persisted, and dropped when the settings version changes. Routes that call out use `ctx.http` directly (a bounded read-through a person is waiting for), never inside a transaction. The weather is also a `dashboard.card` on Today (a sky drawn from the WMO code and Open-Meteo's `isDay`, still under `prefers-reduced-motion`).
  - **Ambient mode** is this extension's `display.ambient` slot contribution: it watches pointer, touch and key activity, covers the widgets after `idleMinutes`, and leaves on any interaction.
  - A `setup.step` ("Where do you live?", a city search with Skip) lets first-run setup offer a place without knowing about weather.

## 14. Realtime and offline

- The server is the source of truth. After commit it broadcasts `{ entity, id }` invalidations over one WebSocket; clients refetch.
- The PWA caches the app shell (including the SPA fallback `index.html`, which is not in `$app/manifest`) and the last read models. Every page the server answers is the shell, so each successful navigation refreshes the cached copy and an offline start sees the packages and import map the server last wrote.
- Extension packages have a cache of their own (`famos-extensions`). Once open, the app posts `CACHE_EXTENSIONS` with every file of the listed packages (source maps aside); the service worker fetches the missing ones and drops files of packages no longer listed. Their addresses carry the package's digest, so `/extensions/*` is served from that cache first, and a page of an extension never opened online still opens offline.
- Service-worker updates are pushed (the app asks a waiting worker to `SKIP_WAITING` and reloads on `controllerchange`), because display tabs are never closed.
- Web Share Target posts multipart data to the app; the service worker intercepts and stores it, then redirects to the share screen, which uploads it to the inbox.

### Idempotency keys and the offline queue

The app is used in shops with poor reception, and the common moments are small (tick off an item, mark a task done). Actions already carry what a replay needs (an id, a Zod input, a server-side permission check), so the server stays the only source of truth and the browser queues a few declared actions: no sync engine, no CRDT, no local database.

- Any action call may carry an `Idempotency-Key` header (1-100 characters of `A-Za-z0-9_-`), from a member or an AI agent; the system and displays send none. The key space is per principal, `idempotencyPrincipal(actor)`: `principalOf(actor)`, for an app `app:<id>`, for an app acting for a member `app:<id>/member:<id>`, and for an AI also the member it works for (`ai:mcp:<tokenId>/member:<id>`). So a member's browser and an agent working for that member never share a key, and a stored answer only goes back to the principal that made the call.
- The action runner stores `(principal, key) -> action, status, response` in `core_idempotency` **in the action's own transaction**, so a failed action leaves no key and can be retried. The primary key is `(member_id, key)`: `member_id` holds the member's id for a member and the principal itself for anyone else; the `principal` column records who asked (null on older rows, which count as `member:<member_id>`).
- A repeated key returns the stored answer without running anything (`Idempotent-Replayed: true`); the same key for another action is `422 idempotency_mismatch`. Validation, forbidden and not-found answers are stored too, so a replay answers the same. Keys are kept 7 days (a daily core job deletes older ones). This also absorbs online double taps.
- The MCP door reads the same header on a tool call that proposes a change (a repeat returns the first suggestion's answer instead of proposing again); a malformed key is a tool error, and read tools ignore it.
- `defineAction({ offline: true })` marks actions the web app may queue: idempotent for a repeated key and still meaningful minutes later. Today: add and check shopping items, complete and reopen a task, mark a chore done and undo it. Each has a replay test (same key twice, replay after a conflicting change).
- The web app (`apps/web/src/lib/offline*.ts`) gives extensions `app.runAction(id, input, { offline, label })` and `app.waiting()` through `useApp()`. A call that gets no answer is stored in IndexedDB with its key and resolves `{ queued: true }`; pages show it optimistically with a "waiting to send" mark. The queue logic (`offline-queue.ts`) is pure, with injected storage, network and clock, and unit tested. Replay runs in creation order on `online`, at start and every 30 s; a 4xx (except 401, 408 and 429) moves the change to the "could not be saved" list, anything else keeps it queued with backoff and stops the run so order is kept. The queue belongs to the signed-in member and is cleared on sign-out. Inputs are never logged.
- The service worker keeps the last answer of a short allow-list of read routes: the app's own (who I am, members, family settings) and the ones each extension declares as `offlineReads` in its `./web` entry (paths under its own API; calendar occurrences, tasks, shopping lists and items and chores today). The app posts the list (`OFFLINE_READS`) after it opened and the worker keeps it for the next start, so the shell names no extension. Network first, the stored copy when offline or after 5 s without an answer, marked `x-famos-offline: 1` with a message to the page, which shows "Offline — showing what was last seen". Nothing else under `/api/` is cached. The server marks every API answer, and everything `/mcp` answers, `no-store` for browsers and proxies; this private copy of the allow-list is the one deliberate exception, deleted on sign-out.

## 15. API contract

- Routes are defined framework-neutrally with `defineRoute` from `@famos/sdk` (Zod params, query, body, response, `requires`). The server's HTTP adapter turns them, and every action, into `@hono/zod-openapi` routes, so extensions never import an HTTP framework and handlers are testable without HTTP.
- The running server serves the whole document at `/api/openapi.json` to a signed-in person only (it names the installed extensions). `pnpm gen` (`main.ts openapi openapi.json --extensions ../../extensions`) builds it without the server, split by owner; every part is committed, and CI regenerates them and fails on any difference:
  - `apps/server/openapi.json`: core's and the app's own routes (members, settings, AI, backups, push, Telegram, email, MCP) and `/actions/core.*`;
  - `extensions/<id>/openapi.json`: an extension's routes (`/api/v1/<id>/…`) and actions (`/actions/<id>.*`), with its types in `extensions/<id>/src/web/api.gen.d.ts` (`openapi-typescript`, written by `apps/server/scripts/api-types.ts`).
- `packages/api-client` (types from `openapi-typescript`, runtime `openapi-fetch`) is the only way `web` and extensions talk to the server. Its `paths` are the host's only; `createApiClient<Own>()` adds an extension's own, so an extension's web code (`src/web/api.ts`) is typed against the host's routes and its own and builds without the rest of the app or any other extension. Future native clients use the same documents.
- An extension's types are its `./api` export (types only). Another extension reads them only for a declared dependency (`dependsOn` or `optional`; ambient reads the calendar, kitchen the lists, pets and vehicles the records) and passes them to its client: `createApiClient<paths & calendar>()`. dependency-cruiser fails an undeclared one and forbids `apps/web` from importing any extension's API types or client.
- All routes are versioned under `/api/v1`, and every operation has a stable `operationId` (`shopping.addItem`).

### The public API (`/api/public/v1`)

How programs outside the family (Home Assistant first) read and change data: a third surface beside `/api/v1` and `/mcp`, and a contract other people's code depends on, so it is small, explicit and only grows.

- **Nothing is public unless it is marked.** An extension marks an action with `expose: defineApi({ name, method, path, summary, … })` (several for one action: `complete` and `uncheck` are one action with a `fixed` field each) and a GET route with `expose`. The registry (`apiOperations`, `packages/core/src/api-operations.ts`) refuses a name outside the extension's own, a path or method used twice, a read offered as an action, a change offered as a GET, a PUT without a version-checked `target`, an external action, a route that is not plain JSON or not behind a capability, and an input that is not an object. Marking never says who may call: the action's `requires`, its approval policy and the app's mode decide, in the runner. Expose only what a program has a reason to use.
- **The shapes are the action's and the route's own Zod.** The request body is the action's input minus what the path or `fixed` sets and minus `omit` (fields only a model fills, such as a review `label`), with `describe` to word a field for programs (an action's descriptions are written for a model and name its tools). The answer is the action's output or its `output` projection (`apiOutput(schema, project)`), which drops undo and internal fields (`before`, `merged`, `previousKey`) and applies the wire rules: instants are RFC 3339 with the family time zone's offset (`apiInstant`), all-day values are plain dates, ids are typed, an occurrence is `{ eventId, recurrenceId }` with `seriesId` and `recurrenceKey`, the install-time shopping list is named in the family language with `isDefault: true`. Public schemas are named (`.meta({ id })`) so generated clients get readable types; never on a schema also used nullable, since the document would then mark the component itself nullable.
- **One grammar:** `GET` list and get, `POST` create and named commands (`…/complete`), `PATCH` some fields, `PUT` the whole record (`If-Match` required), `DELETE`. Reads are GET routes because validators need GET. Every answer is `{ items, next, timeZone }`, `{ item, timeZone }` or `{ status: 'applied' | 'drafted', …, timeZone }`; errors are `{ error: { code, message, fields?, reason?, capability?, currentVersion? } }` with a closed `code` enum, our own `fields` for a refused request (not Zod's tree), `feature_off` as its own 404, `precondition_failed` as 412 and `gone` as 410.
- **The door** (`apps/server/src/http/public/`, its own Hono app below `/api/public/v1`, so its OpenAPI registry is separate) reads the bearer through `authenticateApp` and nothing else. It never reads cookies, so there is no request forgery to defend from, no CSRF check and no CORS. A wrong key counts against the client address's IPv6 /64 (the limiter is shared with `/mcp`); each app has its own request limit; `touch` records a use only after both passed. The extension must be on (`feature_off` otherwise).
- **Behaviour on the log of §9.**
  - A list answers with `ETag` = `collectionTag(extension, actor, window)` (the window is the query, the page, the family's zone and language and the hour, since views change without a write), and a matching `If-None-Match` is a 304 before the handler runs. One thing answers with `"v<version>"`. Every write answers with the version it left, in the `ETag` header and the body (read from the row after the write, since the action returned what it saw before its last update).
  - `If-Match` becomes the runner's `ifMatch`; `Idempotency-Key` is the runner's, keyed by principal (§14). The door cuts a list route into pages of up to 500 (`limit`, an opaque `cursor`).
  - `GET /changes?since=` is `kernel.changes.since` for the caller, limited to the extensions that offer operations and are on; without `since` it gives the current cursor.
  - `GET /drafts/{id}` is readable only by the principal that proposed it (the app, or the member through it); anyone else gets `not_found`, and an applied draft's `result` goes through the same projection as an applied change. `GET /drafts?status=waiting` lists pending and failed drafts as Quick add does for the caller (the core list's rules: `mayDecide`, `isProposer`, expiry, a vanished subject): an app alone sees what its principal proposed; an app acting for a member sees that member's view (their own and those they may decide) provided the app's role holds `core.drafts.propose`; `canDecide` is always false. Its validator is the `core` collection tag over the visible ids and states, since drafts that expire or fail are not written through the log; draft events are in the log (entity `draft`) but `GET /changes` leaves them out, as `core` offers no operation.
- **Discovery** (`GET /`) gives the API and FamilyOS versions, the family zone and language, the installed extensions and whether each is on, and the operations this caller may use now: a route when the caller holds its capability, an action by `runner.decisions(actor)` (`apply` or `draft`, never a refusal).
- **The document** `apps/server/public-openapi.json` is generated from the marked set only (`main.ts public-openapi`, part of `pnpm gen`), committed, and checked by CI like the others and by `apps/server/test/public-api.test.ts`; the running server serves its own at `GET /api/public/v1/openapi.json` (for a bearer). `familyos-client` is generated from it.
- **The contract rule.** Within `v1` it is expand-only: operations, response fields, optional request fields, answer enum values and error codes may be added; nothing is renamed, removed, made required or given a new meaning. A client ignores what it does not know. Anything else is `/api/public/v2`, announced in advance and run beside v1. So removing an operation is a major-version act, and a field of a marked output is part of the contract the day it ships.

## 16. Deployment

- One multi-stage Docker image (amd64 + arm64) on `node:24-bookworm-slim` (Debian, not Alpine, to avoid musl edge cases with native modules on a Raspberry Pi). The Hono server serves the built SPA on a single port, so installation is one `docker compose up`. There is no server-side rendering; a client-rendered SPA suits PWA and display use.
- `FAMOS_ROLES=api,worker` (default both; only `api` and `worker`, at least one, or the server refuses to start) lets heavy installations run a separate worker container from the same image. SQLite's single writer still keeps everything on one host.
- Local AI (Ollama) runs in the optional compose profile `ollama` or on another machine, reached by URL.
- The image ships the extension packages in `/app/extensions` (built with `@famos/pack`, gathered by `scripts/collect-extensions.mjs`) beside the server bundle in `/app/server`.
- The entry point is `node /app/server/famos.mjs`, the supervisor that starts the server again when it asks to (installing an extension, Restart); `node /app/server/main.mjs <command>` runs any command without it. Compose's `restart: unless-stopped` covers a crash of the supervisor itself.
- Volume `/data` holds `famos.db`, `files/`, `backups/`, installed language and theme packs, and the generated secret (unless `FAMOS_SECRET` is set). `FAMOS_SECRET` seals provider keys, bot tokens, mail passwords, subscription URLs and backup passphrases; it is never inside a backup, so restoring on new hardware needs it too.
- HTTPS is required for PWA Share Target; the docs cover Caddy and Tailscale.

## 17. Verification strategy

- **Extension tests**: in-memory SQLite with real migrations; actions and routes tested end to end.
- **Port contract suites** for queue, files and LLM; every adapter and fake must pass them.
- **Architecture tests**: dependency-cruiser rules in CI.
- **Migration tests**: empty DB → current; previous-release fixture DB → current; refuse to start on a newer DB (`SchemaNewerThanCodeError`).
- **Backup tests**: backup → restore into an empty volume → data and files are equal.
- **Pipeline tests**: the scripted fake model (`k.llm.respond`) for deterministic extraction; the queue contract recovers expired leases, and handlers are idempotent, so a job cut off mid-run completes without duplicate drafts.
- **The model evals** (`pnpm --filter @famos/ext-inbox eval`, `@famos/ext-assistant`; not in CI, they call real models) measure what a single pass cannot:
  - *Runs.* `FAMOS_EVAL_RUNS=<n>` (default 1) runs each case n times per model, because one run cannot tell a model that misreads one time in three from one that never does. The report gives each case's pass count out of n and each model's median pass rate; the baseline records the pass counts. A case that passed every baseline run is newly failing only when it fails most of its runs. Answers are recorded from the first run only.
  - *Missed or harmful.* A failed check is *missed* when the card refused, skipped, left something out or showed it as unsure, so a person sees there is more to do; it is *harmful* when the card shows a wrong value as certain or acts on the wrong thing, so a person may approve a mistake. Each check says which (`failure`; the helpers `has`, `none`, `total` and `flagged` set it from what was proposed and what was marked "check this"; a check without one counts as missed). The report prints both counts per model; the gate is harmful = 0.
  - *State.* A case may start from a household that already holds things (`fixture`, in `extensions/inbox/eval/household.ts`): lessons with one name for two people, a moved lesson, class and plate codes, two shopping lists, so a message that sounds alike is judged on which thing it reaches.
  - *Replay.* CI replays the recorded answers through the real pipeline with the fake model (`golden.test.ts`). A case with no recording yet is skipped there until a full run records it; its code is held meanwhile by tests that feed it the answer a careful model gives (`sim-cases.test.ts`).
- **API drift**: regenerate `openapi.json`, `public-openapi.json`, the extensions' documents and their types → the working tree must stay clean.
- **E2E (Playwright)**: a small set of essential flows and security boundaries: setup → share → draft → approve → undo; sign-in with a password, and a PIN only on a family device; a supervised member's change becomes an approval; a display reads only what it was granted and follows live changes over the WebSocket. Layout and timing are unit-tested or reviewed in the sweep, not gated by e2e.
- **Docker**: CI builds the multi-arch image (amd64, arm64) on every pull request; the image's `HEALTHCHECK` polls `/health`.
